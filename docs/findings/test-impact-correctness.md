## Go 读取 Web 资源的反例与修复

补充最小工程让 `TestWebResource` 通过 `os.ReadFile` 读取 `web/src/value.ts`。仅将文件中的 `value = 1` 改为 `value = 2`，原生 Go 全量实际失败；修复前，旧计划没有选中该 Go 测试。这个反例保留为失败历史，不将早期六类反例通过解释为已覆盖所有资源依赖。

修复后，Go 文件系统、系统调用、源码读取和原生模块形成保守资源边界。进程与资源消费者在任意源码或资源变化后保留，生产依赖与测试终端依赖仍分开传播。该工程的完整和所选运行都实际执行并失败 `TestWebResource`；外层回归通过，漏选从1变为0。两侧实际执行的顶层根均为 `Example`、`FuzzA`、`TestA`、`TestB`、`TestWebResource`。

[机器可读证据](test-impact-correctness.json) 包含六类仓库反例的失败根名、两侧原生 run/fail 事件、选择数量、源码指纹、当前 Web 清单与失败文件，以及第七个最小工程反例的双侧原生事件和修复前后日志摘要。含本机信息的命令行、业务输出和临时路径没有进入公开证据。旧工具的仓库反例及配对只作为历史诊断，未混入修复版本的收益周期。

这些反例与回归证明已验证的边界没有漏选，不证明任意未知外部行为均可自动归属，也不证明相同函数覆盖等价于重复业务断言。缺少收益及完整门禁切换证据时继续 shadow。

## 后续独立 review 的补充边界

第三方 helper 包装文件系统调用时，只有解析主 module 的 import 不足以证明无资源依赖；完整依赖图和仅测试依赖都需要播种及传播文件系统边界。另一个反例使用 Go compiler overlay 替换被忽略或仓库外的源码：路径不变而内容改变时，旧版只记录 flags 文本，导致全量失败但选测空集合通过。两类遗漏均保留为旧版失败历史。

修正后的最小工程回归已实际执行全量和所选根并检出失败：第三方生产/测试导入两种路径，以及被忽略、仓库外、含空格相对路径三种 overlay。overlay 清单和替换内容参与身份；首版始终完整验证，并拒绝发布函数映射基线。新增虚拟文件、删除文件及检查期间替换内容变化也有回归。仓库六类复测现已完成，本文和配套 JSON 均使用上文明确登记的复测源码。


## 构建、链接和执行边界复测

十五个双侧真实失败反例覆盖：Go→Web 资源读取、第三方生产/测试 helper 文件读取、三类 compiler overlay、三类 alternate module 配置、本地模块和 workspace 修改、忽略/仓库外/已跟踪软链接目标变化，以及本地模块嵌入文件执行权限变化。完整与选测的目标根均实际启动并失败；每个反例的原生事件、源码树和日志摘要保留在 JSON 的 `CurrentBoundaryEvidence`。overlay、alternate module/workspace 和本地可变模块继续完整回退；未知资源不据此形成精细依赖。

完整本地集合复用分别验证 shadow 与 affected 只运行一次原始 Go 根，且拒绝启动额外选测器仍可通过；取消回归实际阻塞嵌套 race 调度器的独立子进程组，再取消并核对进程消失。十次取消压力检查保留其较早工具身份，不将其说成当前版本十次重跑。

最终 review 还要求修复两处验收问题：清洁仓库中的未知缓存链接应允许发布不含函数归属的静态索引，使用它仍需全量；故障审计必须核对所选根实际失败。新增真实基线 CLI 测试验证目录及悬空链接下普通全量成功后可建立 `static-resource` 索引，移除链接后旧索引也不能缩小；新增原生失败反例验证“目标通过、其他根失败”被拒绝。既有六类故障日志已另行重新解析，所有47个全量失败根在选测中都有实际 run 和 fail，不能由无关失败替代。
