# 剩余空闲 CPU：调度与用量组装

## 现场线索与复现

初始运行版本为 `578c6672155c`。无正在执行的 run 时，server 的三段十秒
采样为单核 12.1%–17.7%。十五秒用户态采样中，后台会话池资格检查约占 44%，
用量 API 约占 22%，并发预算维护约占 9%。后续三十秒采样期间出现业务活动，
这些比例不能直接当作同负载的性能前后对比。调查期间运行版本又发生替换；
性能回归使用固定的旧版本数据快照、时钟、查询和进程配置。

快照有九个后台候选：七个引用当前不可用的执行环境，一个等待 runner manager
责任恢复，一个可以选出运行环境。队列按到期时间反复选入这些候选，后台池
每秒完整调用 PendingAgentConversations，逐项重做 runtime、Issue 归属和队首
检查。等待条件没有变化仍执行同一资格链，这是独立于历史用量采集的重复工作。
隔离测量六十次资格查询，平均约 20 ms、0.81 MB 分配；本次改变调用次数，
不缓存或弱化真正执行前的资格与归属验证。

并发预算维护也每秒进入写事务，重建 waiting 和执行负载，保存仅采样时间变化
的状态。空组没有饱和时间可积分；没有具体截止时，无须重复此工作。

## 用量 API 的成本

分组器在每个贡献上重新序列化 session 已有的全部 attribution，然后再次
序列化 execution attribution 以寻找匹配项。同一历史 Session 包含多个执行、
模型和时间桶时，序列化与比较随已有执行数增长；SQL 查询快并不代表完整 API 快。

使用同一数据快照、固定时钟、GOMAXPROCS=2，每种查询三十次；经过实际 Go HTTP
handler 的鉴权、数据库读取、组装与 JSON 序列化，身份查询使用固定替身，
不包含真实网络/TLS 延迟。索引仅存在于单次查询的分组器，保持完整 attribution
JSON 的原等价关系，包括 nil 与空切片的区别，不缓存跨请求身份或结果。

| 查询 | 原耗时 | 修改后耗时 | 原分配 | 修改后分配 |
| --- | ---: | ---: | ---: | ---: |
| 全历史 session 列表 | 145.5 ms | 82.3 ms | 39.6 MB | 15.5 MB |
| 全历史 session 明细 | 157.2 ms | 92.0 ms | 44.8 MB | 20.7 MB |
| 最近七天 Issue 列表 | 148.4 ms | 83.0 ms | 39.6 MB | 15.5 MB |

三个响应的完整字节摘要均相同。以上是隔离测量，不代表整机 CPU 降幅。
现场调用栈证明 API 正在被调用，但尚无可靠的客户端与请求频率记录；不能仅据
样本把它归因于旧 Web 的十秒循环。未取得的来源观测保留为证据边界。

## 修复与验收

后台池在扫描前捕获提交广播，等待事实变化、实际队列/回执截止、附件退出或
具体失败的有界重试；无变化历史不产生一秒定时器。附件退出同时释放容量并
唤醒等待方，失败按会话退避；真实执行仍重新校验，未知原请求不重放。

并发控制将活跃/未知执行及等待需求改为三十秒采样，周期内合并通知，空组等待提交后的负载变化、
冷却结束或证据保留期限。内部负载/反馈/等待事实成功提交后唤醒，事务失败不
发布变化。恢复采样仍由原领域规则使缺失采样区间的饱和证明失效，不补算空闲。

回归覆盖一千个已完成用量来源和一千个不可运行积压，在虚拟时间一分钟内没有
周期扫描；事实变化后重新扫描，未来队列截止与具体失败重试仍保留。用量回归
验证执行、CLI 版本、nil/空 attribution、祖先汇总及明细不被错误合并。
生产部署及现场收益单独验收；旧 updater 的日常哈希须在实际二进制替换后复测。

独立 review 补齐两条截止回归：扫描过程中到期的工作仍安排立即复查；已取消 recovery 的 successor 若仍有原回执，继续按原回执截止唤醒。附件即时退出暴露的竞争也已修复：已消费数据库前缀的 closing manager 等原关闭回执，不能重新打开 native 会话。

启动退避同时覆盖 pending 和 sending 的原 outbox 截止；活跃 manager 虽仍由租约候选发现，后台池在创建附件前核验冻结 startup attachment 的准入，避免 intentional pause 经本地完成广播反复自唤醒。
