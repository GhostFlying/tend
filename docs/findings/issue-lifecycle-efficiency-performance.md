# 集中修复：候选构建与 writer 同快照对照

本次离线对照验证候选读取、空领取和普通 ACK 的写入影响。新的路径减少了候选读取和无工作领取占用的 writer；并发负载的排队及尾延迟下降，但 heartbeat 中位延迟没有改善。这里没有测量 HTTP 外层，也没有确诊此前生产环境的 21 秒停顿或一次 2,441 ms 的候选收集。

Refs: D224；实施范围见 `docs/plans/issue-lifecycle-efficiency.md`。

## 数据和源码身份

输入是同一份保留的历史 SQLite 快照，828,727,296 字节，SHA-256 为 `3bcfca1c81bbbec58a9006b507b00e1ca60d652bb8f2e82bd3490ebe7445e5f3`。源快照只读打开，测量使用独立副本；测量后核对源文件摘要未变。迁移和用量投影刷新在计时前完成。

基线来自提交 `6cfdf3f9a2c75947f77fc759eb47ba4683329a34` 的完整源码。新路径使用同一提交上本计划的工作区实现。并发测量的基线二进制 SHA-256 为 `90f4de67321385a974cad111c1f58cd02b4c1acf5a66cdd213d872293531c355`，新路径为 `d2577223d750acd4b6d5d59830bf01504dbf7c22b770bcbf013bc2b5ba18d4fc`。

新二进制测量后增加了领取事务内的容量提前返回；本次新路径由读侧发现容量已满，没有进入该新增分支。上述摘要限定本次测量的实际代码身份，不代表最终合入候选或线上版本的性能验收。

## 候选投影

原快照没有待调度候选。在一次性副本中，将两份已有负责人责任及其原任务、动作恢复为可调度状态，其余历史保持相同。基线函数使用原逐项查询和完整 Issue 读取，新函数批量读取最小调度事实。交替执行三轮只读构建，两条路径返回相同的两份候选，序列化结果摘要均为 `930e85dc6e16cff8cdb3b33568b0240c74d07456e2439a60d382bced7c42ed90`。

| 指标 | 基线 | 新路径 |
| --- | ---: | ---: |
| 查询调用数 | 34 | 11 |
| 热读中位耗时 | 1.855 ms | 1.303 ms |
| 首轮耗时 | 10.067 ms | 1.367 ms |

热读中位耗时降低约 30%。首轮受缓存和运行顺序影响，不据此推断生产冷启动收益。这是两份候选的投影构建对照，不是大队列或历史生产停顿的复现。

## 并发 App 调用

两个副本执行相同负载，分别运行对应的原生协议版本。保留原执行节点身份和 Agent 库存，在副本中将一个已有 Run 标记为 unknown，使单 slot 节点保持实际占用；因此所有领取都应返回无工作。选择相同的 60 条原生事件，将其 ACK 标记恢复为未确认，每条仅确认一次。准备阶段不计时。

同时启动三个领取协程（各 20 次）、一个 heartbeat 协程（60 次）及一个事件 ACK 协程（60 次），共 180 次调用。直接调用 `App.Execute`、`App.RuntimeHeartbeat` 和 `App.AcknowledgeManagerEvent`，不含 HTTP、网络编码或传输。使用相同的 `GOMAXPROCS=2`，进程在隔离网络命名空间内执行；没有 harness、模型或业务执行。每个版本只进行一次有界测量。

两版本均为 180 次成功调用、零错误，目标事件剩余未确认数量均为零。

| 指标 | 基线 | 新路径 |
| --- | ---: | ---: |
| 总耗时 | 817.118 ms | 227.834 ms |
| writer 事务数 | 180 | 120 |
| 其中领取写事务 | 60 | 0 |
| writer 占用估算合计 | 809.744 ms | 222.532 ms |
| writer 排队 p50 | 10.644 ms | 1.973 ms |
| writer 排队 p95 | 59.963 ms | 4.216 ms |
| writer 排队最大值 | 81.587 ms | 12.840 ms |
| writer callback 合计 | 798.704 ms | 216.123 ms |
| writer callback p95 | 11.903 ms | 4.111 ms |

占用估算取每次写入的总耗时减连接等待，包含 callback 和事务收尾的经过时间，不等于 SQLite 独占锁时间或 CPU 时间。并发请求的排队合计可能大于总墙钟时间。

| App 操作 | 基线 p50 | 新路径 p50 | 基线 p95 | 新路径 p95 | 基线最大值 | 新路径最大值 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Claim | 32.326 ms | 1.422 ms | 71.850 ms | 4.471 ms | 79.792 ms | 47.701 ms |
| Heartbeat | 2.635 ms | 2.965 ms | 63.543 ms | 6.710 ms | 70.526 ms | 16.301 ms |

Heartbeat p50 略高；该负载只支持排队和尾延迟改善的结论，不支持所有延迟分位均改善的结论。基线领取的候选阶段合计 150.747 ms，p50 为 2.350 ms、p95 为 3.485 ms；选择阶段 p50 为 5.581 ms。新路径在实际占用已满时读侧结束，因此该负载没有领取候选阶段。

普通 ACK 现在仅在真实改变记录时通知读侧；重复 ACK 不广播，关闭或终止回执实际解锁资源时才通知调度。对应回归另外验证空长轮询不会被普通用量写入反复唤醒，而业务动作仍可唤醒并原子领取。并发测量没有验证所有事件正文上传路径。

## 诊断边界

新增观测将候选阶段分为查询、扫描、转换以及负责人候选查询、扫描和组装，并保留 writer 排队、callback 和事务收尾。正式领取仍在写事务内重新校验控制版本、租约和实际并发资源；读侧预筛不授予执行权。

这次实验没有生产压测，没有重放外部操作，没有以增大超时替代修复。两份候选、固定负载和单次离线运行不足以代表所有规模。此前 21 秒停顿仍属原因未确认；此前生产样本中的 2,441 ms 候选构建也未被此次毫秒级离线构建复现。发布后应根据新增分段日志和同类实际请求继续确认。

## 正文迁移的空间与耗时

同一份 828,727,296 字节快照的另一独立副本验证了历史正文迁移。迁移先校验并持久化文件，再以有界事务提交引用；在完成回读验证后，只对这份离线副本执行物理压缩。源快照摘要保持不变。

| 项目 | 字节 |
| --- | ---: |
| 原 DB | 828,727,296 |
| 迁移并压缩后的 DB | 193,957,888 |
| 新原件文件 | 304,078,866 |
| 已知合计 | 498,036,754 |
| 已知减少 | 330,690,542（39.9%） |

共处理 20,888 条候选，其中 20,830 条完成迁移；58 条无法关联原命令的历史回执保留正文并登记例外，没有用空引用替代。213 个批次耗时 3 分 50.275 秒，最大 writer callback 为 309.878 ms。迁移使用持久水位，原请求重试不会变成下一批。

该快照没有包含既有附件文件，因此上表不包括这些附件、完整备份或生产节点的全部占用。它证明已知 DB 与新增文件的合计收益，不能当作线上总磁盘收益。

正常协议 3 执行另有自动增量原件归档；其回归覆盖原件先持久化、Unicode 分块、半行备份恢复、同 session 跨 Run 关联、丢回执和重复请求。原始 JSONL 的全部字节都保留，索引沿用现有预览的单行 16 MiB 边界；更大记录仍可读取原件，但不解析子值索引，相关正文可能保留独立原件。已写文件但未提交引用的尾部不会作为有效业务记录，本批不增加自动回收。上述并发 writer 对照没有包含新原件上传负载。
