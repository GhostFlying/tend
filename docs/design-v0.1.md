# 中心化 Agent 任务管理服务：系统设计 v0.1

**版本日期：2026-10-14**  
**状态：产品边界已确认；协议与实现细节为设计建议，外部适配尚未实测。**  
**初始形态：Linux 常驻服务 + 纯 Web 客户端 + Codex / traex harness。**

> 用户只与一个中心 Agent 交流，由系统承担任务关联、分派、跟进和独立验收的组织工作。任务账本而非聊天记忆负责保存事实与承诺。所有应用请求具备稳定的 request ID；通过 harness hook 注入当前工作上下文，但不重建底层 agent loop。

本文汇总本次讨论的共识，并补充可进入实现阶段的边界与协议建议。标为“已确认”的内容来自用户选择；其余是初版建议，不代表功能已经实现，也不默认第三方接口具备本文要求的可靠性。

## 1. 要解决的问题

当前并行任务分散在多台机器、多个执行工具和多个 session 中。用户必须不断定位窗口、回忆上下文、检查进度、回答问题、启动下一阶段。新的系统不是把 session 列表换成聊天界面，而是接过这些管理责任。

日常交互应允许用户直接说：

> “Windows 修复先做，WPT 继续排队但别占满机器。前面那个方案先独立 review，通过后再实现。”

系统负责识别相关工作、更新优先级与约束、记录条件式承诺、分配执行环境，并在结果到达后按授权推进。用户不必先选择 topic 或找到对应 session。

**首要产品判断标准：是否减少用户被迫亲自寻找 session 的次数。** 初版由实际使用体感判断，不建设行为埋点、统计仪表盘或管理效率评测平台。恢复、审计和排错需要的请求与任务事件仍须保留。

## 2. 已确认的产品与架构边界

| 编号 | 决策 |
| --- | --- |
| D01 | 默认所有用户输入经过主 Agent 理解；不要求用户维护 topic，也不以绕过主 Agent 作为主要省 token 手段。 |
| D02 | 任务账本是目标、状态、依赖、约束与未完成承诺的权威记录，不能仅依赖 session 历史或模型摘要。 |
| D03 | 初版只持续管理本系统创建的任务。可提供一次性扫描导入，但不与旧系统持续同步。 |
| D04 | 在已授权目标与预算内自主推进；扩大目标、降低验收标准或越过高风险操作边界不能静默执行。 |
| D05 | 验收由独立 Agent 完成，不由主 Agent 或实现 Agent 自行替代。 |
| D06 | 主 Agent 平时保持管理视角，深入技术讨论时按需读取相关材料，不常驻所有 worker 的完整历史。 |
| D07 | 人工接管后暂停针对该执行的自动干预，保留观察；恢复托管前对齐状态。仅查看不是接管。 |
| D08 | 优先级影响排队与后续资源分配。初版不做自主抢占杀任务，不急于支持执行迁移。用户明确停止仍须支持。 |
| D09 | 主 Agent 复用现成 harness，首选候选为 Codex 和内部 traex（由用户说明为 Codex fork）。 |
| D10 | 通过 hook 注入当前任务上下文；不把无法任意重写 harness 内部历史误解为不能主动提供上下文。 |
| D11 | 所有应用请求携带唯一 request ID。同一逻辑请求的重试保留原 ID；不同逻辑动作不能共用一个 ID。 |
| D12 | 服务常驻 Linux，通过远程方式使用，不依赖随身 Mac 开机。初版纯 Web，后续可用 Electron 包装同一客户端。 |
| D13 | Orca、自研工具以及未来其他执行后端可替换；任务模型不绑定它们的 session、workspace 或看板数据结构。 |
| D14 | 初版不建设用户行为效果度量功能；保留保障正确性必需的事件记录与测试。 |

初版建议按单用户、单权威控制服务实施，不做多租户、跨区域控制面或多主调度。单用户仍需远程鉴权与角色权限隔离。

### 2.1 非目标

初版不重建完整 coding harness，不提供完整 IDE 或多终端网格，不把旧 session 全量实时纳管，不迁移运行中的上下文与进程，不自动终止低优先级工作腾资源，不训练专用路由模型，也不建设通用插件市场。

为保证边界清晰，初版不承诺任意外部系统的端到端 exactly-once。对于执行结果无法确认的操作，保留 unknown 并对账，不盲目重跑。

## 3. 总体结构与部署

| 层 | 组件 | 职责 |
| --- | --- | --- |
| 客户端 | Web UI；后续 Electron | 单一聊天、看板、待决事项、任务详情；保留未确认发送的 request ID；断线后恢复视图。 |
| 应用边界 | API / 事件服务 | 鉴权、请求接收与去重、流式响应、历史读取、附件与产物访问。 |
| 控制层 | Task Service / Scheduler | 任务契约、状态转换、依赖、优先级、资源预留、授权、后续动作和独立验收流程。 |
| 上下文层 | Context Builder / Hook Bridge | 查询账本与对话关联，生成有界注入内容，处理版本、恢复与注入记录。 |
| 推理层 | Harness Adapter | 驱动 Codex / traex 的主对话和任务范围的后台决策上下文。 |
| 执行层 | Execution Adapter / Runner | 在 Linux、Windows、macOS 等已配置环境执行实现与验收任务，提供结果、状态及控制回执。 |
| 持久层 | 数据库 / 产物存储 | 保存请求、任务、动作、执行映射、事件、审批、验收、上下文快照与不可变产物引用。 |

以上是逻辑模块，不要求拆成微服务。建议第一版一个应用后端配一个数据库，harness 是受管理的子进程或本机服务，执行节点按需独立部署。

Linux 后端持有主 harness 的连接。浏览器不直接连接 app-server，不持有模型账户凭据，不负责调度。服务到执行节点的路径不得依赖用户的随身电脑中转。

客户端离线不改变任务生命周期。服务器宕机期间，worker 可完成已获授权且能安全继续的当前工作；新的跨阶段动作等待控制服务恢复。节点不可达时不视为进程已退出。

### 3.1 建议的最小持久化形态

使用具备事务和唯一约束的关系型数据库。初版可采用单机本地持久盘上的 SQLite，或已有 PostgreSQL；这是实现选择，不进入核心协议。产物初版可保存到服务端文件目录，由应用提供鉴权读取。

保留任务当前投影和追加式领域事件，无需实现完整的事件溯源框架。事件至少记录来源、相关请求、对象版本和变化；能解释一次状态转换，不要求记录模型内部推理。

数据库、harness 会话数据、产物及敏感配置均需有备份方案。恢复旧备份后先对账，不直接重发备份之后可能已执行的操作。

## 4. 领域模型

### 4.1 任务不是 session

一个任务可以经历多个实现与验收 run；一个 run 使用某个后端 session，但 task ID 与后端 ID 永远分离。用户看到的是任务及其业务进度，session 是需要时才能展开的执行详情。

| 对象 | 关键字段与意义 |
| --- | --- |
| Task | task_id、标题、目标、spec_version、control_revision、优先级、依赖、生命周期、控制模式、阻塞原因。 |
| TaskSpec | 不可变版本的目标、范围、约束、验收条件、交付要求、来源消息与获准预算；新要求形成新版本。 |
| PlanAction | action_id、任务阶段、触发条件、目标版本、授权范围、动作代次、状态；承载“完成 A 后做 B”的承诺。 |
| Run | run_id、task_id、action_id、角色、后端与主机、会话映射、执行代次、期望状态、观测状态、结果、最后确认时间。 |
| Artifact | artifact_id、任务与 run、不可变内容标识、存储引用、校验信息、访问范围。 |
| Acceptance | acceptance_id、验收 run、目标 spec_version 与 artifact_id、判定、证据、问题；由验收身份提交。 |
| Decision | decision_id、待决问题、选项、作用域、版本、状态、原始提问与回答消息。 |
| Approval | 对某个确定动作、参数、版本和期限的授权，不与“选哪个方案”的一般问题混为一谈。 |
| ConversationBinding | 消息与任务／决策的关联、显式引用、讨论候选、可见上下文、已确认的指代。 |
| RequestRecord | 请求身份、调用方、操作、payload_hash、操作状态、稳定结果引用、父请求与下游映射。 |
| Event | event_id、来源、对象 ID、来源序号、相关 request ID、对象版本、内容引用。 |
| ContextPacket | packet_id、context_epoch、关联 turn、账本版本、内容摘要、注入状态及所用材料引用。 |

`control_revision` 用于控制指令的并发校验；进度心跳不必提升该版本。`spec_version` 只在任务要求发生实质变化时提升。展示快照另带事件游标，不把上述版本合并成一个不断抖动的字段。

### 4.2 后端映射

外部身份必须带命名空间，例如 backend_id、host_id、native_session_id、native_run_id。不同 Orca 实例或不同机器上的相同字符串不表示同一对象。

TaskSpec、PlanAction 和 Acceptance 不引用 Orca 专属状态枚举。适配器把外部观测转换为规范状态，同时保留原始状态与证据，不能将无法解释的状态强行映射为成功。

## 5. 生命周期与控制语义

### 5.1 区分三类状态

**任务生命周期**建议包含 draft、queued、running、awaiting_acceptance、changes_required、completed、cancelled。等待资源、等待授权、验收环境不可用等另记录阻塞类型，界面投影为“受阻／待决”。

**控制模式**独立表示 managed、paused、human_control。暂停可以发生在任务任意未结束阶段，不应通过篡改完成状态表达。

**Run 观测状态**至少区分 starting、running、waiting、finished、failed、interrupted、unknown。它描述事实，不自动代表任务验收结论。

例如“暂停已请求，worker 仍在运行”是合法且必须可见的组合。不能把用户表达的期望直接伪装成执行事实。

### 5.2 完成的条件

任务仅在当前要求与当前产物获得独立验收通过，且满足该任务约定的交付条件后进入 completed。主 Agent 不能直接调用无条件的 `mark_completed`。

如交付要求只到“生成可合并补丁”，通过验收后可以结束；如明确要求创建 PR、合并或发布，需额外满足相应授权与交付步骤。验收通过不自动授予合并或发布权限。

### 5.3 条件式承诺

“验证结束后独立 review”保存为 PlanAction，记录触发条件、关联版本与授权。依赖满足由程序查询与触发，不靠主 Agent 记起聊天，也不依赖语义检索发现。

主 Agent 应先提交任务／动作记录并收到服务确认，再表示“已安排”。仅在聊天里答应，没有落账，不算接受了可持续履行的承诺。

## 6. 单一聊天与任务关联

每条用户消息可以关联零个、一个或多个任务。纯讨论不自动创建任务；补充已有要求更新原任务；明确的新工作才创建任务。关联由主 Agent 决定，系统提供候选与证据。

### 6.1 对话焦点与后台事件分离

后台结果自带 task_id，不改变用户对话焦点。任务正在运行，不表示用户正在谈它；最近发生的系统事件，也不表示用户下一句的指代对象。

例如先讨论 Windows 修复的两个方案，期间收到 WPT 完成通知，用户随后说“按第二个来”，应关联前述方案决策，而不是最后到达的通知。

### 6.2 多客户端仍然是同一入口

客户端可自动携带 reply_to_message_id、last_seen_conversation_seq 等可见上下文元数据，不要求用户选 topic。用户从手机回复旧问题时，关联应以该回复的实际对象为主，不能只按服务器最后一条消息推断。

前台主 thread 初版按消息顺序串行处理。用户新输入可以排队；不会因为需要响应而并发写入同一 harness thread。停止按钮和已明确对象的审批通过结构化控制路径处理，不等待主模型完成长回复。

### 6.3 模糊指代

主 Agent 查询相关任务与决策后仍无法确定对象时，针对业务对象澄清，例如“暂停 Windows 验证还是 WPT？”不能要求用户找 session ID，也不能凭低置信度触发有副作用的操作。

自然回复应显露关键关联，例如“Windows 修复按第二个方案推进”，以便用户即时发现串线。

## 7. Hook 驱动的上下文注入

### 7.1 核心选择

由控制服务构建工作上下文，通过 harness hook 注入；主 Agent 再通过工具读取详细材料。Hook 负责把最新任务事实主动送到模型面前，不负责再用一个 LLM 分类用户消息或复述需求。

当前 Codex 官方文档列出 `UserPromptSubmit` 的 `additionalContext`，以及压缩后 `SessionStart(source=compact)` 的上下文补入。`PreCompact` / `PostCompact` 不作为这里的上下文注入出口。[S1]

traex 的具体事件、回传格式与适配能力需针对实际内部版本验证。本文不以 upstream 接口名作为跨 harness 的核心契约。

### 7.2 注入触发与范围

| 逻辑触发 | 内容 | 初版规则 |
| --- | --- | --- |
| 主会话启动或恢复 | 全局角色约束、未完成承诺、待决事项索引、近期讨论关联 | 生成有界恢复快照；不回灌所有 worker 日志。 |
| 用户提交消息 | 当前讨论焦点、相关任务最新状态与约束、明确待决问题、重要变化 | 同步准备当前工作集；主 Agent 决定最终关联。 |
| compact / clear 后恢复 | 必要角色约束、当前任务索引、未兑现承诺与近期决策 | 新 context_epoch 下补完整必要快照，不能仅依赖压缩前 delta。 |
| 任务范围后台推理 | 对应任务要求、动作、失败／验收结果与证据引用 | 在独立内部上下文处理，不抢占前台对话焦点。 |
| 一般执行事件 | 状态与产物更新 | 只落账，不默认唤醒模型或追加到主 thread。 |

不承诺每次模型内部采样前都有 hook。长 turn 中状态变化，仍由服务端操作校验拦住过时动作，必要时在已支持的工具边界反馈；不能等下一次注入才阻止错误写入。

### 7.3 ContextPacket 建议内容

一个 packet 包含 packet_id、context_epoch、相关消息、各任务的 task_id / spec_version / control_revision、必要约束、待决事项、候选关联与详情引用。时间信息只在影响决策时加入，避免每次无意义变化。

注入前候选选择可利用回复关系、明确任务别名、当前待决问题、最近讨论和文本检索。初版不要求向量数据库或额外分类模型；候选不是已确认路由。

超预算时，优先保留安全与任务范围约束、当前待决问题和执行阻塞事实；减少无关任务数量及普通进度。不要截断一半约束来保留更多状态行。

建议把每轮注入预算做成配置，例如先以约 1–2k token 为目标，再根据真实任务调整。这是初始设计参数，不是性能结论或保证。不得把 token 预算当理由省略必要的原始要求；内容不适合直接注入时，必须保留可获取的不可变引用。

### 7.4 注入身份、去重与恢复

同一次 hook 调用的重试保留 request ID，并返回同一个已生成 packet。不能在重试时悄悄改成读取最新状态、却仍声称是原请求。新的状态读取或重新规划属于新请求。

packet 的生成、交付和 harness 接纳应分别记录。Hook 函数返回成功，不等于已经证明模型消费了内容。没有可靠的接纳证据时，不推进“只发 delta”的基线；恢复时宁可补一份小而完整的版本化快照。

初版优先每个相关用户 turn 注入有界的当前快照。只有能确认基线仍在上下文中，才做 delta 优化。compact / clear / 历史重建后必须重新建立基线。

重复返回同一个 packet 不自动保证 harness 不会重复追加。对不提供注入确认或原生去重的版本，不能宣称严格只注入一次；用小快照、版本标识与服务端副作用校验控制风险，而不是因担心重复就漏掉关键约束。

### 7.5 并发绑定

Hook 必须按 harness 实例、thread、turn 和调用身份读取上下文，不使用全局的“当前任务文件”。服务端在开始 turn 前保存待执行消息与请求映射；当 hook 先于 turn/start 的返回到达时，也能从该 thread 的已登记单次启动记录找到归属。

同一前台 thread 的启动串行化，不同后台上下文具有独立映射。不能让多个线程共用一个可变环境变量来表达 task_id 或当前请求。

### 7.6 信任与失败边界

注入内容区分服务端权威状态、用户指令引用和不可信执行产物。原始日志、仓库文件或 worker 的自由文本不直接当作开发者指令注入；默认放入按需读取的证据区。转义和标记只能减少混淆，不能代替权限校验。

Hook 是上下文机制和辅助护栏，不是授权根。Codex 官方文档也提醒工具 hooks 不是完整强制边界，部分失败不会阻止调用。[S1]

因此所有任务写入、调度和验收提交最终在服务端校验身份、权限、对象版本与控制模式。Hook 不可用时不静默宣称上下文正常；不确定或缺少授权的变更被服务拒绝，允许不产生副作用的说明或查询。

## 8. 所有请求的身份与幂等协议

### 8.1 ID 的准确语义

**一个逻辑请求一个 request_id；同一请求的传输重试保留原 ID；新的业务意图使用新 ID。**

所有应用请求包括浏览器 API、MCP 工具调用、hook 回调、调度调用、执行节点控制、审批提交、验收提交和只读查询。心跳每次观测是新请求，重传同一次观测保留 ID。

request ID 由客户端 SDK、harness 适配层、runner 或服务代码生成并保存，不要求模型自己编 UUID。首个受控边界如无法获得调用方稳定身份，需要显式承认只能提供有限去重；不能每次收到重试都生成一个新 ID 然后声称实现了幂等。

对上游不接受自定义字段的协议，保留本地映射，不把未知 `request_id` 字段强塞进原生参数。JSON-RPC 的 `id` 用于请求与响应关联，并不单独提供持久幂等保证。[S3]

### 8.2 标识的分工

| 标识 | 作用 |
| --- | --- |
| request_id | 一个逻辑调用的幂等身份；所有传输尝试共享。 |
| parent_request_id | 直接触发当前调用的上游请求。 |
| trace_id | 将一条用户请求及其所有派生调用关联起来，不作为去重键。 |
| transport_attempt | 网络发送尝试编号，可递增，不改变 request_id。 |
| action_id / effect_key | 某个业务阶段动作的稳定身份，用于防止模型重放或事件重投后用新请求重复产生同一动作。 |
| run_id | 一次实际执行尝试；修复后重新验收等新的业务执行产生新 run。 |
| event_id | 一条事实事件的身份，重投不改变；不同事件不可仅因内容相同而合并。 |
| rpc_id / tool_call_id | harness 原生传输身份；映射到应用请求，不与其他标识混用。 |

子动作具有各自的 request ID，并在首次发送前持久化。例如用户请求 R0 导致调高优先级 R1、启动实现 R2、安排验收 R3，它们共享 trace_id，但不是四次使用 R0。R2 的网络重试仍是 R2。

### 8.3 请求信封示例

以下是本系统的设计格式，不是 Codex 原生 RPC 参数。示例 ID 为可读占位符，生产中使用具备足够随机性的全局唯一值。

```json
{
  "request_id": "req-worker-start-02",
  "parent_request_id": "req-user-message-01",
  "trace_id": "trace-user-message-01",
  "operation": "execution.start",
  "target": {"type": "task", "id": "task-windows-fix"},
  "expected_control_revision": 12,
  "payload": {
    "action_id": "action-implement-v3-1",
    "spec_version": 3,
    "host_id": "windows-builder",
    "spec_ref": "artifact-task-spec-v3"
  }
}
```

调用身份从鉴权上下文取得，不能相信 payload 自报的角色。服务端为规范化操作与业务参数计算 payload_hash；不把重试计数、传输时间和可更新凭据纳入业务哈希。

### 8.4 接收方规则

| 条件 | 处理 |
| --- | --- |
| 缺少或非法 request_id | 在产生副作用前拒绝。 |
| 首次有效请求 | 验证权限与对象前置条件，持久登记；获得唯一执行权后推进。 |
| 同 ID、相同业务参数、已成功 | 返回原操作及原结果引用，不重复执行。当前对象状态可另行读取。 |
| 同 ID、相同业务参数、仍处理中 | 返回同一个 operation/run 句柄及处理中状态，不启动第二份。 |
| 同 ID、不同业务参数 | 返回参数冲突，例如 HTTP 409；不能覆盖第一次请求。 |
| 同 ID、原执行明确失败 | 返回已有失败状态；按原操作的恢复策略处理，不因网络重试擅自创建新 run。 |
| 原操作结果 unknown | 返回待对账状态；禁止把 unknown 简化成可安全重跑。 |

去重键在每个接收方至少包含应用身份域和 request_id。每次返回重放结果仍检查当前访问权限，防止撤权后凭历史 ID 读取敏感结果。

同样的文本使用不同 request ID，可能是用户有意再次执行，不能只按内容哈希去重。哈希用于验证相同 ID 没有被不同意图复用，而不是替代请求身份。客户端重试保留 ID与参数一致的模式，可参考 AWS 的幂等 API 设计讨论。[S4]

### 8.5 只读请求与保留期限

只读请求也携带 ID，支持在途合并与重试关联；用户再次刷新状态是新的读取意图，使用新 ID。普通只读结果不需要永久保存。需要固定视图时显式指定快照版本，而不是让一个查询 ID 永远冻结“最新状态”。

有副作用请求的去重记录必须持久化，覆盖任务／资源生命周期和可接受的迟到重试窗口。初版建议不自动删除控制请求的最小去重记录；大响应可以转为产物引用。未来清理需保留已使用 ID 的最小标记或采用明确过期协议，不能因缓存过期让旧创建请求重新生效。

### 8.6 必须具备业务动作去重

request ID 防止同一调用重传，但不能单独防止以下情况：主 Agent 恢复后生成一个新的 tool_call_id，再次要求启动它先前已经启动过的阶段。

因此 PlanAction 具有稳定身份；创建新 run 时通过数据库约束或事务校验 action_id、执行代次、目标版本和角色。例：对同一任务版本和同一产物的同一验收动作，不因两条“worker 完成”事件而创建两个验收 run。

任务创建与任务要求更新也需绑定已持久登记的意图／计划提交，不能只保护 run 启动。恢复后先读取原消息已提交的动作；同一来源消息的同一规划提交具有唯一身份。重新推理确实改变计划时显式创建计划修订，而不是借新的 tool_call_id 再做一次旧提交。

用户明确要求“重新跑一次”、获准修复后重新验证，或改变目标版本时，创建新的动作代次。这是新业务行为，不应该被误去重。

### 8.7 request ID 不等于 exactly-once

数据库写入可以与去重记录在同一事务提交，但远程进程启动、给 harness 发消息等外部副作用不能假定与本地事务原子化。

例如 worker 已启动，网络在回执前断开：只有下游自身支持幂等启动，或能根据稳定身份对账证明结果，才可安全自动恢复。否则保留 unknown；不能看到“本地没有成功回执”就重发启动。缺失响应造成的这种不确定性也是幂等设计需要专门处理的情况。[S4]

## 9. 事务、事件与恢复

### 9.1 事务发件箱与接收去重

一次控制变更在同一事务内写入请求记录、任务／动作变化及待发送消息。事务提交后，dispatcher 才向外部发送。每个出站消息预先保存稳定 child request ID。

接收方保存 inbox 去重记录，再将事件作用于任务投影并创建后续动作。事件应用与触发下一阶段必须在同一事务范围内，避免“状态已更新，但后续动作丢失”。

初版不必依赖独立消息队列；数据库中的待发送表与事件表可以承担此职责。传输允许重试，业务状态更新必须有稳定身份与版本校验。

### 9.2 外部回执与观测

启动、停止、消息投递均区分：请求已接收、动作已发出、后端已接受、观测到执行结果。UI 不得把第一个状态显示成最后一个。

适配器尽量使用后端原生稳定 run / turn / item 标识。没有可靠事件身份时，使用已知 native item 的快照对账；不要给每次重复通知生成新 event_id 然后宣称完成了端到端去重。

流式文本按 message_id / item_id / chunk sequence 更新，重连时优先恢复消息快照，再接增量。没有可靠的增量序号就不盲目拼接，否则容易重复输出同一段文本。

### 9.3 断线与重启

后端启动时先恢复未完成 RequestRecord、PlanAction 与 Run，再向各适配器对账。已确认提交的动作不重建新身份；已确认未执行的可以按原逻辑请求继续；不确定的进入 unknown。

心跳过期或控制租约过期仅表示失去可确认的控制权，不证明旧进程停止。不得直接释放仍可能被写入的工作区，再把它交给另一个实现者。

若使用控制 epoch / fencing token，必须由真正执行动作的接收方校验才有效。不能只在数据库里提升数字，就认为旧 worker 已被阻止继续写文件。

### 9.4 迟到结果

事件即使属于旧版本也保存为事实，但只有匹配当前 action、spec_version、产物和控制 epoch 的结果，才能触发后续动作。旧验收通过不能关闭已变更要求的任务；已取消计划的旧 worker 返回产物，也不能重新激活发布流程。

### 9.5 Hook 不是事件总线

任务承诺、完成回执与审批状态不能只依赖一次 hook stdout。控制层有独立持久状态，后台进度由执行适配器采集。Hook 失败不能让数据库里的义务消失，hook 重试也不能重复派生动作。

## 10. 调度与跨机器执行

主 Agent 负责理解“今天先做什么”等意图，将其转成优先级、约束和依赖；普通调度器负责实际排队和资源选择。

调度至少检查目标操作系统、所需工具或设备、仓库与工作区可用性、CPU／构建等 slot、模型／账户可用性、依赖、授权和人工控制状态。机器并行能力与模型配额分开建模。

初版使用静态资源配置加实时在线状态即可，不做复杂的自动性能建模。工作区优先一任务一隔离副本或 worktree；同一可写目录只授予一个实现控制者。跨分支集成视为明确的后续任务，不因为能并行就自动认为结果可无冲突合并。

优先级更新影响尚未启动的工作；已运行阶段正常完成或等待用户明确中断。不支持迁移意味着节点暂时离线时允许等待，而不是偷偷在另一节点重启同样工作。

程序心跳与状态轮询不消耗模型 token。普通完成与依赖满足按已授权动作推进；只有范围变化、失败取舍或跨任务冲突需要模型判断时才唤醒后台推理。

## 11. 实现、独立验收与修复闭环

每个任务在启动前具备可检查的 TaskSpec。实现 Agent 提交不可变产物引用和执行证据，不能直接宣告任务验收通过。

独立验收必须使用独立 run 和独立上下文，获得 TaskSpec、待验收产物、必要环境与证据。可以与实现者使用相同模型，但不能在实现 session 里让同一个上下文“自评通过”。不将实现者的成功自述当作验收依据。

验收者默认不能修改被验收产物。需要运行测试时使用隔离工作副本，允许测试生成临时输出；若修复了源代码，则形成新产物并重新验收，不能把“边修边审”算作原产物已通过。

判定分为 passed、changes_required、blocked、inconclusive。环境缺失、权限不足或无法完成测试不等于代码有缺陷，也不等于验收通过。

Acceptance 与确定的 spec_version、artifact_id 和验收身份绑定。验收角色凭据由服务发放并限定作用域；提交者自报 evaluator_run_id 不构成授权。主 Agent 可以安排验收与修复，不能通过修改字段伪造独立通过。

修复循环有预算与次数边界。范围未变且在授权内可以自动继续；连续相同失败、需要降低标准、超预算或存在关键争议时形成待决事项。用户明确修改验收条件生成新 TaskSpec，仍需按新条件验收，不能覆写历史结论。

## 12. Harness 与执行后端适配

### 12.1 HarnessAdapter

这是“怎样驱动主 Agent”的接口，而不是机器调度接口。建议能力包括启动／恢复 thread、开始 turn、订阅输出、响应原生审批、查询状态、安装与验证 hook、请求中断，以及记录应用 request 与 native ID 的映射。

Codex 当前 app-server 文档提供 thread／turn 与事件接口，默认 stdio 传输；生成协议 schema 可对应实际二进制版本。[S2] 初版优先 Linux 服务通过本机 stdio 驱动，并固定已验证版本。不要因为名称相同就假设 traex 全面兼容。

一个用户可见主对话不等于一个覆盖全部后台工作的原生 thread。前台 thread 保持对话连续；需要推理的后台事件使用任务范围 thread。后台结果进入统一聊天时标明任务归属，完整内部执行过程不默认灌入前台。

harness 内部历史和自动压缩仍由 harness 管理。本系统使用 hook、工具及可恢复快照，不直接编辑其私有会话文件。注入是新增上下文，不是删除旧历史，也不保证固定的每轮总输入成本。

### 12.2 ExecutionAdapter

这是“怎样在某台机器推进实际工作”的接口。规范化能力建议为 capabilities、start、send、inspect、read_artifact、interrupt、reconcile 和事件订阅／轮询。

每项控制请求都使用统一应用信封。start 接收不可变要求引用、action_id、角色、目标机器与授权，不强制接收主模型生成的长篇改写需求。send 引用原始用户消息及必要的已解析指代。

能力声明至少说明启动幂等、结果对账、原生消息身份、明确停止、人工输入观测、离线存活和角色隔离。某项能力缺失时显式降级；不能用终端文本猜测替代已有结构化协议，或把猜测结果声明为确定事实。

允许第一版仅一个真实后端加一个测试适配器闭环。不要求同时完成 Orca 和自研工具全部适配，但核心逻辑与数据模型不得依赖首个后端的专有对象。

### 12.3 Orca 的位置

Orca 只作为可选执行后端及可选看板展示入口。Task Source 插件方向用于展示本系统任务，不作为自主调度或权威账本的前提。

上一轮讨论核查的材料包括 PR #26282、PR #22174 和 issue #8376；这些是适配研究线索，不是已安装或已验证能力。实现时重新检查所用版本和接口，不把本设计的可靠性建立在某个未合并 PR 上。[S5]

停掉 Orca 适配器，TaskSpec、待决问题和未完成承诺应仍然完整；只是相关执行暂不可用。自研工具也必须满足同样替换边界。

## 13. 人工介入与一次性导入

### 13.1 人工接管

明确的人类控制输入使对应 run 进入 human_control，暂停自动发消息、自动修复重试和后续动作。保留状态观察，普通打开详情或读取日志不触发接管。

同一时刻只能有一个有效控制者；接管与恢复通过版本校验提交。已经发送或正在执行的工具调用可能无法瞬时撤回，界面必须显示真实观测，不承诺立即静止。

恢复托管时读取当前产物、执行状态和用户补充，确认与目标是否一致后创建或恢复后续动作。没有批准的旧方案不能因“继续”而重新生效。

对于无法观测外部人工输入的后端，只能支持显式接管入口或降级托管；不承诺检测用户在系统外任意终端、编辑器中的所有行为。

### 13.2 一次性扫描导入

导入产生带扫描时间、来源与可信度说明的工作快照，包括目标、已知约束、观察到的进度、已有产物及原 session 引用。不持续拉取旧系统变化，不将导入状态冒充实时观测。

从快照继续时，建议创建本系统的新执行尝试。写入前验证工作目录、产物版本及旧执行是否仍可能写入；不因提供了一次性导入就隐式接管旧进程。

扫描与确认导入分别携带 request ID，重试不产生重复任务。用户明确再扫描是新快照，可以比较或更新导入候选，但不是开启同步。

## 14. 远程客户端与 API

### 14.1 Web MVP

三个主要区域：中心聊天、全局任务看板、待决事项。任务详情显示目标与约束、当前状态、下一动作、执行位置、产物和独立验收结果。需要时可展开执行日志，但不要求先找到 session 才能继续工作。

初版不需要通用看板自定义系统、完整终端交互网格或 IDE。Electron 后续复用同一 Web 与协议，仅增添桌面通知、窗口或本地链接等必要能力，不承担核心调度。

### 14.2 消息发送与重连

浏览器在首次发送前生成并持久保存 request ID，例如与待发送草稿放在本地发件箱。请求超时后的“重试发送”沿用同一 ID；用户编辑后重新提交是新请求。取消此前请求通过独立 cancel 操作表达，不能只删本地气泡。

服务端持久接收后返回稳定 message_id / operation_id。界面区分“已收下”“正在处理”“已投递”“执行状态未知”。发送重试不会创建第二条消息或第二次派发。

后端向 Web 使用鉴权 HTTP API 与 SSE / WebSocket 事件通道之一。初版可选 HTTP + SSE；读取使用新 request ID，事件流按 event_id 与游标恢复。浏览器能力无法自定义握手字段时，通过受控客户端或预申请订阅身份表达请求 ID，不取消鉴权。

刷新、换设备和短暂断网只恢复同一任务快照与消息历史，不重新提交历史指令。快照必须带一致的事件游标；客户端从该游标继续，避免快照与增量之间漏事件。

### 14.3 建议的应用接口

| 操作 | 作用 |
| --- | --- |
| conversation.submit_message | 接受原始消息与可见上下文，进入前台推理队列。 |
| tasks.list / tasks.read | 紧凑索引与按需详情。 |
| tasks.update_intent | 带控制版本更新目标、优先级或约束。 |
| actions.create / actions.read | 创建并跟进条件式工作承诺。 |
| executions.start / send / inspect / interrupt | 规范化执行控制。 |
| approvals.respond / decisions.respond | 对确定问题及版本提交回答。 |
| artifacts.read / acceptance.submit | 读取证据；验收身份提交针对确定产物的结论。 |
| control.takeover / control.resume | 显式控制权交接。 |
| imports.scan / imports.commit | 可选的一次性扫描与导入。 |
| requests.read | 查询不确定请求的状态，而不是重复执行。 |
| context.prepare / context.delivery | 构建并跟踪 hook packet；delivery 不宣称模型已理解。 |

名称仅表达领域操作，具体 REST / MCP / RPC 路径可调整。所有客户端与模型工具调用进入同一服务规则，不建设两套互相漂移的权限或状态转换逻辑。

## 15. 权限与部署安全

远程入口必须有鉴权与加密访问，可由可信反向代理或私网接入层提供。具体部署渠道不绑死；浏览器到服务和服务到执行机器分别授权。request ID 是关联标识，不是访问凭据。

主 Agent、实现者、验收者和人工用户具备不同权限。主 Agent 能安排工作但不能自行验收；实现者只能对分配范围提交产物；验收者只能对授权对象提交结论。跨仓库、跨机器、公开发布和敏感凭据使用按策略审批。

应用数据库与根凭据不能直接暴露给拥有普通 shell 权限的主 Agent 或 worker。使用独立运行身份、受控文件目录、短期作用域凭据与必要网络限制，使程序侧校验不能被“直接改数据库”绕过。

只把应用入口暴露给远程客户端，不直接暴露 harness 控制端口。协议透传功能不得绕过应用授权。[S2]

审批记录在服务器持久化，并绑定目标动作、参数摘要、任务版本和控制代次。旧审批不得授权新命令；撤回授权后，尚未开始的动作重新校验。无法撤销的已执行副作用保存为事实，并明确显示，不伪装回滚。

## 16. 成本与复杂度控制

允许主 Agent 对每条用户输入做一次必要理解，不以用户手工选任务交换 token 节省。主要优化点是原文／产物引用、紧凑 hook 快照、按需详情和程序化事件推进。

Hook 不额外调用 LLM 来决定注入内容；非语义事实与待执行条件通过数据库查询获得。普通轮询、看板渲染、客户端重连和状态合并不唤醒主模型。

长原始需求若主 Agent 已经阅读，其输入成本确实存在；传引用只避免不必要的重新生成，并不能取消已经发生的模型输入。worker 获取完成任务所必需的完整要求，不因为省 token 而只收到失真的摘要。

预算与防循环仍然需要最低限度的资源记账，例如每个任务可重试次数、可创建 run 数量、并发 slot 与授权支出范围。它们属于执行控制，不是用户行为分析。不能准确获得上游消耗时标记未知，并采用更保守的启动上限。

## 17. 初版实施顺序与正确性测试

### 17.1 实施顺序

| 阶段 | 交付边界 |
| --- | --- |
| A. Harness 与身份验证 | 用实际 Codex / traex 版本确认 hook 注入、compact 恢复、原生 ID 映射、流式读取和异常行为。 |
| B. 持久控制骨架 | 任务、请求去重、动作、outbox / inbox、版本校验、事件恢复；先用测试执行后端验证。 |
| C. 最小真实闭环 | Web 发消息 → 主 Agent 关联任务 → 一个实际 worker → 独立验收 → 自动推进或待决。 |
| D. Remote 可用性 | 断线与服务器重启对账、审批恢复、人工接管、额外执行机器适配。 |
| E. 可选增强 | 一次性导入、Orca Tasks 展示插件、Electron 外壳；不阻塞前述闭环。 |

不以完备监控平台、复杂 UI 或所有后端同时支持作为起步条件。

### 17.2 必须覆盖的故障场景

| 场景 | 应有结果 |
| --- | --- |
| 浏览器提交后未收到回执，重试相同 ID | 一个消息、一个逻辑操作，不重复启动。 |
| 两个并发请求使用相同 ID、相同参数 | 只有一个接收方执行者，另一个得到原操作句柄。 |
| 相同 ID 携带不同参数 | 拒绝冲突，不覆盖原意图。 |
| 同一父请求派生多个子动作 | 子动作不同 ID；每个子动作的重试保留其原 ID。 |
| 主 Agent 恢复后用新 tool ID 重复启动同一阶段 | action/effect 约束阻止额外 run。 |
| 外部动作已执行但回执丢失 | 对账；无法证明时 unknown，不盲目重复。 |
| DB 提交后、outbox 发送前重启 | 恢复发送同一动作，不丢承诺、不换身份。 |
| Hook 重试或返回顺序变化 | 不跨 thread 串上下文；packet 可追溯；无证据时不错误推进 delta 基线。 |
| compact 发生在 turn 中途 | 后续推理得到恢复快照，要求与待决事项不只存在于旧摘要。 |
| 后台结果穿插“第二个方案”对话 | 指代关联仍正确，系统通知不覆盖讨论焦点。 |
| 任务要求改变后旧验收通过 | 保存证据但不关闭新版本任务。 |
| 人工接管时自动动作恰好排队 | 服务端版本／控制权校验使未获当前授权的动作不再执行。 |
| 机器心跳丢失但进程仍在运行 | 标记不可确认，不释放可写资源并创建重复 worker。 |
| 验收环境失败 | 标记验收受阻，不当作实现缺陷或通过。 |
| Hook 不可用或漏触发 | 服务端权限与状态校验仍生效，不靠 hook 唯一保证安全。 |
| 从旧数据库备份恢复 | 对外部状态完成核查前，不直接重放可能已生效的操作。 |

这些是实现正确性测试，不是被排除的“减少 session 查找次数”产品度量功能。

## 18. 实现前需要验证、但不阻塞产品定稿的事项

实际选择的 Codex / traex 二进制、hook 覆盖与接纳语义、MCP 调用身份暴露方式，以及各执行后端的幂等／对账能力，需通过最小原型确认。不能把文档中存在接口等同于目标环境已可用。

数据库、认证接入、服务部署方式、初始注入预算与并发上限可配置，先采用适合现有 Linux 环境的简单实现。不为这些选择重新打开已经确认的产品边界。

第一版应把未知能力显式呈现为“待验证／不支持／需人工对账”，而不是通过主模型猜测或无限重试补齐。
