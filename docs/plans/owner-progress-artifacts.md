# 负责人部署前阶段成果与原件登记

Refs: D219、D222。

## 问题与目标

负责人沿同一 Task 重基、验证和交付时，原 Task 可能已经绑定 deploy=true 的
执行。`submit_result` 目前无条件复用部署报告的升级绑定校验，导致新的检查报告
在尚未启动升级时被要求提供 `upgrade:<id>`；上传文件又只有进入不可变产物后
才能在原 Issue 内发布和给 reviewer 读取。因此正常的部署前检查原件无法共享。
刷新候选后仍会绑定部署执行，不能消除这条依赖。

阶段成果登记不是部署完成，也不创建或结束 Task/Run。修复必须使真实负责人
能在当前有效 Run 登记阶段报告、正式引用其上传原件，并沿已有对象权限共享。
最终部署结算仍须实际匹配的合入、升级、目标范围和安装证据。

## 实施

1. 保持 `issues.update_delivery action=submit_result` 的现有输入和身份、租约、
   文件 manifest 校验。负责人结果没有升级引用时只登记成果，不推断部署批次；
   显式包含升级引用时沿现有严格绑定校验，拒绝空、重复、错误或替换批次。
2. 独立部署 worker 的最终 `SubmitArtifact` 仍必须提供升级报告；不放宽现有
   批次排空和独立验收调度。`complete`、历史结算和 unknown 对账保持原条件。
3. 增加实际链路回归：已绑定部署的 owner 上传、登记、读取和发布阶段原件；
   Task/Run/原授权不变且不能提前 complete。显式无效升级引用失败时事务回滚；
   真实已绑定升级不能被阶段报告改写或用缺失证据结清。
4. 同步 D222、Agent 指令和 CLI 使用说明。现有 owner API、工具、CLI 和生成
   类型可表达完整输入，不增加字段、迁移、协议或额外业务抽象。

## 验证与交付

先复现本次 owner 已绑定部署后的阶段成果拒绝，再运行相关成果、附件权限、
连续交付及部署结算回归与 race。实现收敛后一次独立整 PR 审阅、最终完整
`make check TEST_COUNT=1 CHECK_JOBS=0` 和 exact-head CI；保留所有真实失败和未知。

合入前重基最新 main。部署前重新核对原业务 PR、受控批次、真实进程和配置，
不得与业务交付重叠或重放。统一 format 2 发布集、单个固定身份及截止时间的
受控升级，完成真实进程/配置/正常回执核验后，通过原 Issue 的 Tend chat 交接。
保留原 Task、审阅、授权、上传及失败记录；不直接修业务状态或代替业务升级。
若恢复时已进入后续 Run，仍遵守当前 Run 的真实上传来源约束，不把旧 Run 上传
伪装成当前执行；可从原件重新核对并沿已有按内容去重设施登记当前真实结果。

本次不处理 Agent 分配 backlog、Main 失败创建尝试的收尾标记或其他独立问题。

## CI 中已发现的事件投递回归

本候选的原 CI 在既有 runner 回归中记录工具事件两次、原生 turn 和完成各一次。
正常 runner 的原事件可以被发射方和待投递恢复方并发重投；正式服务按 Run、事件
序号及正文一致性去重，但该测试的 HTTP 替身把每次传输都再次执行业务效果。
原日志没有逐次事件身份，不能据该计数断言原生业务重放或唯一调度原因。

先注入“服务端已应用工具事件但 ACK 丢失”，保留未修替身下的确定性失败；再让
替身沿实际事件身份去重，并拒绝同序号正文漂移。不同序号仍应用、计数，保留
严格的一次工具业务效果、一次原生 turn、一次完成、归档仍待处理，以及永久
事件投递失败必须上报且保留原 journal 的断言。只修测试，不给生产引入额外锁、
重试或放宽次数断言。补充故障回归和相关 race 后，由原独立 reviewer 判断增量，
以实际最终源完成完整本地检查和 CI；旧失败与旧源门槛保持可追溯。
