# 原生命令阶段与负责人回执恢复

## 目标与故障链

业务目标是让原 Issue 负责人消费已经产生的命令结果，继续同 Task 的独立审阅与合入。实际故障从长命令的 `backgrounded` 通知开始：它与后续 `completed` 都使用同一 item 和 `item_completed` 事件类型。rollout 当前把该键解释为单一不可变终态，因此拒绝真实完成结果；旧事件未 ACK，回执恢复反复创建新的协调 Run，原负责人无法继续。

## 实施范围

1. 先新增回归，在未修改生产实现上证明命令 `backgrounded` → `completed` 被误拒绝；同时保持普通消息和真实终态变更的冲突检查。
2. 在原生 rollout 登记中区分命令运行阶段与终态。保留每份原件，按相同执行身份验证阶段转换，重复通知幂等；不重跑命令、不覆盖历史，不把 `exitCode=0` 单独当成终态。
3. 复用现有 attachment 启动重试预算和 Attention：明确区分新输入启动失败与该原输入的回执恢复失败。只有真实失败的回执恢复受自己的退避/耗尽约束；新输入失败不阻止旧输入读取。旧状态可以在一次真实失败后归入正确责任，不新造业务输入。
4. 调度入口与 attachment 入口共同尊重该回执恢复预算，避免一个入口停止而另一个持续创建 Run。保留未知请求和旧未处理事件；正式处理原 Attention 后可以继续同 Task。
5. 以原业务路径验证：后台通知登记、真实命令完成登记、旧事件 ACK、失败恢复停车及正式恢复；覆盖重启、重复通知、不同执行身份/终态的拒绝和无新模型业务 turn。
6. 回执 attachment 的退避期限必须进入后台唤醒计算，涵盖原生 turn 和没有 main turn 的未决手动 compact；按原操作身份及会话匹配，完成后不再为旧期限安排唤醒。

## 验证与交付

- 保留原 RED 与修正后的定向 race 原件，检查受影响包及跨组件实际恢复。
- 必须独立 CLI 审阅；最终候选的必要本地检查、CI、当前 main 适用性和保护规则分别核对后才能合入。
- 生产当前故障与本地修复分别报告；保留原 Task/Run/事件/unknown，不覆盖原始接收事实、不重复 PR/标签操作。
- 本轮业务主线的 merge-only 范围不因修复计划变为部署授权。确需安装平台修复时，先准备具体候选、验证与受控恢复步骤，再明确该动作的授权边界。

## 边界

不修改 Agent 配置、并发/租约规则、原业务目标、PR 标签需求或独立性要求；不通过延长超时、关闭 race、覆盖原件或强行标成功解除阻塞。不新增通用请求账本或永久检查账本。
