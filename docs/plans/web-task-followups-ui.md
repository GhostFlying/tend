# 已完成任务的跟进入口与关系 UI

在任务阶段看板和完成通知基础上扩展任务定义的 follow_up / related 关系。关系协议、追加迁移、存储、API 和工具由后端实现；本子任务等待生成类型契约，前端不自行定义或手改 generated 类型，不直接调用任务创建操作。

## 交互

- 已完成任务详情在本版交付附近显示“跟进 / 修改”入口。点击后关闭详情、回到主聊天，并将原任务标题、有效 task ID 和“需要补充或修改的内容”提示放入输入框；焦点进入输入框。
- owner 补充具体意向后手动发送，走现有可恢复 outbox；入口本身不发送消息、不创建任务、不修改已完成任务状态，也不自动触发模型。已有草稿保留，新意向作为独立段落补入；重复点击同一意向不重复追加。
- 原任务完成事实保持可见；后续任务通过持久化 follow_up 关系体现，不把原任务重新标为运行中。实际关系建立由主 Agent 使用已冻结的任务定义/关系工具完成。
- 详情展示当前任务的双向关系，区分跟进来源、后续任务和相关任务，按后端返回的 kind 与方向解释，不从标题、项目或聊天正文猜测关系。每个关联项可跳转到对应任务，保留完成任务的交付优先布局和返回看板/聊天路径。
- 切换关联任务时取消旧读取，旧响应不得覆盖新详情；后端事件和重连刷新关系。链接使用真实任务身份，历史/完成任务不依赖活动 snapshot 才能访问。

## 接点与验证

1. Shell / Services 增加显式的“打开聊天并填入意向”入口；Composer 保留现有草稿、发送、停止、离线恢复和模型设置行为。
2. 使用后端生成的 TaskDetail 关系字段渲染任务定义关系；字段、方向及事件身份等待契约确认后编码。
3. 补充草稿拼接/重复点击和关系方向的有意义回归；生产构建浏览器核对桌面/390/320、明暗主题、现有草稿保留、无自动 POST、手动发送、双向跳转和迟到响应隔离。Browser plugin not available，沿用 Playwright，不增加依赖，不使用 orca。
4. make check 与 diff 检查通过后独立提交，不推送；临时服务与浏览器 finally 清理。后端和独立 review/PR/部署由主任务负责。

协议冻结后采用生成的 relations/kind/direction 与 current_artifact_id。任务卡元信息显示 spec 版本，避免将 next_implement_generation 误称为当前代次。
