# 持续可靠性：数据库读路径、回执诊断与终态投影

## 目标与边界

R1 在现有事务快照内完成初始负责人候选、handoff 屏障和待回执批查，并让具体 Agent 不匹配的空领取只读返回。最终 Claim 写事务仍重新校验权限、库存、资源和业务版本；不跨请求保存授权事实。

R2 对去重后的完整正常场景采样，按真实剩余成本决定固定 SQL 的 prepare 生命周期是否值得采用。局部微基准不替代完整场景收益。

R3 将连接等待、事务启动、回调、提交与客户端取消/真实期限分别记录；保留原事件与 ACK 身份，通过正常收据路径证明收敛，不把所有历史取消解释为 ACK 丢失。

R15 根据当前 Issue 终态和责任投影有效状态，将旧摘要及已过适用期的信息提示明确标记为历史；保留原始工作状态、摘要、Attention 和真正未解/unknown 阻塞，不重新打开已完成业务。

## 实施顺序

1. 对比固定基线与既有私有分支，复用尚未合入的窄改动并保留已合入语义。
2. 增加快照与真实 writer 占用回归、批查身份/epoch 隔离测试；先完成 R1。
3. 以固定资源顺序执行基线和候选完整正常场景，保留原生 JSON、profile、源码身份与失败；据此完成 R2 取舍。
4. 核对现有写诊断和回执取消因果链，补足分类及正常回执状态转换测试。
5. 增加只读适用性字段和 Web 展示，验证完成、取消、重新打开、历史 revision、当前 unknown 与责任迁移。

## 业务契约与验证

实际故障起点是重复候选读取占用 SQLite writer 及旧展示覆盖当前终态；目标终点是原 Claim/回执正常完成与用户看到当前状态。快照优化只改变查询组织；当前责任、原事件/收据身份和终态不变。回执失败时可继续读取原状态并沿原身份恢复，未知外部操作不重放。

定向 race 覆盖 views、claim preflight 和窄 store 诊断，完整业务场景采用既有 sandbox 测试及有限 watchdog，不修改业务断言。独立审阅、全量检查、CI、合入及部署由统一集成者执行。共享设计说明和生成 schema 由集成者同步，交接单列 API delta 与设计段落。

## 本轮受控观测与采用决定

在当前固定基线 `ee04f3f9` 与去重后的候选之间，各执行一次原有完整正常 sandbox 场景。两者使用相同 Go 版本、race、两个固定 CPU、GOMAXPROCS=2 和原阶段 watchdog；共享主机存在同期负载，不作全机独占或统计显著性声明。单例 288.38 → 270.43 秒，真实业务阶段 236.17 → 217.12 秒，CPU 样本总量 501.90 → 459.98 秒。历史更老基线的改善比例不作为本轮结果。

候选的批量 handoff 查询整条调用树为 8.33 CPU 秒，占完整场景 1.81%；这已经是完全消除该调用成本的收益上限，实际 prepare 复用收益更小。因此本轮保留固定 SQL 生命周期微基准，不增加双连接池拥有的 prepared statement 机制，也不引入跨事务结果或调度权限缓存。全局 SQL parser 仍占候选 CPU 样本 46.27%，涉及其他启动与后台路径，是后续调查事实，不将其宣称为本轮已解决。

慢写观察 303 → 233 条；`RecordRunEvents` 在连接等待阶段的取消仍为 7 → 7。这些是任意 Run 事实持久化的取消观察，不能等同于丢失 manager ACK。新诊断保留原错误和失败时 context 状态；原事件收据的真实排队期限失败、同身份正常 ACK 收敛和重复 ACK 不重复副作用由独立回归覆盖。并发等待累计与 inclusive callback 时间不相加为墙钟耗时，慢写阈值样本也不作为全部事务计数。

Refs: D248。

### R3 诊断身份补全

原场景取消记录缺少 Run/事件序号，不能逐条关联之后的补交。`RecordRunEvents` 在验证原调用身份和批次后，注入固定 `runner.events`、原 Run 与实际首事件序号；空批次明确使用零，不沿用外层事件序号。HTTP 入口同时携带已验证信封的 request/trace，直接内部调用保留既有外层诊断身份。仅记录有限标识，不复制事件正文或凭据，不增业务缓存或重试。已保存的七次旧观察仍保留 unknown；不为这一诊断补正重跑性能配对。
