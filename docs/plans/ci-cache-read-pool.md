# CI 读连接复用、滚动缓存与浏览器分组

Refs: D147、D148；延续 D145。

## 依据与验收

现有完整 CI 的两个样本分别为 11 分 06 秒和 13 分 23 秒，关键路径在 Web 与其他 Go 包之间切换。sandbox 完整 race profile 中迁移只占约 2.4% CPU，读连接初始化约占 22%；同一最慢场景的原配置两次约 171 秒，保留 16 个空闲读连接的临时实验约 110 秒，累计 CPU 采样由 610 秒降至 262 秒。当前 Go 缓存按依赖文件生成固定 key，命中后不保存新增构建及测试结果。13 项浏览器回归串行约 509 秒，可平衡为约 260/249 秒两组。

验收保留全部静态检查、race 测试根、13 项浏览器回归及真实 Web 产物的交叉编译。完整 CI 以 8–10 分钟为待验证目标；Go 缓存有效命中的 Web 修改以 6–7 分钟为待验证目标。冷缓存首次运行、单轮主机波动和累计 runner 占用分别报告，不把局部样本当作整轮承诺。

## 实施顺序

1. 对比 4/8/16 个空闲读连接的同一真实 sandbox 场景，记录耗时、CPU、内存和连接统计，选择有收益的较小保留数。仅调整读池空闲连接保留，不改变写池单连接、最大读并发、事务或迁移语义。补充并发读连接复用、快照一致性、query_only 和关闭释放的有效回归。
2. Go 模块下载缓存单独共享；构建/测试缓存按职责与工具链/依赖分区，按候选 key 保存快照并回退到同职责最近快照。测试命令继续执行，由 Go 原生缓存检查源码、参数和外部输入。仅可信 main push/手动运行发布构建缓存；PR 恢复 main 快照，避免每个 PR 复制大缓存。保存及恢复体积可观测，维护任务仅清理本方案自有 main key，保留每职责一个快照及最近两个模块缓存；其余历史缓存不主动删除。
3. Web 检查构建一次，发布当前运行的构建 artifact；两个浏览器 job 下载同一产物，保留各脚本的临时目录、缓存与端口隔离。通过显式测试清单完备且互斥地覆盖原有 13 项检查。交叉编译仍包含该真实产物，并行于浏览器回归。最终同名 check 要求每个依赖成功。
4. 增加有界缓存保留策略及其纯函数测试，支持 main 手动 CI 以验证新 checkout 的暖缓存；缓存维护放在门禁之后，不扩大 PR 的 Actions 写权限。
5. 冻结候选后执行一次完整 make check、独立 CLI review、PR CI，并在 main 暖缓存后验证实际命中与资源代价。修改源代码或出现有效缺陷时再做必要复检。

## 边界

读池调整会进入后续服务端发布，CI 流程合入即可对新运行生效；本任务不部署业务服务。缓存命中不跳过测试命令，不跨分支提升 PR 缓存，不改变协议、业务状态或重试规则。内存、文件描述符、清理保留范围和失败汇总作为评审要点。

## 本地实现验证

同一真实 sandbox 场景的 4/8/16 个空闲连接样本依次约为 115.5/108.9/99.2 秒，关闭的超额空闲连接分别为 187/1/0。选择 8：已消除绝大多数反复初始化，16 的单轮更快结果尚不能排除运行波动。该场景的 race 进程峰值常驻内存约 300 MiB；编译进程的累计资源统计不能用于比较读池内存开销，本轮不据此宣称生产内存收益。新并发回归验证两轮读突发中连接保留、独立快照、拒绝写入以及关闭释放。

Go 原生缓存仍会因测试读取的 checkout 文件时间戳、环境或嵌入构建变化失效，不能保证暖缓存全量复用。首次新 key 冷运行和 main 快照发布后的暖运行分别验收；检查全集没有削减。
