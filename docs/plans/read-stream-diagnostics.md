# 慢读与 Web 事件流诊断

生产读池已经观察到 8 个 reader 全忙及累计等待，成功的慢 GET 缺少请求级耗时。浏览器黄点已有断流观察，服务端主动重置游标时缺少同次连接的关联标识。沿现有 HTTP 请求跟踪器、读事务和黄点接入诊断。

- Owner API 经通用读事务入口的 GET（含 Chat 历史和快照），在服务端用同一个 trace 贯穿响应头和诊断日志。用单调时间记录 HTTP 状态和总耗时、获取 reader 与开始事务的合并耗时、事务回调内的查询/投影耗时、释放事务耗时、JSON 编码与响应写出合并耗时。底层 ResponseWriter 的写调用耗时是响应阶段的子集。响应写完只表示服务端写调用完成。
- 仅记录超过 1 秒的读取、请求 context 取消/截止或响应写失败。使用现有池和写诊断对照相邻时窗。各进程按慢读、异常读、事件流预期结束、事件流数据库读失败和其他非预期结束独立限量，每类每 10 秒最多 10 条。一个事件流尝试只在结束时提交一条摘要。
- SSE 在已认证的 GET 响应返回同一个服务端 trace，覆盖流内 reset 与头部提交前的 HTTP 拒绝。记录请求游标、初始服务端水位、最后成功 flush 的流位置、reset 水位、首帧时间、连接持续时间、最近 flush 与心跳、HTTP 状态及结束原因。只记录已观察到的事实，context 取消和 flush 失败不推断客户端为何关闭。心跳和事件本身不逐条记录。
- 浏览器沿现有 fetch、自动重连及黄点展示上一次中断的 trace。heartbeat 超时由浏览器定时器判断。收到头部之前关闭、或服务端没有返回关联头时，黄点标明服务端诊断 ID 未确认。日志投影只用注册路由、服务端生成的 ID、固定枚举、状态及计数，不写原始请求参数、认证材料、事件负载或错误文本。
- 验证真实 HTTP Chat/快照入口在读池竞争下成功缓慢返回及取消。使用真实 SSE handler 产生游标重置，核对同一 trace 的服务端日志和浏览器黄点，并验证正常请求/心跳的日志边界。运行受影响本地检查并提交 PR 供独立审阅。

## 诊断读法

- 在浏览器 Network 选中慢 GET，复制响应头 `X-Tend-Trace-ID`。用同一 `trace_id` 查找 `HTTP read observed`。`reader_begin_ms` 同时包含池等待与开始事务，`query_projection_ms` 包含事务回调里的查询与投影，`reader_release_ms` 只覆盖回滚释放调用。事务未开始时省略查询和释放。读结果以 `http_status`、`context_result` 与 `write_failed` 一起解读。客户端在收到响应前取消时可用时间与注册路由查找候选，服务端状态可能是尝试写回的状态。现有慢写日志中的 reader 和 writer 池指标可用于比对该时窗，池等待累计值包含同窗其他请求。
- 从黄点或该次 SSE 响应头取 trace，查找 `HTTP event stream ended`。HTTP 409 的 `cursor_expired` 表示开流前拒绝，HTTP 200 带 `reset_watermark` 表示开流后决定重置，`reset_write_failed` 说明服务端写出 reset 时遇到错误。服务端 `read_failed` 表示流内读取出错，即使状态仍是 200。
- 黄点的「事件流心跳超时」表示浏览器在静默窗口内未收到任何流数据。用同一 trace 核对最近成功 flush 和心跳的年龄，以及是否发生写失败或取消。服务端 flush 成功只能证明该次写调用未报错。浏览器只观察到关闭或响应前失败时，后续归因需要同一 trace 的服务端证据；没有 ID 或触发限量时可以保留未确认结论。

## 独立审阅后的修正

游标拒绝可耗尽异常流结束配额，导致已开流的 SQLite 读失败丢失诊断。沿用同一固定窗口限量器，把事件流数据库读失败计入独立类别。以真实 HTTP 409 耗尽配额，再从已收到 start 帧的流触发 SQLite 读失败，验证服务端仍能用原 trace 记录该结束原因。

第二轮复审发现，浏览器收到 HTTP 错误响应头后，等待错误正文仍可能触发静默定时器。超时分支要保留该次 HTTP 错误已经带回的 trace，黄点显示错误响应读取超时。收到响应头前的超时继续保留未确认状态。用实际 ApiClient 和流读取触发这两条边界，并在真实 HTTP 连接上复跑独立反例。
