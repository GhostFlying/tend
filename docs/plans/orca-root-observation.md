# Orca 根会话观测与误接管恢复

Refs: D107, D108

## 问题与边界

升级 runner 不会改变旧验收产物自行编译的代码。嵌套 app-server 的旧启动
逻辑仍可能继承外层 Orca 身份，使首次观测绑定测试子会话，触发错误接管。
本轮不修改冻结验收源码，不放宽真实人工接管、未知结果或资源释放约束。

## 实施

1. **O1**：首次 provider session 仅在新鲜且非空的预期 prompt 观测匹配后
   绑定；接管判断先于身份持久化，失败观测不污染 journal。
2. **O2**：旧验收产物保持冻结；若需重跑其集成测试，从外部清除测试
   子进程环境的全部大小写不敏感 ORCA_ 项，保留外层 TUI 设置。通过
   原启动代码的合成子进程验证继承失败、外部隔离成功；后续实现正式
   吸收 D107。创建者标签不能证明当前执行者，不据此排除 provider
   观测或放松接管判断；读取不到当前归属时保持既有保守对账。
3. **O3**：增加旧代码子进程隔离、首次错误绑定、真实人工输入、旧 app-server
   会话恢复为 TUI、旧 handback 回执重放和工具桥重建的回归验证。保留脱敏身份证据，
   不记录 prompt、hook 凭据或原生 transcript 路径。
   handback 指令只声明恢复托管，不虚构 owner 已在终端操作的事实，
   并要求保留已完成检查，避免仅为补交结果重复执行。
4. **O4**：通过完整门禁、独立 review 和 PR 线性合入，使用不可变产物
   受控升级。部署、主机开放领取和业务恢复分别核对。
5. **O5**：两个原验收 run 先核对真实外层身份，再正式 handback，恢复
   工具桥并由原验收者提交已有发现。后续实现吸收 D107；旧产物若需重跑
   真实测试，通过外部清理环境启动，不更改冻结对象。保持原 run 和证据。

## 验收与兼容

- 不匹配的首次观测不会成为持久根身份；真实 TUI 输入保留接管保护。
- 真正的 owner 输入、不同 TUI 会话、未知来源仍保持接管保护。
- 不通过不可证明的创建者标签推断当前控制者，不泄漏 prompt 或凭据。
- 不改变 server/runner 通信字段、默认协议语义或存储 schema；仅修复
  本机 provider 观测关联与环境隔离的运行行为。
- 原验收结论只有经 submit_verdict 入账后才算恢复完成。
