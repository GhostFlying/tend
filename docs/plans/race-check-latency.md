# 缩短本地检查和 Actions 的 race 测试耗时

沿用 [影响选择](affected-validation.md) 和 [长尾优化](race-tail-latency.md)。

## 迁移准备与 App 热点

- 记录当前候选的 Store 迁移和 App 热点逐例结果。用 CPU profile 区分测试准备与被验证动作，保持同一 Go 版本、CPU 预算和 `-race`。
- Store 的交付观察历史用例复用真实迁移生成的 schema 104 空库。每个用例使用关闭后的独立副本，并继续播种各自的旧数据、执行真实的 104 → 105 迁移和全部断言。空库全迁移、启动和重开测试保留原路径。
- App 只改有实测依据的重复准备。必须保留每个用例的真实业务动作、隔离状态、失败与恢复断言。用量规模用例继续使用能跨越实际分区上限的输入和原写入路径。

## 分组与资源预算

- 在共享计划中将 Store 从 `other` 分出。本地和 Actions 使用同一包分组，调整工作流缓存保留及分组回归，确保所有包仍恰好归属一组。
- 本地在既有 CPU 预算和 E2E 隔离条件下优先排重组。用同一 App 工作量比较 4 CPU 下单片和双片。以实际对照决定是否调整自动预算，保留显式覆盖的含义。
- Actions 比较同一 App 测试源码、同一四片计划在一台 runner 和两台 runner 上的效果。记录作业准备、执行、总作业分钟和 required `check` 墙钟。分片计划动态发现所有根，分派必须完整、互斥，并保留 Go 原生逐例报告和严格聚合。根据对照决定是否启用额外 runner。

## 验证

先对照同一工作量的独立准备与总耗时，再记录本地 `make check` 和 PR Actions。性能样本显式使用 `TEST_COUNT=1`。日常入口保留 Go 原生缓存。保留各次原始失败、取消、测试覆盖和进程预算，区分受控对照、离线估算和整轮门禁结果。
