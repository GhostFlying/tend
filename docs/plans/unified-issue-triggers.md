# Server 统一触发与 Issue 诊断（D137）

## 目标与已确认边界

服务端统一安排到期检查、记录外部事件并向既有 Issue 分发；runner 仅领取观察工作、查询并上报。保留现有负责人、assignment epoch、账本、完成条件、租约和 unknown 对账。现有 Issue CLI 是完整产品入口，本次扩展而非另建专用对象。

已确认诊断设计包含全局调度列表、事件列表及详情时间线、Issue 内过滤视图和手机全屏详情。页面只读；管理操作由完整 CLI 和 owner API 提供。沿用当前主线的路由及组件系统，保留白底、灰色分隔、蓝色强调与可阅读详情。

本期包括 at/every/condition、五字段 cron、交付观察和通用入站 webhook。不包括自动创建 Issue、多目标路由、出站 webhook、公网网关部署或生产切换。

## 实施批次

1. T1：cron 纯领域判定及现有跟进引擎集成。必须提供 IANA 时区、期限与次数上限；默认 20 次。夏令时空洞跳过、重复当地时刻仅一次；漏过周期合并一次，unknown 暂停。保留 deadline/Attention 的现有专用规则。
2. T2：统一 server 扫描，并持久记录可领取的交付观察任务。兼容原 runner poll/report 格式及能力、nonce、generation 和维护行为；不占 worker slot。
3. T3：订阅固定绑定一个已有 Issue 的通用 webhook。独立接收监听默认回环，外部反代终结 HTTPS；HMAC、时间窗、稳定 delivery ID；同身份异内容冲突、提交后确认。私有凭据与账本引用分离，支持完整管理和轮换。
4. T4：诊断 API 从规则、观察、触发、事件、来源、批次与投递事实建立关联视图；未记录的历史时间不猜测。稳定游标、筛选、读取水位、SSE 刷新。无变化与未分发原因可查询，不记录空轮询心跳。
5. T5：补齐 schedule/webhook/event/observation/request 命令组及 Issue 别名、摘要输出与现有完整生命周期能力。提供 JSON、原请求 replay、revision/epoch、dry-run、稳定请求身份与恢复，不重写服务端业务规则。
6. T6：按已确认设计实现诊断页、Issue 入口与手机详情，使用生成协议类型。Browser 插件不可用时使用 Playwright，真实沙盒账本用于验收。

## 协议、历史与授权

迁移只追加，旧规则和审计不删除。runner wire 保持协议 2/1：新增内部队列不改变请求必填字段或分配合同。Webhook 只提供外部事实，不选择目标、不扩大授权。暂停订阅的接收记录不补发；Issue 暂停保留待处理，恢复后继续；终态取消未领取工作。未知业务投递不自动重放。

## 验收与交付

覆盖并发/回滚/重启/时钟与 DST、到期与次数、重复与冲突 webhook、签名和私有凭据、Issue 生命周期及权限、观察租约和迟到上报、旧 runner、只读分页与关联追踪、CLI 独立完成管理与诊断、桌面及手机返回与断线恢复。

每批先定向验证；最终 make check、独立 CLI review、PR CI 与交叉编译。按最新 main 建短分支，线性提交；不部署生产。代码、文档和提交不包含机器特定信息。设计稿中的示例状态不作为已支持能力或真实运行证据。
