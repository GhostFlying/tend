# Runner 预热与原子切换接单权

Refs D259。

后继应在前驱继续领取、续约并投递原 Run 的事件、回执和用量时启动。按旧代待处理集合启用候选仍会把新工作整体挡住。候选的完整发布集、受监督进程、旁路和协议窗口依然需要核实。退出和回执结算属于原代的独立退役。

1. 协调器为已选 runner 发布滚动目标。旧主机控制保持 normal。用于 legacy 引导的目标查询和正常自动安装使用同一批次、精确前驱身份和修订。启动授权绑定唯一候选和期限。前驱的运行、待处理集合和维护应答不提供启动权限。旧版助手仍可发原滚动请求；服务端接收已发布的可选证明字段，已开始的批次按原绑定继续。
2. 候选 Hello 与心跳只保存该安装的观测，采用独立 journal 和只允许预热的控制。主机 inventory、扩展激活、清理和领取由接单实例持有。候选健康来自其自己的观测，监督器验证进程并持久写入 commit。服务端事务核验同一候选提交回执后，保存旧代及其私有收尾控制、发布新代和正常接单控制。失败或未确认阶段保留旧主体和接单权，恢复沿原安装标识。
3. 领取和切换共用写事务。切换前已经分配但丢应答的 claim 沿原 journal 取回同一 Run/lease；切换后旧代的未分配 claim 无新权限。主机槽位跨代计算。Run 和工作区绑定沿旧 journal。已预约的工作区删除需受原预约身份约束，避免老构建与后继同时修改同一物理资源；未知保持在该资源上，无关任务仍能继续。保持现行协议窗口和自然退役条件。
4. 验收使用原授权、Runner Hello/heartbeat、监督器 health/commit、真实领取和退役入口。覆盖忙碌的协议 6 前驱、持续旧事件与待处理项、候选失败期间旧代继续接单、预热候选拒领、两种在途 claim、原工作区冲突、后继接单与旧代继续对账及退出、两代协议间隔拒绝。测试区分本地进程或服务端观测夹具与真实业务状态转换。

线上协议继续使用 6–7。上一发布中可选的启动证明字段仍可解码，已开始的旧批次沿原授权处理。候选的观测通过升级记录的可选字段保存。工作区清理只追加 schema 0146，既有预约若能判定唯一 journal 则绑定，否则保留原预约号并等待可能的旧执行器退出。任何不明状态只影响其对应资源。

托管 Linux fixture 使用固定 SHA 校验两份已发布的历史产物。测试包含原协议 6 包直接滚动到目标，以及经已发布协议 7 包接单且协议 6 继续收尾时升级到目标。历史 runner 通过目标包已有的 `runner-handoff` 进入新流程，目标代码的后续滚动通过正常阶段自动提交。用隔离的 LocalAPI 连接控制候选实际启动和首次联系之间的顺序，原接单过程和后续领取均由实际 runner、监督器和服务端执行。

老构建仍可能使用固定路径准备第一次仓库克隆。切换完成后，调度在同一领取事务按原 Run 的冻结 spec 找出正在准备的仓库，只延迟使用相同仓库的后续任务。原准备收到启动回执后，该仓库恢复领取。新进程自己的临时克隆路径独立。监督器读取候选的启动授权和健康时让出状态锁，使旧构建照常读取状态、续约和领取；返回时核对持久状态代次及候选进程身份。

切换以后，原 journal 可读回已提交的 inventory 快照。尚未发布的原请求沿现有 API 返回确定失败，历史 runner 可以结清该请求。只有当前接单实例可以登记新版本。
