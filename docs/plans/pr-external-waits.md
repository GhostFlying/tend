# PR 观测与一次性外部等待

Refs D266。

普通 PR 观测继续写入同一个交付账本，更新界面、候选、发布守卫与正式交付判定。现有通用交付观察与查询开始事件曾在 #393 和 #351 的状态波动里反复调度 Issue Agent。默认保留观察，静默更新。独立用户输入、正式审阅、任务结果和已授权的交付终态沿各自业务入口推进。

1. 追踪 runner 与 server provider 观察接入、交付 fact/CAS、Issue 通知与 context 分类、外部等待回执。以真实事件区分查询、观测和交付业务结算。
2. 扩展现有 `runs_wait_external` 的 `kind=pr`，要求原 Run/Task 有该 Issue 和注册交付权限，记录 provider/repo/number 以及明确的条件。条件支持固定 head 的命名检查终态、冲突出现或消失、显式目标 ref 移动、合并或关闭。来源、应用、运行及 attempt 可消歧。缺失、截断、来源冲突、较早的运行及未确认结论保持待观察。
3. 在已接受的 delivery fact 提交中原子匹配，保存第一次证据及准确头、目标、结果和 URL。已知成立的请求直接返回证据，同一 Run 继续。异步等待沿原物理停止与同 Task 后继流程，在停止前捕获结果且释放后才调度。原责任、闭包、用户提前接续与一次性生成约束沿既有实现。新订阅只有明确 deadline 才以超时唤醒，旧等待保持原约定。
4. 补齐实际 Agent tool 描述、CLI 等待列表及原恢复命令的说明和 schema。验证纯观察静默、正式终态/人工输入继续、不明确的 provider 状态无误唤醒、固定 attempt/候选跨重启、stop 竞态及一条 context 证据。按实际 integration 源、快检、独立审阅和本地影响检查保留验证结果。

验证样本保留 #351 的 17 个纯观察唤醒组及 #393 的 25 个，重放这两批通知关联的
52 与 30 个 provider 快照。候选 commit 和检查名已匿名化。历史数据缺少 app 和
attempt，精确检查结论、GitHub attempt API 及 worker 的失败回执另用测试输入覆盖。
普通终态观测仍可见。只有原合并交付已绑定、授权和独立验收成立、provider 证据匹配
原 head 与实际目标 lineage 时，才为原责任发布一条可结算的合并事实。
