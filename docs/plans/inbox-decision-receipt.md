# Inbox 决定提交回执

从 Inbox 打开原问题，沿现有 `attentions.respond` 写入原问题版本。
提交期间锁定表单。核对原 Attention 和原问题版本的已答复记录之后，
在原决定区域展示实际选择及说明，保留问题、来源与当前执行结果。
待处理列表和导航徽标消费同一权威终态，保留正在查看的详情路由。

1. 读取 Decision 或旧 Choice 的权威答复及其版本。应答后的版本比原问题版本大一，
   用该规则区分同版本答复、问题更新和仅 Attention 展示字段变化。
2. 沿现有本地操作日志核实未知结果，在原请求身份下读取业务对象。
   相同或不同的已记录答复都显示实际记录。开放且原 CAS 已被较新状态阻挡时，
   确认仍可回答后保留输入；缺少落账证据时保留待核实状态。
3. 用已确认业务状态覆盖滞后的详情和列表读取，重查待处理、全部记录、
   导航徽标和关联待办。窄屏验证确认回执的焦点和读屏提示。
4. 通过 Web 测试和桌面及 390 px 浏览器验证正常提交、明确失败、
   回执未知、跨端应答和迟到的刷新，验证写请求只发一次。

### 独立审阅后的修正

- 原问题版本的权威答复经事件刷新到达后，按原请求身份结清本地日志。
- 在窄屏决定详情显示底部导航，验证可见徽标的变化。
- 保留交付批准和结束交付的现有授权语义。将带条件的答复作为仅正文的独立选项，延期说明沿原路径提交。现有审计说明仍走明确的审计参数。
- 两组 CI 暴露了普通事项待核实文案及旧决定投影的兼容回归。恢复现有处理路径，并重跑原场景。

### 兼容性复核

- 由服务端按原决定与交付责任的关联给出交付审批标记。选项同名的普通问题继续接受说明。
- 原详情按原问题是否开放判断有效性。收件人路由继续用于列表和待处理统计，
  owner 从原详情打开时保留已有答复入口。
- 恢复延期交付时保留历史回执文案。原决定关闭后允许从持久的交付答复记录
  识别其来源，当前写入仍只使用活跃责任关联。
