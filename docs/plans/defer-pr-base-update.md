# 将追主干推迟到准备合入

## 起点与范围

GitHub 的 `main` ruleset 要求分支最新、必需 `check` 通过，且只允许 rebase merge。
这些条件在实际合入时生效。仓库 `AGENTS.md` 的合入条款只要求先 rebase 到最新
`main`，没有交代何时追主干。`internal/mainthread` 给 Issue 负责人的实际指引要求
先处理冲突再安排新候选验证，同样没有明确区分仅落后与冲突，也没有定义合入前才追
主干的时点。历史 PR #355 记录了无冲突 rebase 与随后对最终候选的验证。

GitHub 观察器 `internal/reviewwatch` 读取候选、目标、冲突和 CI，服务端保存原始事实并
通知负责人。交付准入重新核对候选和适用授权、共享审阅与检查。仓库中没有由目标分支
前移直接调用 rebase、推送或重跑 CI 的自动化。因此调整仓库约定与实际注入的负责人
指引，沿 D220/D222 现有审阅及交付规则推进。

## 实施与验证

1. 开发、审阅或等待合入授权时，PR 仅落后且无冲突就保留候选和正在运行的验证。
   实际冲突已阻碍审阅或验证时，负责人可以处理冲突并验证变更后的候选。
2. 确认现有授权及其余交付条件允许进入合入阶段，再读最新目标与候选。以提交祖先
   关系判断是否追上 `main`。已经追上且现有检查适用时直接走受保护的 rebase merge。
   落后时才 rebase、推送并验证最终组合，按现行规则处理受影响的审阅证据及候选批准。
3. 合入前再次核对候选和目标。目标在验证或提交合入请求期间前移时，读取新事实并
   重新判断；沿原 strict、必需 CI、候选授权与 rebase-only 规则继续。
4. 测试实际 runner-managed Issue 负责人配置包含上述各分支，使用临时 Git 历史演练
   等待、已追上、落后、阻塞性冲突及检查期间目标再次前移。复用现有交付测试验证候选
   漂移、检查和授权的保护，读取 GitHub ruleset 核对线上配置。新 PR 走原 CI。
