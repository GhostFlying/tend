# 可读的最终报告与可靠发布

状态：实施中。基线为当前主线；沿现有 Issue、交付、通信及审阅模型实施。

## 问题与目标

调查结果已保存并通过独立验收，不代表用户已收到最终结论。真实交付中出现了报告责任登记成功、Issue 关闭成功、最终回复发布失败、异常提醒又被关闭后的权限拒绝的组合。动态虽然存在交付卡片，通用标题、截断摘要、混杂的证据文件和缺少 Markdown 阅读入口仍使报告难以使用。

用户主要阅读验收通过的最终成果。长时间执行后的报告应能脱离原聊天独立阅读：先恢复最初的现象、目标和需要调查的问题，再解释结论、影响、仍未知的部分与建议。验收记录、原始证据和运行身份作为可选的核查材料；不要求用户阅读第二份验收报告来理解成果。

## R1：修复最终发布和异常记录

- 先复现具名负责人在关闭 Issue 后发布原结果与附件的真实路径，查明内部错误，不能只把工具失败改成成功或靠调整调用顺序避开缺陷。
- 已准入且身份仍有效的原会话可完成本项责任的最终沟通、读取与异常记录；关闭不扩展业务执行、其他 Issue、已换负责人的权限或失效租约。权限按具体动作和责任事实判断。
- 结果不确定时保存原请求、失败及未发布事实，不自动重发或复制业务结果。正式发布以成功回执和实际消息身份为证据。
- 针对原结果附件、关闭前后通知、发布失败的异常记录与失效身份增加真实回归；只有可证明的产品缺陷才增加防护。

## R2：以最终成果为主的阅读界面

- 交付卡片优先显示报告的可读内容和简短验收状态；完整验收记录、技术证据、校验信息按需展开。
- 为 Markdown/文本报告复用已有原文件和下载接口提供阅读入口，保留原件下载。不同交付类型正确命名，不把只读调查一律叫实施交付。
- 不根据猜测替换报告内容、不伪造缺失正文、不混用旧候选和当前候选。必要读取按需发起并复用现有刷新及取消语义。
- 验证流程：Issue 对话或动态入口 → 阅读最终报告 → 查看必要原文件 → 按需核对验收；手机和桌面均能完成，正文无需由用户拼接。

## R3：改进报告撰写与现有审阅判断

- 在实际调查、实现、验收及负责人的指引中落实自包含交付：简短背景及原始问题、直接结论、影响与剩余未知、下一步建议，证据附后。
- 正文解释具体发生了什么，不用内部术语循环解释，不用哈希、权限声明和执行过程替代答案。范围有重要变化时简短交代。
- 现有审阅同时判断最终成果是否清楚回答问题、普通读者是否能理解；不增加机械字数、格式、字段要求或额外强制审阅轮次。
- 验收报告作为支持材料，不与主要成果并列要求用户阅读。审阅通过不自动证明最终通知已发布。

## R4：交付观察与原任务重跑

- 现有本地观察器解释工具结果中的成功或失败，区分账本登记、Issue 关闭、正式消息和附件发布；不能把工具事件已入账或回合完成当成发布成功。
- 旧定时器保持停止，不新建巡检或模型等待循环；沿必要的有界观察核对本次验证任务。
- 修复合入、部署并确认实际版本后，使用原已关闭的调查 Issue 和原始截图/问题背景安排重跑，由负责人重建必要上下文并交付可读报告；保留历史失败、报告和验收。不启动另一条 backlog，也不建立重复 Issue。
- 原执行 Task 已完成，不能通过重试复活；沿原 Issue 的真实新来源重开责任，由恢复的负责人安排报告修订，确需新执行或新验收时在同一 Issue 下建立后续 Task。这个执行身份变化不代表另建问题或删除历史。
- 重跑成功要求真实的最终回复、可阅读的已验收成果及正确的收尾；实现代码不直接代替负责人写业务报告。

## 验证与交付

先运行与实际缺陷相关的回归和前端阅读验证。最终候选完成仓库要求的完整本地检查、独立审阅及所需 CI，经线性 PR 合入。按现有配置受控部署，保持执行配置不变，分别确认服务进程和健康回执。公开资料不包含部署身份、私有路径或原生产记录；现场证据保留在忽略目录中。
