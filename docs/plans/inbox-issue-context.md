# 收件箱的 Issue 上下文与待处理入口

Refs: D125、D132、D133。状态：实现与沙盒已获确认，完成工程门禁和独立评审后提交 PR。

## 问题与目标

收件箱角标统计未解决的决定和行动，但列表默认混入已处理历史，并自动选中最早的记录。故障标题只说明执行失败，列表和详情都未直接呈现所属 Issue 名称，用户无法判断需要处理哪件事。

列表及详情应首先说明所属 Issue、执行任务、原始问题和需要用户采取的动作。默认待处理列表与历史入口分开；已读状态独立于业务完成状态。

## 方案

1. 在 owner API 的 AttentionView 增加可选的 issue_title、task_title 只读投影，取自既有 Issue 和 Task，不改问题原件、存储、版本或 runner wire。同步生成 Schema 和前端类型，避免按每条记录额外请求 Issue。
2. 收件箱默认请求 open 记录，提供“待处理 / 全部记录”入口。待处理包括收起但尚未解决的事项，保持角标和可处理列表一致；类型筛选与分页保留当前入口。直接链接仍能读取已解决记录。
3. 列表以所属 Issue 名称为主要标题，下面展示原问题或固定失败问题的简明摘要。无 Issue 时明确显示“全局事项”，不以技术 ID 或虚构名称替代业务上下文。
   用户确认类型名称统一为“需要你决定 / 需要你处理”，用于筛选页签和记录标签，明确需要 owner 回应，避免“待行动”被理解为 Agent 尚未开始执行。
4. 详情顶部直接显示 Issue 名称和执行任务名称，随后保留原问题、选项、答复、请求去重和版本校验。时间提醒放入可展开区域。开放决定与行动不提供容易与完成混淆的收起按钮，已读和稍后处理保留明确说明。通知保留收起入口，收起后从待处理列表隐藏，仍可在全部记录查看。
   根据设计反馈补充原目标、当前版本是否有交付物及该交付物是否有同 spec 的通过验收记录；只从当前账本投影，不用“没有交付物”推断“没有做过修改”。固定系统选项增加真实效果说明；修改要求仅记录意图，不能宣称修改已执行；取消执行任务不等同于关闭 Issue。
   当前结果优先呈现已知的实现／验收失败及原始原因，不能以“等待用户决定”替代结果；决定区域只询问如何继续。原问题放入可展开记录。已经答复或任务已推进时展示当前状态，不把历史失败当成当前失败。
5. 使用既有独立 tend-sandbox 和真实 owner API 构造“两条已处理记录 + 一条待处理失败决定”的场景。通过沙盒 app 命令创建数据，不读取或变更生产账本，不调用真实模型，不操作线上任务。

## 独立评审修正

- 待处理默认列表和角标通过 `actionable_only` 在分页前筛选决定与行动；归档决定／行动仍是待处理义务。通知通过独立类型页签读取，避免历史通知挤占分页后隐藏真实待处理项。
- 当前版本是否有交付物从 artifact → run → action 的 spec 关联派生，验收要求返工后仍保留已提交证据，不把清空验收候选指针显示为没有交付物。
- 当前任务状态复用既有 execution 投影，分页共享调度事实；未知租约／执行保持 unknown，不以任务生命周期推断正在执行。
- run、host 和 workspace 事实会使已打开的 Attention 读取失效并刷新；没有打开的页面不发起读取。失败原因只在原决定的控制版本仍匹配当前任务时作为当前结果，否则保留在原始问题中。
- CI 的 320 像素巡检发现长类型名称会挤压短页签的点击区域。手机页签禁止收缩并保留最小触摸宽度，超出时沿用容器内部滚动，保证每个筛选仍可操作。

## 验证与交付边界

- API 回归验证 Issue 与 Task 标题投影、全局事项及原决定身份保持不变。
- Web 验证待处理/全部记录请求、默认选中、已读仍保留角标、提交决定后消失且可从全部记录查看；覆盖长中文 Issue 标题、全局事项、桌面与手机。
- 运行类型、格式、lint、单元与构建检查，以及适用 Go 检查；提交前完整 make check。
- 设计图与真实沙盒已经过用户确认，按当前信息层级交付；完整工程门禁和独立评审通过后提交 PR，合并遵循仓库 CI 要求，正式部署单独受控推进。
