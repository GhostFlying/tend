# 具名后台变化通知

Refs: D240。

## 目标与故障路径

Issue 讨论中的后台批次目前固定显示“负责人收到后台变化”，折叠内容只有泛化消息，用户无法判断接收者和具体变化。已有背景批次、来源、实际 Run 执行 pin 和只读来源分页是事实来源；本次只改变 owner 展示投影及 Web 呈现，不创建通知、任务、权限或新业务写入入口。

目标路径为：已保存的背景来源和批次 → owner conversation/transcript 投影 → 具名、具体的通知概要 → 展开查看来源原文并通过原 Issue／Task／消息身份回到对象。

## 实现边界

1. 在既有背景批次展示元数据中增加有界来源概要及实际接收 Agent 的身份。身份必须来自该批次的实际执行绑定；无实际执行证据时保留未知，不把当前负责人反投射到历史通知。
2. 使用现有来源 kind、body、data 和原始消息 ID 说明哪些对象有何变化。列表保持有界，显式保留更多来源标志，展开后复用原来源分页接口读取原文。
3. 待处理、已领取和完成核对分开表达；进入队列不显示成 Agent 已执行。旧通知缺少元数据时显示明确的保守文案，并仍可读取来源。
4. 不修改后台通知合并、水位、消费、租约、执行与权限规则；来源读取失败只影响该通知展开，并提供重试，不阻塞讨论。
5. 字段是向后兼容的 owner 只读投影扩展，不改变 server／runner wire 或 CLI 操作。复用既有 CLI background sources 与 API 原文分页，类型由现有 schema 流程统一生成。

## 验证

- 投影回归使用真实持久背景批次、实际执行 pin 和更换后的当前负责人，检查历史身份不会被改写；待处理、来源取消与有界分页各自保留真实状态。
- 组件回归检查具名、事件对象／摘要和链接，及无身份、读取失败、尚未处理时的保守文案。
- 在合成只读 API fixture 中通过真实浏览器展开通知、读取下一页并使用对象入口；核对桌面和窄屏、控制台与截图。该验证不构成生产业务或部署证明。
- 最终整包 review、full、CI、合入与部署由协调 agent 在冻结组合候选后统一执行。

## 原独立审阅修正

同一 pending 批次的新增与取消来源必须使展开原件失效；折叠期间保持惰性读取，展开时核对最新 metadata。投影从已保存 source data_json 及批次所属对象补足真实 Issue 来源链接，使用实际状态/定义通知 producer 到 conversation 的完整回归，而非仅人工添加关联。只读 source watermark 取现有来源 seq，不新增存储计数、迁移或账本。
