# Owner 当前回合补充消息：验收修正与依赖整合

## 调查结论

原功能已保存为本地提交，工作区开始时无未提交改动。原生回调先按原 turn 投递确定来源，随后消费 user-item 并将来源切到补充消息；`main_tool_sources` 仅固定相同 native call ID。规划业务去重目前按 `(source_message_id, commit_seq)`，因此消费状态询问后使用新 call ID 重试旧序号会绕过去重。来源用于 owner 审计，不能为修正去重而抹掉真实补充消息来源。

Web 的 waiting 通用提示将附件/消息准备失败也解释为原生拒绝，但该失败发生在原生调用之前，消息仍排队。需要准确区分阶段。

正式 main 已有 D107 独立 app-server 环境隔离和 D108 身份绑定/handback 恢复。本功能原设计号占用 D107，需要在线性整合时改号，不能覆盖正式决策。所有模型测试子进程必须清除大小写不敏感的 ORCA_ 环境项，保留外层环境和已有模型鉴权配置。

1. 获取正式依赖，保存原提交可达引用并 rebase 原功能到 D108 提交，逐文件解决冲突，保留全部功能。将本功能设计号改为下一个可用编号，保留 D107/D108 原文与依赖代码。
2. 在 hosted 工具调用上下文从持久初始投递（或 turn/start 未完成时的 active 初始投递）独立传递稳定规划身份，业务事务用它去重，同时 payload、任务/spec、工作项和消息绑定保留实际 owner 审计来源。其他执行形态保持既有语义；不改 worker 投递模块。
