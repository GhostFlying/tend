# 原生完成后的关闭对账

状态：实施。沿 D203 保留业务结果、原生终态和资源关闭各自的事实。

## 已复现的问题

一次报告执行已保存结果与文件，并持久化原 Run、attempt、thread 和 turn 的原生
completed 事实。关闭前发现脱离原进程组的后代后，Session 仍退出原 app-server，
却不保存关闭观察；随后恢复仅接受仍活着的原 leader 或既有关闭证明。即便已记录
的后代后来退出，重入仍反复得到相同拒绝，原结果不能进入后续验收。

最后三条原生事件已在 runner journal，但其有界上传也被资源关闭成功条件拦住，
导致服务端继续显示旧的 running。已保存的业务结果不等于资源已经关闭；反过来，
关闭尚待对账也不应抹去已经收到的原生终态。

## C1：保留并发送完成事实

- 在执行结束及 worker_done 重入时，通过现有上传与 ACK 路径有界刷新原事件。
- 使用原事件序号、Run、租约及请求身份；失败保持原队列，不重放原生输入。
- 上传原生 completed 只更新已观察事实，不伪造关闭回执、不提前提交成果或启动验收。
- 回归覆盖关闭不确定、上传失败后重入、原 ACK 去重及取消上下文。

## C2：有界且可恢复的正常关闭

- 复现真实 Session 关闭顺序：观察到 detached 后代后，原 leader 退出，关闭未确认，
  后代随后退出。测试必须覆盖恢复重入，而非仅断言第一次拒绝。
- 正常 Close 的历史成功与后来的进程集合对账使用不同记录。原 Close 失败后，
  对原 leader、原组及已登记 detached 身份及其可能的进程组进行新鲜核对；全部
  无活跃且没有身份冲突或观察错误时，记录明确的 `known_owned_process_set` 范围。
  不把这个事实写成原 Close 曾成功，也不要求证明任意未观察历史后代不存在。
- 保留已复现的晚生后代边界：已登记 detached leader 退出后，它的原进程组仍有
  活跃成员，仍必须拒绝。未观察的假设不成为无限阻塞理由。
- 只操作本执行已证明归属的进程；PID 复用、仍活跃后代、观察或持久化失败保持
  未确认。每次关闭与对账有明确期限，不启动新的模型或业务执行。
- 新鲜对账沿原 `StopOwnedWorker` 与 worker_done 接点自动处理本次既有 Run；
  不手写成功回执、不改业务数据库、不用新 Task 绕过旧结果。原生业务终态仍独立
  校验，进程集合退出不证明业务成功。实际仍活跃或观察失败的集合继续隔离。
- 关闭范围为本机已有身份所界定的受管执行，不声称覆盖未登记的任意外部副作用。
  这是对当前无限后代反证要求的明确简化，与 agent 自主执行的约定一致。

## C3：交付与原结果恢复

- 在编码前收敛具体关闭证据设计，并同步更新设计决策；明确本地持久化兼容及
  server/runner 通信是否变化。
- 对真实关闭竞态和原结果恢复运行必要回归，再完成仓库要求的完整检查、独立
  review、CI 和 PR 合入。
- 保持现有执行配置受控部署；保留原 Run、原结果及文件，由 Tend 从原责任链
  继续新的独立验收和最终 chat 发布，不重复报告业务执行。

现场身份、原日志、机器路径及操作记录仅保存在忽略目录。
