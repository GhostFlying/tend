# 多组检查的包并行预算下限

当前检查驱动在8个有效 CPU、两组并行时，以 `cpus/10` 将多包 Other 固定为 `-p1`，但已有最大同时进程槽预算可以容纳两包、每包两个 Go 执行线程。本计划只利用这部分预算，不修改产品逻辑、检查集合、超时、分组顺序或原生测试缓存语义。

## C1：复用已有进程槽预算

保留现有 package 预算及上限，仅在 `jobs>1` 时将下限提高为 `min(2,cpus/(2*jobs))`。仍将各组进程槽排序，取最大 `jobs` 项之和推导每个子进程的 GOMAXPROCS。8 CPU、App2、suite2、Other2、CHECK2 的最大两组共四个进程，每个两个线程，总声明 CPU 为8。默认32/64 CPU 预算、显式单组 profile、E2E 独占及串行原因校验保持不变。

## C2：验证与结论范围

先落盘计划，再调整既有 capacity 表和任务环境检查；运行1至128 CPU、1至7组的现有资源不超配性质检查，并验证包并行值确实进入 GOFLAGS，未改变私有 Web 产物和 E2E 隔离。

已有一次相同 Store、Serverkit 各两个固定根的 race 配对，串行墙钟55.208秒，并行33.834秒，八个根执行均通过。该先串行后并行的短样本没有覆盖长 sandbox、其他 runner 用例或与 App 同时执行，不推断完整检查收益，也不解释另案的 named 等待截止失败。最终效果和全部检查集合只由本批原本需要的一次最终正常 `make check` 验证，不追加性能 full。
