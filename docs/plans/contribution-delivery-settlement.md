# 已完成交付中的历史贡献结算

## 问题与范围

同一 PR 的早期实现和候选准备 Task 已接受完成，后续 Task 真实合入、部署并通过
独立验收，其交付责任也已结清；早期贡献仍只有 preparing 责任。现有 complete
只读取责任自身的执行绑定，不能使用调用方提供的已完成执行，因此 Issue 无法
正常关闭。不能重开 Task、重复部署或以 end_delivery 冒充实际完成。

本次只补历史结算路径（D215）。Issue 的部署授权策略和部署连接配置另行处理。

## 实施

1. 复用现有 `issues.update_delivery action=complete` 的 `execution_task_id`。
   仅为尚未进入候选执行的历史贡献责任，允许显式引用同 Issue 已接受且交付责任
   已 complete 的真实执行。必须有同 PR 的明确贡献关联，不能仅凭 Task 名称或
   同一 Issue 推断贡献；不得重新绑定、启动或改写原执行。
2. 以原贡献的接受事实、已结清执行及其冻结的 provider/upgrade 证据记录完整
   结算来源。保持旧 Task/spec、artifact、费用、批准、请求与升级不变。历史结算
   不要求当前 main 或部署基线仍等于原候选；也不授予新的合入、部署或执行能力。
   调用方提供 upgrade_id 时必须与该真实执行原升级一致。
3. 仍拒绝尚未验收/尚未结清的执行、无关贡献或 PR、跨 Issue 引用，以及试图
   覆盖已有候选/执行责任的请求。真实存储错误保留，不把未知或未完成当完成。
4. 同步设计、CLI 帮助/能力说明与完整输入验证，不增加新操作、表或 runner wire。

## 验证与交付

用实际完成和接受路径构造回归：原贡献保持 preparing、后续执行已结清；既有
输入在修复前失败，修复后结算贡献并允许原 Issue 关闭。覆盖原请求幂等、来源
不变、后续维护推进基线、错误执行/PR/Issue 和尚未结清状态。不重跑真实模型。

定向 regular/race/vet 后，完成最终候选的完整 make check、独立 review、CI，
从最新 main rebase 合入，按现有授权和配置受控部署。最后由原负责人沿原任务、
原最终报告和真实结算证据关闭 Issue；不重复业务交付或唤醒下一个 backlog。
