# Issue 默认进展中的 PR 冲突与候选

- 复用已登记交付的 provider 观察与变更事件。显示 PR、head、base、当时的目标分支 tip、观察时间和来源。保留最近一次有明确候选身份的冲突，区分当前冲突、查询待确认和随后观察到的新 head。只凭新 head 确认提供方已有新候选。
- 扩展既有进展提交，允许显式绑定交付候选。当前负责人可对确切冲突记录“已看到”或“已开始处理”；服务端验证责任、候选与冲突匹配。读取、分派、运行或普通进展文字不产生这些记录。
- 默认 Issue 进展显示当前交付，活动历史展示已保存的候选观察和带候选的进展。候选过期的总结与下一步标为历史。已有无绑定总结保留，CI 只在其 head 与观察候选匹配时展示。
- 使用真实观察提交与进展写入验证检测、确认、处理、新候选、旧证据、未知和过期候选。检查默认页面渲染、CLI JSON、仓库影响检查、独立整 PR 审阅及候选 CI。
- 沿用现有观察刷新、回执与重试。观察延迟或失败时保留上次有来源的历史，手工进展可继续。评审、审批、合入和部署沿用原规则。

### 首轮独立审阅后的修订

- 在候选替换时保存被替换的最后一次已观察快照。即使旧观察来自升级前或一次无变化的读取，活动仍可看到当时的 CI。沿用交付观察的归属和事件顺序。
- 编辑现有总结默认保留原候选，显式重新选择时才改变关联。原候选已过期时继续按历史标识显示，修改总结不重新声明负责人动作。
- 基线发生变化、PR 关闭或冲突明确消失后，再次观察到冲突时分配新的身份。Issue 重开后从新的责任周期展示负责人动作。
- 当前进展根据最新交付观察判断适用性。历史修订读取保留原进展语义。移动端默认可见的历史标签覆盖没有候选绑定的旧总结。
- 使用首轮审阅原件复核六项场景。首轮 CI 的沙盒失败继续保留，修订后的候选由自己的 CI 验证。
