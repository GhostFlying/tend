# 存储清理与改造：业务状态、持久原件及备份

状态：实施中。按已确认原则完成源码、历史迁移与恢复演练后，统一受控发布及清理。
所有删除均绑定已核验的迁移或回收清单，保留真实未结动作和恢复责任。
Refs: D11、D87、D200、D223、D224、D225。

已确认原则：内部幂等由业务唯一 key、唯一约束与业务状态完成。内部请求不独立
持久化请求档案、参数摘要、返回缓存或请求到业务对象的映射；通用请求表目标占用为零。
真实业务对象、待执行命令和外部动作状态保存在各自 SoT 中，不建立变名后的请求账本。

调查基线：2026-11-11，源码 `c570b9639c03734f3bdea62462fbeb6e750d2ee1`、
schema 118、runner 协议 3；实施开始时再次核对实际版本。

## 1. 目标与已核实基线

在保留真实业务历史、业务幂等与对账、原生事件去重、用量与附件可读取性的前提下，
同时减少在线数据库、重复文件和备份占用，并修正持续产生重复数据的写入方式。
先停止产生新的冗余，再迁移历史，最后回收副本和压缩数据库。

基线来自同一源码版本的只读表页、字段长度、精确重复比较与调用链调查。
所有 MB、GB 使用十进制。数据库收益以相同数据集计算，不将自然增长算作回归。

迁移时先确定对应真实业务动作和结果，再退出旧请求存储；不把历史请求状态继续
作为新模型的权威事实，也不能因顶层 Issue 结束而一并清除真实未结动作。

## 2. 明确存储边界

### 2.1 留在 DB 的内容

- Issue、Task/spec 版本、Run、产物归属、贡献、审阅结论、交付责任与真实用户授权。
- 控制 revision、实际身份和对象关系、租约、并发占用、等待条件、领取与投递水位。
- 业务对象和动作自身的稳定身份、必要的内容冲突信息、成功/失败/unknown 与版本事实；
  不要求对所有 HTTP/工具请求另建请求记录。
- 原生事件身份和连续序号、去重键、文件稳定身份及 offset/length/hash 索引。
- 用量不可变计数、归属和覆盖事实，以及服务实际查询所需的紧凑增量投影。
- 需要和状态变化原子提交的紧凑业务事件、未完成投递和消费水位；
  已有业务唯一键的事实不再另存一份 inbox 去重记录，纯刷新通知不建立永久事件历史。

短标题、状态、短消息和经查询使用的小字段可直接保存。不会为了“全部文件化”
将短字段拆成大量小文件，也不会把有实际查询用途的用量投影改成每次读取都扫文件。

### 2.2 由持久文件保存的内容

- rollout、工具输入输出、原生事件原文、调试日志及完整命令正文。
- 最终业务结论实际引用的独有原始材料，以及无法从业务版本重建的未结动作固定输入。
  普通周期查询的完整返回、已完成动作的输入副本不默认归档；模型价目表只保留最新有效值。
- 能从业务权威记录重建的普通接口返回直接组装，不另存返回正文或返回正文文件。
- 完整检查或调查报告、证据原件及附件；数据库保留正文引用与业务关系。

沿用 blobstore 和原件归档，不建立第二套文件系统或业务总线。已有 rollout 内容
直接引用稳定窗口；只对没有对应原件的独有内容持久化一次。重建规则也只保存一份。
正文不再依次复制到原生事件、请求回执、后台缓冲、工具展示等多张表。

### 2.3 可以移除的内容

- 已确认重复且可通过同一稳定引用恢复的正文、重复嵌入的重建规则及版本原因。
- 有真实查询证据支持裁剪的冗余索引、重复投影字段和重复维度表示。
- 全部读写和 schema 依赖退役后的小型遗留表；历史唯一事实先归档。
- 不再被在线数据、保留备份、未结操作或正在暂存的写入引用的文件。
- 超过保留策略且不再承担恢复责任的备份、演练工作副本与临时文件。

“空表”“日志名字”“已经失败”“未找到配套回执”都不是单独的删除依据。

## 3. 改造工作包

### S1：统一正文引用，修正重建规则放大

涉及 `retained_original_bodies`、`retained_body_recipes` 和所有引用它们的记录。

1. 先区分权威原件和普通派生 JSON。派生展示或接口返回优先从业务记录组装；
   可以直接引用完整原件时只保存稳定窗口，不默认生成重建规则。
2. 现有重建规则记录“固定 JSON 片段＋原件文件窗口＋必要编码”，用于恢复已有历史正文。
   只有确有原始内容校验或外部读取要求时才保留；不为了键顺序、空白或重复的接口外壳
   默认保留所有返回字节。必要规则保存一次，业务行只保存短引用。
   沿归档段/pack 保存，不为每个窗口或规则创建一个小文件；新规则不递归打包历史正文。
3. 文件归档的长身份只在归档元数据中保存一次，窗口使用内部紧凑关联键；
   hash 在 DB 使用二进制表示，公开 ID、历史请求 ID 和外部 hash 表示保持不变。
4. canonical hash 只作为候选筛选；精确读取、校验与冲突语义继续保留。
   维护已修复的非空部分索引查询条件，不重新引入扫描。
5. 明确每个查询使用的投影字段，避免通用 JSON 投影继续携带无查询用途的大结构。

全部 22,407 条现有规则都有实际引用，不能整表删除。逐类改为 SoT 组装、直接窗口
或必要的共享规则；核验对应消费者后，再移除 23,215 处嵌入规则和不再需要的规则。

### S2：覆盖工具、后台输出及其余大正文路径

涉及 `background_replies`、`conversation_tool_uses`、三个原生事件/日志表、
`manager_native_requests`，以及大上下文、历史查询响应等。

1. 后台缓冲和已发布的工具展示共同引用同一正文；发布时间、顺序、来源、处理位置
   和未发布状态分别保留。发布不再复制 input/output。
2. 工具预览只是展示投影，完整原件可以按需读取。对于历史已经截断的预览，
   如无可核实原件，继续标记截断，不宣称通过迁移恢复了从未保存的内容。
3. 将日志类原文移出 DB；保留按 Run/序号/时间查询的紧凑索引和消费水位。
   真正的业务状态变化仍在原事务提交。纯刷新通知只维护对象/范围版本和合并后的
   待通知位置，不将每次变化追加为永久业务事件；游标过期时从 SoT 重取当前视图。
4. 大型命令和结果、冻结上下文/交接正文、历史外部查询响应使用同一原件引用设施。
   正在 pending、prepared、unknown 的记录仍保留其完整冻结输入及对账身份。
5. 小型业务消息可以 inline；大字段迁移按实际读写语义判断，不能只按列名批量替换。

现有正文迁移的“pending=0”只覆盖原先列出的六条字段路径。新清单必须覆盖新写入、
历史迁移和校验的全部正文路径，按字段分别报告覆盖，不能继续用局部完成代表全部完成。

### S3：以业务事实完成幂等，退出通用请求账本

业务记录是 SoT。内部幂等只使用业务唯一 key，不保存独立请求档案、请求级 hash、
请求到对象的映射、返回缓存或返回正文文件。
当前 `request_records` 通用保存返回 JSON，`native_requests` 又逐项分配请求映射，
这些是既有实现方式，不是正确性的前提。本项退役两张通用表及其全部索引；
不预留另一份紧凑请求表或回执定位表。业务权限、状态机与版本校验继续属于原业务入口。

1. 创建对象由调用方提供稳定对象 ID，或使用已有明确业务唯一键；同一对象重试受
   业务主键约束，详情从 SoT 读取。不得按标题/内容相似猜测是否同一个创建意图。
2. 修改已有对象使用业务状态机和 expected revision。冲突后读取真实状态判断，
   不要求所有重试逐字节返回第一次响应，也不为保证旧响应永久保留请求结果。
3. 原生事件用 Run/sequence、thread/turn/item/phase 等实际身份去重，
   用量按原生响应身份去重，ACK 按业务水位处理。若业务自身要求不可变事实一致，
   在对应业务记录校验；不为幂等另外保存每次请求的参数摘要。
4. 部署、执行、消息投递等异步业务动作保存自身命令/执行身份、实际输入、授权及状态；
   业务结果不确定时按该动作对账，不重放。该记录承担真实业务责任，不是每个 HTTP
   请求都保存一份的通用账本。普通请求的 trace/诊断放轮转日志。
5. 普通响应从 SoT 组装，当前状态和真实历史版本明确区分。确有历史查询需求时使用
   已有业务版本/事件；不可替代的外部原始回执使用原件引用，不默认缓存全部响应。
6. 列出当前请求表对恢复授权、动作绑定、失败判断和历史读取的实际消费者，
   将必要事实迁到对应业务记录。已经覆盖的记录清除，唯一事实和未结动作先迁移对账。
   历史失败请求不能冒充未执行的新请求，历史真实对象/动作 ID 不重新分配。
7. 并发创建、同一对象键内容冲突、CAS 冲突、删除对象后的晚到重报、重启及断线均验证。
   外部接口重试语义变化按真实 breaking change 处理；旧读取适配有明确退出条件。
8. 同步修改 D11、请求去重的工程约定和相应 API/CLI/工具，保留 app 单事务业务写入、
   对象权限和真实业务幂等，不把通用请求表固定为架构不变量。
9. 同步退出 server 和 runner 的请求级记录。`manager_native_requests` 中已完成 RPC
   的请求/响应历史不再持久保存；普通只读 RPC 不进入持久请求账本。真实待执行命令
   沿现有命令投递路径保存业务执行键、必要输入和实际状态，完成后结果归属 Run、
   会话或对应业务对象；原始证据引用现有原件，不保留另一份命令完成历史缓存。

当前 12,731 条映射中 11,218 条来自工具 item 阶段，优先退出这条重复记录路径。
87 条没有通用回执的映射仍逐项确认实际含义，不直接因缺少关联当作垃圾删除。
迁移期间沿原历史身份解析既有记录，不能仅删表就让旧操作被再次执行。

### S4：用量事实与投影瘦身

1. 计数、原生响应身份、归因版本和覆盖水位保留为紧凑 DB 事实，原始提供方证据
   使用已有原件引用；计数冲突不被元数据补全掩盖。
2. 将反复存储的 title、归因维度等规范化；去掉 contribution 中可从权威记录恢复的
   重复 `record_json`、`dimension_json`、`totals_json` 表达，采用适当的类型化列。
   必要的归属变更历史引用真实业务版本；金额统一按最新价目估算，不冻结历史价格或费用。
3. 缩短内部主键，减少长 `(source, request_id)` 在 11 个 secondary index 中的放大。
   按真实筛选、分页、归因、补采和完整重建查询决定保留、合并或删除索引。
4. 保留有界增量 summary 及 dirty/watermark 机制。投影可以重建，但不能在日常读取时
   反复扫全部原件，也不通过重跑业务恢复计量。
5. 模型价目表是 OpenRouter 模型价格目录，只保留最新有效目录及其获取时间。
   更新成功后替换上一份；失败时保留最近有效值并显示时间。当前旧快照迁移时删除，
   不转存历史文件，不保留历史价目版本。金额按最新价目估算，不提供历史价格重放。
   历史用量的金额也标为估算，价目更新后由当前计数和最新价格重算必要的小聚合。
   原始 token 计数不因价格变化而改写，不保存每次估价或每次重算的历史副本。
6. 原生响应计数采用紧凑类型化列和业务唯一 key；来源、模型、归属和文件定位共用关联。
   不逐条保存整份 TokenUsageSample JSON、参数摘要或通用请求记录。
   页面汇总只使用小聚合；时间筛选、明细、归属修正和断点补采使用必要的小明细索引。
7. `token_usage.changed` 与其他纯刷新通知使用按订阅范围合并的版本/水位。
   一个范围待通知时后续变化推进其水位，消费确认后清除待通知状态；
   不保留每个响应一条的已处理通知历史，也不因合并而省略真实 token 计数。

验收使用已经核实的固定响应集合、逐响应计数、归属与覆盖状态。重扫、重复补采、
断线和历史恢复均不得增加一次计费或重新遗漏曾恢复的响应。

### S5：小型冗余和遗留结构

- 297 组重复版本原因保存一个权威版本，另一处通过该版本引用，保留各自控制语义。
- `request_records_trace` 约 3.82 MB，随通用请求表一起退役，已计入请求组的
  77.48 MB，不再作为额外索引收益相加；诊断消费者改读轮转日志或真实业务事实。
- `agent_sessions`、`background_assessments` 是退役候选；后者仍被旧 trigger 引用，
  必须一并处理。`retained_delivery_observations` 的四条历史事实先归档并核实迁移来源。
- 其他小表默认保留。空表总收益很小，禁止仅为降低表数批量删除；
  `sqlite_sequence`、迁移记录、晚到消息 fencing 等有实际用途的结构继续保留。

逐表处置清单须包含字段、实际读写者、schema 依赖、行数、字节和结论强度。
静态未找到引用表示候选，不能直接等同于“已证实无用”。

### S6：备份、文件回收与增长治理

建议默认保留策略如下；保护条件优先于数量和期限，超过预算时报告原因。

| 对象 | 建议策略 |
| --- | --- |
| 恢复检查点 | 每节点至少最近两个已验证可恢复检查点；含 DB、文件清单、配置及源码/组件身份 |
| 日常历史 | 最近 7 个日备份、4 个周备份；同一备份兼任多个时间档，不重复复制 |
| 迁移前锚点 | 保护到新版本恢复演练通过且观察满 7 天；不兼容 schema 变更的锚点至少保留 30 天 |
| unknown/争议现场 | 显式保护至对账完成或人工处置，不按过期时间自动删除 |
| 成功演练工作副本 | 恢复证明落盘后不再承担备份责任；默认 24 小时后回收大副本 |
| 已解释的失败演练副本 | 唯一事实归档并被有效恢复点覆盖后，默认 7 天回收；紧凑证据保留 |
| 唯一业务原件 | 只要业务或保留备份仍引用就保留；不按 Issue 关闭或文件年龄删除 |
| 普通诊断日志 | 默认保留 30 天，7 天后压缩；被事件调查引用的片段显式保护 |

备份改为紧凑 DB 快照加文件 manifest，复用不可变文件对象；同一存储内按内容身份
保存一次。保留备份必须固定其需要的文件对象，不能靠活跃 DB 当前引用决定文件生死。
独立灾备仍需在独立故障域保存实际内容，引用同一块盘不算独立备份。

沿 updater 的现有备份和控制流程实现 preview/status/verify/prune，不用临时脚本
直接递归删除目录。preview 输出保留、可删、受保护与 unknown 清单、原因和预计字节；
执行绑定清单摘要和恢复点，状态变化时重算，保留明确回执和可恢复进度。

文件回收以在线 DB、保留备份、未结操作及暂存写入的引用并集为根。
第一批仅回收整对象未引用的文件，不重排含活跃窗口的 pack，不改变既有 offset。
原件不能直接 gzip 后继续沿用旧窗口；压缩编码如需调整应单独设计可随机读取的索引。
不能通过复制到同盘另一目录宣称释放空间。实际回收前后分别记录文件长度、
分配块数和可测的独占物理空间，并注明无法确认的 COW 共享。

### S7：runner journal 和离线传输副本

## 4. 迁移、验证、压缩与回滚

### P0：冻结验收基线

- 重用本次逐表调查；实施前增量核对实际源码、schema、协议、未结操作及文件范围。
- 制作一个 DB 与文件一致的受保护迁移前恢复点，核实恢复能力。
- 同一历史快照建立历史 API/日志分页、原请求结果、原件窗口和用量基线。
  记录 writer 排队/持有、API 分位数、写入字节与查询计划。

### P1：先完成新写入与兼容读取

- S1–S7 在同一分支分原子提交，新增迁移，修正新写入；停止产生旧的大正文副本。
- 兼容读取既有 inline、旧规则、新引用；每次只写一个权威正文，不长期双写。
- 文件在事务前持久化，事务提交引用与业务事实；回滚事务留下的无引用文件由回收流程处理。
- 新接口沿 owner API、Agent 工具、CLI 扩展，同步能力目录、帮助、schema 和生成类型。
- 在可恢复的历史数据副本上完成迁移和恢复演练，再独立审阅、完整 `make check` 与 CI。
  不为每个字段修正分别部署。

### P2：一次受控发布，在线分批迁移

- 使用 format 2 完整发布集；现有 Agent、登录态、模型、思考强度、slot 与并发分组保持。
- 基线 runner 协议为 3；本次 claim 显式 Run ID 与原生命令双向确认改变 wire 语义，提升到 4、适配 3、
  退役 2 并验证拒绝，发布前核对实际节点和未结束执行，不重新沿用旧计划的 2→3 基线。
- 历史迁移以表/字段/稳定游标建立明确覆盖清单，按行数、字节和时间三重预算分批。
  推荐初始每批最多 100 行、准备数据最多 2 MB、目标事务持有低于 100 ms；
  按实际负载调节，保留原接口截止时间，不增大 timeout 掩盖慢写。
  超大单行单独流式准备和校验，不因超过普通批次字节预算永远被跳过。
- 查询、文件读取、解码及重建在 writer 外准备；事务内重验源值 hash、revision 和引用，
  冲突后重新准备当前批，不覆盖并发更新。
- 每批以迁移 ID 和批次序号唯一定位已提交进度，保存游标、水位和迁移结果。
  旧接口适配期间沿原 request_id 查询既有批次；新模型从迁移 SoT 对账。
  unknown 不自动另起动作；重启恢复同一迁移检查点，不从头重跑业务。

### P3：全量核验后清除旧字段

- 逐项核对 SoT 重建的真实业务结果、历史版本和新旧重试语义，以及日志顺序和游标、
  Unicode 字节/字符窗口、附件权限、原件完整读取、冻结 prompt 与覆盖统计。
  不以仅行数相同代替内容相同，也不强制所有派生 API JSON 与旧缓存逐字节相同。
- 对缺文件、损坏、半写、DB 事务回滚、进程退出、并发读取和备份恢复验证真实错误与可恢复性。
- 新旧 API 的对象级授权一致；迁出的原件不能通过裸路径绕过原权限。
- 检查业务数字序号和真实分页游标；不能要求所有隐藏 rowid 相同，也不能忽略实际游标变化。
- 已验证批次才清除旧重复字段；读取所有历史格式的责任与退役时间显式登记。
  历史 schema/备份读取和通信适配分别管理，不将必要的历史读取当过期网络适配删除。

### P4：单次物理压缩与备份回收

- 全覆盖完成后安排一个有界维护窗口，执行一次实际 DB 压缩。
  恢复入口与长压缩分离；已证实 SQL 没有执行才允许新动作，unknown 先对账。
- 每阶段输出正在执行的步骤、截止时间、原操作身份和失败原因；到期执行恢复流程，
  不无限等待。原 DB、服务单元和配置身份以真实状态复核，启动后允许有界 readiness 重试。
- 压缩成功、服务恢复、正文可读和现场回收分别验收。一个即时 health GET 失败
  不能覆盖“进程已启动”的事实，也不能触发无条件重复 Start 或重复 VACUUM。
- 新恢复点通过演练后，执行绑定 preview 的备份清理和孤儿对象回收。
  旧证据、受保护 unknown 和仍被保留备份引用的原件保持。

回滚：迁移前恢复已配套的源码、配置、DB 与文件；迁移期间优先停止新批次并从
原检查点恢复，不先恢复旧 DB 而遗失此后已提交的业务写入。存在迁移后的业务写入时，
必须先保全并对账这些新增事实，不能直接覆盖线上 DB。旧二进制不读取新格式；
旧恢复点也不能引用已清理的文件对象。

### 5.2 按唯一事实、冷数据与常用投影审查字段

必要性审查以字段和事实为单位，不按整张表简单分类。同一行可能同时包含唯一的
业务关联、可从文件恢复的原文和可重建的查询投影。唯一信息也不必全部进 DB：
需要事务和业务查询的事实留 DB，独有的历史材料进入持久原件。

| 类别 | 具体内容 | 存储和读取方向 |
| --- | --- | --- |
| 唯一业务事实 | 用户原始输入、真正需求/授权、责任归属、实际归属变更、状态转换、外部操作 identity/unknown、租约与消费水位 | 在对应业务 SoT 原子保存；业务主键与引用足够，不引入请求档案 |
| 唯一原始材料 | 无其他来源的 runner 事件、最终业务结论确实引用的原始证据、无法从版本重建的未结动作输入 | 原件一次保存；不保留模型历史价目、一般查询返回或已完成命令的独立副本 |
| 可恢复且按需访问 | 有已验证原件的完整旧 rollout/日志/工具正文、派生上下文渲染、普通历史展示 JSON | 冷原件或按需组装；不保留另一份 DB 全文，未验证原件覆盖前不声称可恢复 |
| 可恢复的常用查询投影 | 用量计数聚合与过滤键、活跃消息顺序和 item 定位、执行当前恢复状态、当前 PR/检查视图 | 按实际查询保留紧凑列、索引和水位；派生大 JSON 不同层反复存 |
| 无额外信息或无保留用途 | 通用请求/返回档案、重复后台输出、同键 inbox、重复规则、已经处理的纯刷新通知 | 退出；不因为可恢复就保留副本，也不为将退役的请求读取保留加速层 |

“常用”目前由读取路径和调用方式支持，不代表已测得生产 QPS 或缓存命中率。
`web/src/live/data.ts` 在用量变更时刷新订阅视图；用量读视图使用 summary 聚合、
contribution 边界及分页。因此紧凑聚合和筛选索引有实际用途，不能由此论证保存
三份完整 JSON 或全部 11 个索引。当前 4–8 MB 是待迁移原型验证的预算。

`run_logs` 同时支持按需查看历史过程和当前执行恢复视图。完整历史原文属冷数据，
当前失败/恢复阶段和消费位置属于常用状态或投影；不能把整张日志表都叫冷缓存，
也不应为了显示当前阶段反复扫并读取历史大正文。

用量计数如果已在完整归档的原生响应中存在，可从原件重采，其紧凑 DB 表属于派生
事实/查询加速；Issue/Run 归属、人工修正、覆盖缺口和冲突处置可能是 Tend 独有事实，
不能从模型原始 token 数推断。字段名 `request_id` 在旧用量表中表示原生响应身份，
改造使用明确原生业务 key，不能将其与通用 HTTP 请求账本混为一谈。

模型价目表按已确认产品需求只保留最新有效值，不因旧值无法重取而保存历史。
当前生产源码能找到
`token_usage_binding_revisions` 的写入，未找到其正常读取者；历史确有业务保留目的时
归档，否则不应把整套旧归属副本当常用投影预算。静态未找到读取者仍需核对 schema 依赖。

原件字节可读不自动代表所有定位都可重建：archive→source/run/host 关联若只在 DB
存在，必须保留最小关联或已验证的清单。未结动作的固定输入若无法从版本重建，
要保留一次；动作完成且归属业务结果后退出独立输入副本，不扩展成每次请求的历史档案。

### 5.3 具体字段解释与已确认裁剪

- 价目表当前 38 行、3.27 MB；最新目录长度不超过约 85.5 KB，单份含页开销约
  0.1–0.2 MB。只保留最新，不再为历史价格或估价结果建立归档；金额明确是估算。
  相对当前表估计减少约 3.1 MB，已包含在用量组缩减中，不重复计算。
- “外部观测证据”限最终业务结论引用的真实材料，例如交付所依据的候选/检查/部署结果。
  普通周期 PR 查询的整个返回没有独立长期保留需求；保留业务结论与实际引用即可。
- “固定输入”具体包括会话交接时即将注入的 prompt。来源版本可重建时保留版本/引用；
  不能重建且动作仍未决时才保留单份内容，避免后来业务变化导致误认为发的是同一内容。
  现有 `main_thread_handoffs` 14 行中 prompt 值字节约 0.946 MB；这不是永久保留依据。
- “待执行命令”表示 server 已决定让某 Run 执行一个具体动作、runner 尚未确认结果。
  保存业务执行键、动作、固定输入版本或引用和真实执行阶段；结果归属 Run/会话后退出。
  当前原生执行表 5,814 行中 5,810 已 completed，3 pending、1 unknown；不能按这张
  历史表大小为当前队列预算，也不能据四条旧未结记录宣称有四个活跃任务。
- 用量事实的 4,522 行是原生响应/用量采样的版本行，当前身份为 4,142 个，不等于
  turn 数或精确线上 API 调用数。JSON 保存计数及大量来源字段，不含 prompt/回复正文。
  当前 payload JSON 4.04 MB、索引 1.58 MB，其余身份/行/页开销约 2.16 MB。
  仅五个 int64 计数字段的理论值字节为 180,880 字节（约 0.18 MB）；完整目标还需
  业务身份、时间、模型、归属、水位和必要索引，不能将理论计数字节称作实测 DB 大小。
- `events` 当前 7.24 MB：正文约 1.34 MB，文本身份/来源/actor 等约 3.24 MB，
  数字/行结构/页内空隙约 0.86 MB，索引约 1.80 MB。条数中至少 49.06% 是三类
  纯变化通知。移除永久通知历史和请求/trace 档案字段，业务 actor 等信息使用必要关联；
  当前状态和增量上下文读取同步迁移，不保留整张旧事件表只为适配旧读者。

## 7. 最终交付和退出条件

- 总空间下降不是硬性目标；独有且仍有用途的内容允许从 DB 迁入文件。
  验收重点是避免重复保存和保留无价值数据，不能将 DB 冗余转移到文件系统。
  正式原件、备份和演练中间文件均按该原则核对，并保留必要恢复点与真实未知。
- 提供逐表/字段处置清单、实际改动和保留理由；所有大正文路径均有明确存储归属。
- 同一历史集的真实业务身份和结果、顺序/分页、原件/附件、用量和权限核验一致；
  幂等由业务唯一 key 完成，无通用请求持久记录；旧未结或未知业务动作未被重放。
- 当前数据和旧备份均能按匹配版本恢复；文件 GC 不破坏任一保留恢复点。
- 报告主 DB、WAL/SHM、runner DB、唯一原件、备份/演练、总量与可测物理字节；
  分清已实测、估算和未知，并附同负载写入/API 对照。
- 新写入的增长率与新备份去重效果通过有界观察验证，避免完成一次清理后继续膨胀。
  记录每类原始输入字节、唯一原件字节、引用数量、DB/WAL 写入量与增长率；
  诊断使用紧凑指标和轮转日志，不再把每次采样的完整明细写回业务 DB。
- 实施集中独立审阅、完整检查、CI、受保护合入和完整发布集升级。
  本计划本身不触发生产清理、部署、已结束 Issue 重跑或任何 backlog 启动。

## 7.1 联合演练发现的派生正文边界

首次联合演练的文件净增不能直接称为必要原件。对已有登记原件匹配失败不等于
原 rollout 不存在；旧事件的 server 包装、普通业务返回和只为键序/空白保存的
重建规则均须重新判定，不能因旧 DB 字段可逐字回读便一律归档。

- provider 原文、用户/工具文本和真实未结动作输入保持原字节；已存在稳定原件时
  直接挂窗口引用。未找到原件时保留真实未知，不声称源文件不存在。
- server 派生事件只保存消费者需要的结构、序号、类型、状态和关系。长原文节点
  复用已有原件引用；展示层按语义组装 JSON，不为整个外壳另写原件或逐行拼接规则。
  字段类型、消费者需要的 null/缺省区别、事件身份、分页和 Unicode 文本仍保留；
  JSON 外壳的非合同键序和空白不作为独有业务事实。
- 已确认的普通工具返回从其实际业务事实或已有已发布工具原件读取。独有执行阶段
  内容与尚未确认的外部结果不能因看起来像接口返回而丢失。
- 先以代表样本及小回归核对消费者，再用最终源码重做同快照迁移及恢复核验；
  首次演练保留并标明已知冗余，不将其空间数字冒充最终收益。

## 8. 本轮实施与验收顺序

- 基线为上述主线提交，沿同一修复分支分原子提交；不为每个字段分别部署。
- S1/S2 先完成原件窗口/规则和工具、日志正文路径；只在核验后清除旧字段。
- S3 逐入口将普通请求幂等迁回业务 SoT，保留真实对象/动作身份，删除通用请求表。
- S4 统一类型化用量事实和查询投影，最新价目覆盖更新，保留真实归属和覆盖缺口。
- S5 迁移纯刷新通知与重复 inbox，保留业务事件、游标恢复及未结投递。
- S6/S7 补齐备份 preview/verify/prune 和 runner journal 的实际清单与回收路径。
- 迁移编号分配：119 原件与正文，120 用量，121 通知与小型冗余，122 业务幂等；
  如某项无需 schema 迁移则不生成空迁移，编号以最终已提交集合为准且不修改旧迁移。
- 根任务统一维护 D225、工程约定、CLI 能力目录、协议评估和集成；各实现报告具体边界。
- 在相同历史快照上验证业务状态、token、正文/Unicode/分页、幂等与未知操作，
  收敛后完成独立审阅、完整本地检查、CI、rebase 合入、format 2 fleet 升级。
- 先取得最终安装与迁移读取证明，再安排受控压缩与备份回收，报告所有存储范围的实测变化。
