# Server 重启时的 Run 覆盖

目标是让正常受控升级在账本保留已隔离的历史执行时完成 Server 切换。沿原 Run、Task、action、lease 和 journal 核对执行权，保持原工作区、槽位和未知操作的现有约束。

- 在排空后和签发替换授权前，按主机的接单及收尾 journal 核对开放 Run。未知执行需要原 lapsed lease、可辨认的 journal 归属或原窗口退出证明。缺身份、租约冲突及超协议窗口须继续拒绝。
- 对当前且依赖 Server 租约的 Run 保留固定维护覆盖和原租约的记账。固定执行权使用原协议语义。原维护控制已限制某个固定执行权时，以原确认的窗口计入预算。接单 runner 仍确认接单围栏，收尾 runner 的控制用于证明有执行权的旧进程不再接单。
- 用正常升级阶段与授权入口校验结果。旧发布的实际记录和测试预置数据分别标明。测试对照历史保留、活租约、确认不足、授权冲突、孤儿和协议窗口，并检查原身份、物理容量、工作区及结果对账。
- 验证首次迁入所用正式入口及真实效果。运行旧守卫的实例需要在独立授权和预检满足时使用已支持的受控恢复，或在原执行已通过正式流程自然收敛后正常升级。生产安装不在本次实施范围。

独立审阅补充两项实际边界。账本恢复 normal 后，runner 仍保存原本地 grant。下一次维护按已应用控制报告每条仍受限制的 Run 和保守截止。旧版本只报告最近 grant 的聚合截止，活固定执行用它作为保守上限，不能用新 grant 覆盖仍需对账的旧证据。首次外部恢复先关闭接单，确认 ACK 后排空旧活执行，保留门禁直到替换实际提交。隔离测试将用协议 6 runner 和排队工作验证这段门禁。

排空和授权之间仍会收到原 journal 的 Hello。切换准备就绪后，未纳入固定覆盖的 lapsed 协议 6 Run 保持原对账状态，待切换稳定后再按原身份处理。这段门禁避免在重启授权之后重新引入续租依赖。

第二轮复审补充连接续行。逐 Run 证据在心跳写入，随后同进程、同代、同 journal、同控制修订和授权身份的 Hello 可沿用证据，证据时间保留原心跳观测。旧 Server 的严格请求解码仍接收原 Hello 形状。续接新 Server 的 runner 可从成功心跳响应得知支持，并立刻回报现有本地截止。

第三轮复审补充维护前校验。发布会启用本地截止的接单围栏之前，按原 runner 的新鲜逐 Run 证据或兼容聚合证据核对固定执行的剩余预算。预算不足时保持原 normal 控制、Run 和 lease。签发替换授权前仍重新核对应用控制及截止。定向测试覆盖已过期、尚未过期但不足以重启、缺失或过期的逐 Run 证据，以及证据可用时重试成功。

第四轮复审补充维护确认期限。即将启用原固定截止的 primary runner 按最早原截止限制 `server_ready` 等待。在等待期间为正常恢复控制保留现有 runner 在线观察窗口，同时保留实际重启预算。首次停止授权必须在这个阶段有效期内签发。超时仍走既有 attention 与未改变主机控制恢复。已签发的原授权保留原绑定和回执对账。使用注入时钟复现 125 秒旧截止、120 秒重启预算及第 6 秒 ACK，覆盖旧聚合和逐 Run 证据，并验证原执行继续、已签授权不受等待期限误清理。

严格 CI 揭示两个执行器端到端夹具把服务端读回的逐 Run 观察原样作为 Claim 请求。使夹具与真实 runner 相同，在构造 Claim 时省略该字段。继续验证实际 CLI、执行器选择和接受流程，并保留接收端拒绝客户端提交服务端时间戳的契约。
