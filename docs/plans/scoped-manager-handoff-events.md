# 按候选 Issue 查询旧 manager 回执

runner.claim 在同一写事务内构造候选并分配 Run。首次领取一个从未分配过的 Issue，也会检查旧 owner 的物理执行、租约、投递及未应用事件。SQLite 可从 manager_native_events 开始扫描，再与此次候选和旧 epoch 关联。已消费的无关历史会增加独占写连接的时间。

1. 从本次候选 Issue 和其下一 assignment epoch 定位历史 manager Task，再按 Task 找原 Run，用 EXISTS 判定该 Run 是否仍有未应用事件。保留一个原 Run 对应一个 blocker，以及其他来源、输出身份和排序。
2. 追加单列索引，按 Issue 找各状态的历史 Task 并检查旧 epoch，以及按 Run 查找未应用事件。后者也供已有 manager 续派和回执查询使用。事件追加及应用仍由原事务维护，既有数据库由普通迁移建立索引。
3. 用真实迁移后的查询计划验证两次定点查找，避免以机器耗时作为测试门槛。验证同一 Run 有多个未应用事件时只报告一个 blocker，逐个确认到最后才解除，且其他 Issue、同代执行、已消费历史、原执行 unknown、未释放租约以及终态待确认仍按原事实处理。运行真实领取、停止交接及回执顺序检查。

任何未结回执继续由原执行对账。在确认最后一条后，下一次领取重新读取事务内事实，按现有 admission 和调度规则产生结果。
