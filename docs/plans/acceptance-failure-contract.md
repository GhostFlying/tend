# 验收失败与阻塞责任合同

Refs: D178

## 问题与边界

已执行的交付质量门失败不等于无法执行验收，也不要求验收者先证明某一产品缺陷才能交还诊断、返修责任。现有验收提示没有解释此边界，且 `blocked`、`inconclusive` 与验收执行器自身失败统一进入名为 `acceptance_env_unavailable` 的历史阻塞码，Web 又将该码直接描述为环境故障。

本计划只修可证明的通用机制。保留已提交 verdict、证据、Run、Task、原问题和责任历史，不读取自由文本猜测缺陷归因，不为一次现场问题改写状态或重派未知执行。主线实现仍由 Tend 承担。若负责 Agent 未消费原问题，先用原 source、logical turn、native receipt 证明首个断点，再独立追加该机制的最小修复；不移除 context-only 的业务写入限制。

## 实施顺序

1. 明确验收者合同：实际运行后不满足约定质量门应提交 `changes_required`，列出失败门和必要诊断；`blocked` 需要明确不可满足的外部前提，`inconclusive` 必须保留不确定性和后续调查责任。验收者仍不修改实现。
2. 本轮不新增结构化证据硬约束。新约束需要独立设计显式选择的版本、旧 server 对新字段的行为、能力协商与冻结 Run 合同，不能把可选字段被旧端忽略说成硬约束兼容。现有任意 Evidence JSON、已知与未知归因保持原样。
3. 历史阻塞码保持原值、原调度语义和重验收入口，用户文案改为中性“验收待处理”；详情继续呈现真实 verdict 与原证据。CLI 文本输出增加原验收 Evidence，保留真实阻塞码、verdict 和 Issues，不将未知归因为环境故障。新增阻塞与无结论的任务规则问题各自描述原判定，不从共用阻塞码猜测环境。
4. 通过现有责任 Attention、原 Task 的版本化合同修正及显式重验收入口承接后续，不新增自动重试，不扩大实现次数或绕过原 scope。验证验收失败返修在预算内自动生成下一代，预算耗尽保留唯一待决责任，阻塞与无结论也持续交原验收责任 Issue。
5. 若源码证明缺少现有执行入口，另列设计、CLI、CAS 与预算验证后再扩展；不先加入仅有文案而无动作的“诊断”选项。

## 兼容性

runner wire 保留现有 N / N−1；旧 verdict payload、旧任意 Evidence JSON、旧 journal 恢复和原 verdict 回放维持原行为，不追加必填条件、不收紧旧有效请求。现有 `acceptance_env_unavailable` 仅作为兼容性的待处理码，不能据此断言环境已损坏。无持久数据迁移，不重写历史事实，不为未知结果创造替代请求。验收提示编译于 runner；只有 server 部署不能使旧 runner 使用新提示，真实执行器更新须独立满足受控发布与原 journal 证明，不能由文案改动宣称现场已恢复。

## 验证与交付

- 回归覆盖实际输出与既有机制：CLI 不因 Issues 为空而隐藏 blocked/inconclusive 的原证据；不同 verdict 的任务规则问题不相互冒充；有效失败产生返修反馈，预算到限仍等负责人判断；旧 verdict 仍可提交并恢复。
- 验证原责任路由：验收问题归独立复核 Issue，并沿当前责任链交接，CAS、assignment epoch 和 owner 合同不被绕过。
- 所有重检查由唯一协调者按机器资源排期，使用现有 `make check`、`CHECK_JOBS=0`、`TEST_COUNT=1`；保留原失败日志，不以单例通过覆盖完整失败。
- 最终候选必须取得完整本地检查、仓库要求独立 review 和 required CI 后方可合入；部署沿原受控窗口及已有生产状态核验。部署完成后再让 Tend 沿当前原责任继续主线。
