# 测试重复性审计

关联 D172 的收益验收。若完整五 PR 周期不能证明净收益，进一步审计测试集合本身；本阶段交付具体候选及证据，不改变现有门禁或业务断言。

## 分析方法

1. 按当前构建配置枚举普通 Go 测试，单列 integration 测试；结合真实根耗时及本轮墙钟瓶颈，优先检查 App、API、sandbox、mainthread 和 E2E 的昂贵场景。
2. 通过 AST 查找完全相同的测试体、共享参数化场景、重复启动和建库。结构或函数覆盖相似只产生候选，不能直接证明断言冗余。
3. 逐项比较前置状态、业务操作、错误/成功分支、协议边界、持久化及重启语义、并发与故障注入。对跨层重复场景记录各层独有断言，避免删除唯一的线路或身份边界验证。
4. 将候选分为可合并的断言重复、可共享无副作用准备的成本重复，以及应保留的不同边界。列出具体源码位置、预期节省机制、保留的检出能力及尚缺的实验证据。
5. 需要删除或下移昂贵场景时，后续变更必须先核对保留测试能检出相关可复现故障，再在同候选、同预算下测量完整检查收益。本审计不修改生产 SQL，也不直接实施业务测试删减。

## 交付

在 findings 中保存源码版本、自动候选清单和人工核对结论。区分源码确认、历史成本提示和实际删减后的实测值；尚未实施的候选不宣称已经节省时间。远端固定回放继续，审计本身在另一台开发环境进行，避免增加测量机器的 CPU 负载。
