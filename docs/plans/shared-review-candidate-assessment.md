# rebase 后共享审阅的适用性判断

## 业务契约

已有正式审阅通过后，提供方可能观测到 rebase 产生的新 head 或 base。当前具名 Issue 负责人检查补丁、上游改动和冲突处理对原审阅范围的影响。确认仍适用时，通过原 `issues.review_delivery` 的 `assess` 操作提交理由，并使用读回的 review revision、head、base、候选代次及需求摘要。需要进一步核对时，用原 reviewer 的 `recheck`，继续真实审阅 Task。

适用性记录引用原通过轮次、当前候选和负责人的身份及指派代次。原审阅的候选、结论、reviewer、Task、Run 和独立检查证据保持历史原义。任意确认的后续 head/base 变化使该判断失效，即使提供方后来读回之前的 SHA。未知或待刷新时不能使用判断。相同候选的 CI 或观察刷新不会消耗判断。既有不携带候选的同候选评估继续读取和使用。

`prepare` 及后续授权读取和执行检查使用相同的共享审阅适用性规则。独立审阅资格、真实候选和目标、CI、合入授权及部署约束继续通过各自原入口核验。提供方事实未知时等候原观察，CAS 或候选不匹配时读取新快照再判断。

## 实施和验证

1. 在共享提供方事实中记录 head/base 的候选代次，复用已存在的事实写入事务。共享审阅读取返回当前候选及需求摘要。
2. 在原 `assess` 事务中校验责任、review revision、候选和需求，保存对原轮次的适用性记录。从有效性投影和交付授权读取采用同一候选匹配规则。
3. 使用现有 App 夹具替代 GitHub 观察，由正式的 link/start/record 建立通过结论。验证通过正常交付 prepare 和授权读路径继续，覆盖候选变动及恢复到旧 SHA、错误候选、未知观察、CI 未就绪及聚焦复核。更新 CLI 帮助和契约验证，并对 PR 候选执行独立审阅。
