# 原生主管事件传输与归档解耦

## 问题与范围

原生日志返回真实路径，配置目录使用同一目录的别名时，读取器的文字包含检查
错误拒绝原件。主管工具回调与原生事件又先同步归档，再进入本地 journal；归档
错误因此阻断业务工具。事件转发遇错静默退出，主管循环仍存活，最终完成事实未
回传，界面持续显示运行。此次集中修复这三个原因，不混入 Issue 工作状态展示。

## 实施

1. **P1 路径身份**：共享 rollout 读取入口识别配置目录与原生目录的真实身份，
   保持根目录约束、原生 session 身份核验和符号链接越界拒绝。覆盖双向目录别名、
   缺文件及目录外文件，不能通过放宽任意绝对路径解决。
2. **P2 独立传输**：主管事件先按原顺序可靠保存，再投递；业务工具、完成事件和
   worker 生命周期不以 rollout 归档成功为前提。归档沿现有不可变原件及原请求/
   水位恢复，独立有界处理和记录错误，不新增模型回合或重放业务操作。正常归档
   可用时继续使用原件索引；暂存的必要事件证据不得伪装成归档已完整。
3. **P3 故障生命周期**：本地事件持久化或转发的真实故障必须反馈主管循环，日志
   记录 Run、thread、事件及失败阶段和原错误，不能用一个通用文本隐藏原因并
   留下无事件消费者的空主管。已保存事件沿原序号恢复；未知原生命令不自动重放。
4. **P4 恢复与验收**：原 Task/Issue/native 身份不更换，不补造历史执行。先核对
   原生完成事实，再恢复原责任，通过 Tend chat 告知维护结果。原有配置、身份、
   模型、思考强度、slot 与并发组保持。

## 验证与交付

- 故障回归先证明旧代码失败：配置根别名与真实路径；归档拒绝/超时仍能使用工具
  并交付完成事件；原生事件持久化失败能被主管观察，保留原事件恢复身份。
- 正常归档、未知上传回执、断线/重启、重复投递和已完成 turn 对账不得退化；不因
  归档恢复重跑业务 turn。目录外与越界符号链接仍拒绝。
- 源码收敛后独立审阅、完整本地检查、最终候选 CI，统一 PR 合入及 format 2 完整
  发布集升级。核对真实节点、未结束执行与受控升级原身份，部署后验证实际进程和
  配置，再让 Tend 自行继续主线。监控与修复为不同责任，定时观察不终止维护。

## 独立审阅修正

- 归档队列仅在完整遍历分页后回绕，持续产生日志的前序 Run 不得饿死后续 Run。
- 同一 Run 的原件分别尝试；缺失原件保留错误与待归档状态，不阻挡其余可用原件。
- 未登记任何原生来源的执行沿用跳过归档的行为；已登记来源而原件不可读则仍待补齐。
- 每事件的归档脏标记通过 Run 前缀索引查询，追加 journal 27 迁移，保留已提交的
  journal 26；验证实际 SQLite 查询计划及历史 journal 升级。
