# Issue 看板按执行事实分列

1. 保留工作状态、领取条件和手动状态命令。为看板读接口加入按执行事实分列的视图。用同一份投影计算列计数和分页，沿用根 Issue、项目、负责人和「等我处理」筛选。
2. 沿 #352 的负责人 Run 归属、普通任务和审阅 Run 的责任记录，核对实际开始、当前运行、外部等待和物理停止。并行活动优先进入 WIP。使用现有排队事实和待答决定，缺少新证据时保留最近可证明的列，清理失效提示。
3. Web 添加五列并沿用既有列内分页和状态菜单。拖到 Waiting 只用于开放领取；业务等待由事实产生。同步 CLI 的只读列筛选，保留原工作状态查询。
4. 通过真实领取、启动、登记 CI 等待、物理停止、检查完成与同一负责人再次启动验证列变化。覆盖并行、人工决定、停机未知、终态、分页和过滤。针对 #372 做组合检查，覆盖 PR 关联和操作入口。

## 并行 Run 审阅修正

登记领取和实际开始提供不同的证据。仅领取的 Run 保留已经生效的等待提示。使用实际开始和物理停止形成的时间范围判断等待是否曾生效：如果另一 Run 停止时 CI 仍未结束，随后清除 CI 提示时保留 Waiting，直到后继 Run 实际开始。对比 CI 先结束的场景，沿同一业务路径覆盖两种顺序。用原等待、provider 观察和 lease 回执计算这一投影。

提供方可能重复读取 CI 终态或连续更换 PR head。新登记的 checks 等待在原账本记录所见候选，由同一事务保存首个使它失效的实际提供方事实。后续读取、换 head、CI 重跑和原等待的更新保留这条证据。字段供看板读取，沿用原停止、唤醒和调度规则。旧等待缺少这段历史时，仍按当前明确观察展示提示。时间戳相同且缺少可核对先后时，保留已证实的列。回归覆盖原终态重读、部分结果、开始后续 CI 周期、连续换 head 和换回原 head。
