# 收尾回执与同机 runner 启动授权

完整发布集升级已经确认 server 切换，但旧 runner 的 journal 中仍有已停止负责人 Run 的原始 native 回复。启动授权把这类回复计入全部待处理操作，候选无法启动，该主机的新工作也无法恢复。目标是候选完成现有的健康确认和持久提交后领取无关 Run，同时允许前驱保持原身份对账，最终按原有条件退役。

1. 沿现有 `runner.rolling_authorize` 入口判断原监督进程、目标构建、批次阶段、心跳新鲜度、维护版本和 claim 围栏。普通零待处理路径保留。需要区分旧 runner 的待处理操作时，返回当前已接受的前驱心跳序号和待处理数量；旧调用方仍可读取原授权字段。
2. 由当前监督器给哈希固定的候选授权工具传入前驱 journal 标识。工具以 SQLite 只读连接，在一个快照中核对已持久应用的本次维护版本，并检查现有表的完整待处理集合。仅在集合全部是本地已确认退出的 `manager.native_reply` 时提交原 Run、lease 和命令标识与心跳序号。候选不启动前驱代码，不取得其 writer 锁，原正文和本机路径不经 RPC 传输。该路径沿用侧路连通性和主机凭据。
3. Server 在原授权事务中重核最新前驱观测、数量、版本及 Run/lease/journal 归属。只接纳已结束、已释放 lease 且有当前物理停止证据的负责人 Run 原 `close` 或 `tool_result` 回复。读不到证明、存在未确认 claim、工作区释放／清理、未分类操作或不匹配时继续等待。已有 scope、工作区占用、关闭后的事实入口和同机容量检查约束两代的后续操作；维护应答后前驱不能创建新 claim 或 cleanup reservation。已发生的回执提交不改变旧业务身份和 unknown。
4. 后继注册、健康、持久 commit 后才开放领取。旧代退役继续要求实际退出、原有 ready 条件和完整待处理清点。超时前等后继安装授权或回执在原代自动恢复；现有批次、停止和原回执对账入口继续有效。
5. 验证历史协议 6 和当前协议 7，包含旧调用方未提交证明、真实只读日志采集、陈旧观测与隔离证明、受保护的候选领取、原凭据晚到回复与退役。使用独立日志和临时账本；测试标出夹具预置与实际命令。使用现有协议窗口与旧 journal 表，无需迁移。只在收到支持证明的响应后添加可选请求字段，因此可与旧服务端回退到原路径。

## 已接单的负责人 Run 轮询

已登记独立 journal 的前驱可以持有已领取的负责人 Run。原生进程的空轮询可能持续写入和删除 `manager.native_claim`，即使 server 已确认不再允许该实例领取新 Run。前驱只持有本次已分配的 Run/lease，领取原生命令按原 Run 校验，独立候选无权接手它。仍处于 starting 的旧版负责人 Run 可以处于此轮询状态，其执行分支无工作区准备。

只读快照可把该轮询与已停止 Run 的回复一起识别。服务端重核非空 journal、原 lease 有效、Run 为具有原负责人绑定的活跃执行、无工作区绑定，并且原 Run 当前无排队、已开始或 unknown 的原生命令。留在快照之后新增的命令仍由原 lease 与 Run 围栏约束。快照全量校验本机请求和其他队列。若原轮询已经收到回执，导致请求数量与当前心跳不符，等待下一次观测再尝试同一启动授权。无 journal 标识的旧接单代继续沿原 starting 工作区保护及回执证明规则。实际 `runner.claim`、未识别类型或工作区准备仍阻止启动。

验收补充已登记 journal 的协议 6 前驱。其负责人 Run 真实领取后保持 starting，以原凭据执行空轮询，候选完成提交后领取无关工作，原 Run/lease 仍只在前驱可用并占用物理槽位；相关证明无法用于其他 lease 或未知原生命令。退役继续等待该 Run 结束、待处理队列排空和实际退出确认。
