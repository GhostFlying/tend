# 问题沿 Issue 责任链处理（D150）

## 目标与授权

Issue owner 是唯一责任主体；独立委派的工作通过子 Issue 承担责任，Task/Run 只是该责任下的执行记录，不引入独立 worker 管理链。执行中产生的问题回到当前 Issue owner。负责 Agent 可以在既有目标和约束内处理原问题；处理不了时显式向当前 Issue 的父级负责人提交。遇到人工 owner，或顶层协调 Agent 明确无法解决后，才形成用户待办。任务额度耗尽、执行失败、验收环境问题和 worker 提问共用原问题身份，不因事件类型直接要求用户介入。

## 实施批次

1. R1：在原 Attention/Decision 之上追加持久责任路由，记录来源 Issue、当前接收责任、assignment epoch、版本及逐跳原因/处理事实。已有未结 canonical 问题按真实责任接续，历史原文和原回执不改写；交接、重挂载、终态及旧执行继续受围栏约束。
2. R2：Agent 具名工具增加责任问题读取、回答和逐级上报。权限由当前责任与执行 identity/epoch 校验，父负责人仅能处理明确上报的原问题，不获得任意子任务编辑权。回答沿原 Decision effects/执行答复，不伪造用户消息；上报不转移 Issue 归属、不重新执行 unknown、不新建任务逃避次数限制。
3. R3：自动问题先路由到本次执行或任务的具体 Issue owner；Agent 主动提交的问题路由给上级。根 Issue 上报给唯一主协调 Agent；主协调继续不能解决才转用户。用户直接控制仍可用。Agent 待处理问题不生成用户 Inbox、渠道交互或提醒；问题解决及交接沿原 outbox/background batch 唤醒责任方。
4. R4：同步 owner API、完整 CLI（分页/筛选、原问题读取、CAS/epoch、回答/上报原因、dry-run/replay、帮助和能力目录）及生成类型。保持现有页面布局，既有详情可查看原问题和处理结果。
5. R5：验证多层 Agent→Agent→人工、根协调、同 Agent 不同责任、人工中间层、正常补证据返工、权限负控、重放/并发、交接/重挂载/取消、真实 Inbox/通信静默及升级后的历史待决接续。冻结后完成 make check、独立规定 CLI review、PR CI 和交叉编译，再依原受控发布流程部署。

## 边界

不将内部问题回答冒充用户授权。超出既有目标、外部授权、人工操作和无法确认结果的问题继续沿链上报；不得通过无限上报、创建后继问题或 task spec 刷新重置预算来制造无限自循环。独立验收仍判断交付物，负责人不能自行通过验收。

Runner 既有提问请求、稳定 question_key 和答复读取保留。新增 supervisor-questions-v1 能力及可选分配字段，并在 run 创建时持久冻结：只有明确协商的新 run 接受 Agent 答复；历史 run 仍需真实用户答复，问题也沿责任链逐级上报，不直接通知人工。此为可选能力协商，不改变旧协议请求/响应及默认语义，wire 仍为 2/1。新增 owner/Agent 入口不授予 runner 调度权限。机器细节、发布证据与操作记录仅放 .local。


交接与容量合同：新执行按 `issue-question-handoffs-v1` 冻结分轮交接能力。提问持久保存原问题并由 runner 确认真正停止后结束本轮、释放 slot；代表 Issue owner 的执行自动提交父 Issue owner，根 Issue 提交唯一主协调 Agent。答复与退出确认均持久后才创建接续 Action/Run，沿用原 spec、artifact 和 generation，不消耗实现尝试额度，不复活旧 Run。固定原主机、执行配置和 workspace 互斥；可恢复的实现会话保留原生 thread，验收与不支持原生接续的适配器通过原问题及完整合同重建上下文。协调与执行均严格使用配置容量，不提供额外名额。新合同仅向明确协商的执行启用，历史 Run 保留原等待合同并受控排空；wire 仍为 2/1。详见 docs/plans/issue-run-handoffs.md。Agent 决策和行动完成不能用作真实人工授权证据。

问题内容修改时同步推进责任版本并补发当前问题的答复入口；阅读、归档不造成业务版本变更。内部接管造成的人工控件停用与原问题改版造成的永久替代分开保存，同一原问题再次逐级上报给人工时恢复原控件。历史复核问题按运行责任及冻结的 review Issue 合同接续，不把旧 Attention 的实施 Issue 链接当成复核责任；历史问答正文和引用保持不变。

最终复核补充：责任快照冻结当前祖先链，任何重挂造成的链变化都推进路由版本并重新交由当前路径中最早变化的已达责任判断，不能借仍存在的共同祖先跳过新上级。撤回/取消问题同样唤醒来源 Issue。责任对账在同一事务同步已发布渠道卡片；内部路由仅禁用未决问题的人工控件，已回答/撤回结果仍读取原业务事实并展示实际处理记录。

答复返回继续使用责任来源而非历史展示链接：旧复核问题保留实施 Issue 的原 Attention 引用时，真实答复仍唤醒冻结的复核 Issue。人工负责的行动完成后恢复原主协调回访，不因不存在 Agent owner 而丢失完成通知。

责任祖先快照同时冻结各层 assignment epoch：中途任何上级 Agent 改派都会推进原路由版本，不能沿前任上报继续绕过新负责人。负责人按其原主机和执行配置正常领取；来源执行先让出容量，不要求来源与上级在同一主机。

与子 Issue 进展投影合并时，Web 预览和 CLI 子项摘要同步显示 waiting_supervisor；该状态参与问题优先展示，但不成为用户待办。

旧 runner 不被赋予未实现的交接能力；发布先确认历史活跃执行排空或按原合同完成对账。零容量主机始终不接单。

旧合同容量对账：若所有实际配置槽位都由不能交接的旧问答占用，且当前接收负责人也固定在同一主机，系统记录该容量阻塞并沿原父链提交给可接手的上级或托管主协调。遇到人工 owner 仍停在该层；原问题、旧答复合同及槽位事实保持不变，主协调无法处理时才形成用户待办。等待交接的原执行快照继续参与保留交换，库存移除不使原合同失去接续配置。
