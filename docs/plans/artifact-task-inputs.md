# 交付文件作为后续任务输入（D93）

## 目标与边界

后续任务在独立 worktree 或 temporary 工作区中，能通过显式 `spec.inputs`
读取前序任务已经提交的原始交付文件；实现和独立验收获得相同版本的输入。
调度 Agent 从任务与 artifact 清单选择必要文件，用户不用重复上传或提供文件 ID。
关联关系不自动复制文件，也不赋予 workspace 复用权限。

当前单 owner 的规划工具本来可以读取全部 finalized 交付。沿用这个信任模型：
精确 file_id 就是规划者的选择，不额外要求关系、同工作项或通过验收作为读取条件。
验收失败的报告也可能是合法调查输入；可读取不表示认可内容或扩大后续执行授权。
未提交的上传不作为后续输入。

## 实施

1. 保留现有 `spec.inputs: [{file_id}]` 调用。附件查找未命中时解析已提交 artifact
   的文件成员，核对 task/run/name/size/hash；冻结原件身份与来源 task/artifact。
   来源从存储解析，不信任调用方自报 metadata。不复制 blob、不伪造聊天附件。
2. 来源和 metadata 一起保存在已有不可变 task spec JSON，沿用请求去重、事务和
   spec revision。无新增来源表、迁移、导入工具、权限池或来源摘要。
   已冻结输入保持原值；删除只影响新版本；旧 run 不获得新 spec 的输入。
3. 来源字段仅供规划与任务读取，workerSpec 去除这些新增字段后再下发，保持
   task-inputs-v1 runner wire 不变。沿用已有流式下载、哈希校验和两角色输入范围。
   本次不变更 server/runner 协议版本。
4. 更新外挂与托管调度说明、工具 schema/描述和输入文案：确定来源时直接选择
   必要子集；绑定失败修正请求或报告平台问题，不删除 inputs 改写成文字，也不
   把“允许使用同一文件”当作修复；真正来源或用户意图不明才提问。
5. 更新 D93 设计；运行 targeted tests、完整 make check、独立 review 和 CI，
   通过线性 PR 合入并按既有升级流程部署。保留任务、会话与原件，核验工具交接。

## 验证

- 原 bug 回归：提交原文件后，另一个工作项的 temporary 任务只传 file_id 即可
  创建，实现和验收各自下载得到完全相同原始字节；无需源工作区。
- 未提交上传、未知 ID、重复 ID 拒绝且无部分任务/计划/action 写入；调用方伪造
  metadata/provenance 被真实存储值替换。
- 无显式 inputs 的 follow-up 无文件继承；未绑定的文件下载仍拒绝。
- 输入增加、删除、请求重放、相同 ID 无变化、旧 spec 下载范围及历史冻结验证。
- 未验收/失败后的 finalized 文件仍可作为调查输入，来源结论不伪造为通过。
- 旧 runner wire 不新增字段，投影不修改原 spec；现有附件和完整 GIF 原件回归。
- 发布后用真实设计交付验证输入解析；原取消的预览任务保持取消，另起关联任务。
  新预览仍须独立验证页面、资源和实施退出后的服务存活。

## 暂不纳入

不热扩权运行中的任务，不增加自动读取所有父任务文件的行为，不新建技术故障
上报协议或额外 owner 确认流程。本次输入绑定修复不需要这些扩展。
