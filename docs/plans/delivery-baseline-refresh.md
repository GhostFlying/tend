# 部署基线变化后的共享交付刷新

状态：实现及聚焦验证完成，待统一交付门禁。Refs: D185、D190。

## 已确认问题

已合入 PR 的成功观察会停止周期轮询，将共享 provider job 的下次时间置为无限远。普通升级完成或取消后，部署基线变化会使相关 Issue 的原观察失效，并设置本地 refresh pending；当前路径没有同时唤醒共享 job，因此 server 无法领取该刷新，交付执行会一直等待旧基线观察。

## 最小实现

1. 从正式 `issues.refresh_delivery` 提取同事务的观察排队 helper，保留原请求/CAS入口。server 模式同时把共享 job 排为当前可领取、重置有限失败预算、递增刷新顺序并绑定成员；旧 runner 查询仍按原身份保留，generation/nonce 使旧结果不能结算新刷新。
2. 完成及取消升级的基线失效路径复用同一 helper。对受影响 Issue/delivery 去重，不新建 timer、模型唤醒、provider 调用或部署工作流，不使已合入 PR 恢复永久轮询。
3. 不更改任何审阅结果、交付批准、安装证据或冻结执行；读取未知/失败仍保留原事实。事务失败全部回滚，旧协议请求和默认 runner 路径保持兼容。

## 验证

先建立实际 RED：成功 merged 观察已停共享 job，真实升级完成或取消后不人工刷新，server 仍应能领取新基线查询。GREEN 进一步核对结果落新基线并清 pending，随后不再轮询。

覆盖基线变化时旧查询在途：晚到旧结果不能清掉新 pending，也不能以旧共享缓存替代新的读；覆盖多个 Issue 引用同一 PR及同一 Issue 多个交付责任，只需一次共享外部查询、每个成员的原事实与刷新版本保持。复用现有正式刷新、限次失败、旧 runner nonce 和升级相关聚焦回归。本轮聚焦验证不作生产故障演练；合入前由交付协调者统一执行最终候选完整 `make check`、独立 review 和必需 CI。

实际回归通过真实完成/取消升级事务复现了 pending 无可领取查询，以及同 Issue 多责任的重复代次失效；修复后四个场景均通过。受影响的共享观察、授权读面和交付并发 29 个根用例 race 通过；旧 runner nonce、终态显式刷新及公平排队另外三个根用例 race 通过，`go vet` 及差异空白检查通过。完整检查、独立审阅、CI 和实际发布由交付协调者继续完成。
