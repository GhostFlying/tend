# CI 并行检查与共享空库夹具

Refs: D130、D145。

## 现状与目标

最近成功的 CI #512 与 #513 分别用时约 36 与 52 分钟。单个 `check` job 串行执行静态检查、其他 Go 包、E2E、App 分片、Web 检查、浏览器回归与交叉编译。#513 的其他 Go 包阶段约 24 分钟，其中 mainthread 和 API 分别报告约 22 与 20 分钟；E2E 约 8 分钟，App 最长分片约 8 分钟，后续 Web/浏览器约 9 分钟。Go/pnpm 均命中缓存。同一基础源码的旧工作流 #515 随后成功，用时 34 分 57 秒；mainthread 为 819 秒、API 为 749 秒，E2E 为 283 秒，App 最长分片为 301 秒。

本次保留全部现有检查及 race、传输隔离和独立用例数据。目标是同时缩短关键路径和重复迁移的计算量，以实际 PR CI 度量，不把本地样本当作远端承诺。

## 实施顺序

1. 留存当前工作流步骤时间与日志，测量 API 简单用例的 race 基线，确认真实迁移热点。
2. 将 D130 的空库模板实现提取到独立测试辅助子包，App、API 和 mainthread 的通用新库夹具复用。模板通过真实迁移建立、关闭并检查 WAL 后保存只读字节，每个夹具复制到新的独立文件后仍走正常 `store.Open`。迁移、历史和重开库测试保留原入口，不改生产存储实现。
3. racecheck 增加互斥且完备的包分组，CI 分别使用 App（保留四分片）、API、mainthread、E2E 和其余包的独立 runner。默认本地全量入口保留原有顺序与失败传播。新增包自动进入其余组。
4. 静态检查、完整 Go race 分组、Web 检查及全部浏览器回归并行；交叉编译仍在 Web 构建后执行，以包含真实 Web 产物。保留名为 `check` 的最终汇总门禁，任何依赖失败、取消或跳过都不通过；仅同一 PR 的旧候选自动取消，main 检查不自动取消。
5. 继续使用已有 Go/pnpm 缓存与统一 `make check` 本地入口。各 job 的编译和安装开销纳入实际 CI 收益评估。

## 验证与交付

- 验证模板 schema/迁移记录、完整性、外键、并发副本写入与原文件隔离，以及已有路径不会被覆盖。
- 验证每个包只属于一个 CI 组，App 每个测试根仍只覆盖一次；未识别分组立即失败。
- 对比同一用例优化前后的 race 样本；最终候选执行一次完整 `APP_TEST_SHARDS=4 make check`、交叉编译及规定独立 review。
- PR CI 保留所有浏览器命令，核实所有分组与汇总门禁结果，记录远端总时间、最长 job 和计算资源代价。候选未通过前不宣称提速完成。
