# 独立 Tend 自维护服务

状态：部署前交付。源码、最终候选检查、独立 review、CI 与发布结果在对应 PR 中分别记录；本批不启用生产服务和定时器。

## 已确认的目标

- 独立程序监测 Tend，事件唤醒并每五分钟补查；系统定时器每六十分钟启动一次有界 Agent 检查，等待不调用模型。
- 任何时刻仅有一个活跃维护会话。新问题、审计和补充线索合并交给它，原生启动或中断结果未知时先对账。
- 后端由外部配置，支持 Codex 与 TraeX，不检测额度或自动切换。配置可以等待当前执行安全退出后采用，或中止当前执行后采用；均不要求业务系统进入维护模式。
- 仅中止后向后继 Agent 提供前一个 Agent 及 session ID 或 rollout 路径。其余读取交给 Agent 普通工具，不注入专用工具，也不复制旧会话正文。
- 正常检查只给身份、触发原因、问题和证据索引及已有读取方法。实际维修沿当前会话推进，修复后验证原工作恢复。
- 漏报属于维护范围：修复业务阻塞后补检测与正常等待对照回归。维护器失败不阻断业务。
- 用量面板接入不属于首版；原生记录与会话身份保留。原生 App/TUI 是观察与人工交互入口，Web 仅展示维护状态。
- 明确配置的维护范围内自动验证、合入和受控更新；新增范围及破坏性接管保留现有授权边界。

## 实施顺序

1. M1：验证已有 app-server 连接，增加独立配置、持久状态、单执行身份及检测/调度；提供进程入口和完整 CLI。
2. M2：接入 Codex/TraeX 原生会话、人工观察、索引式输入、外部配置切换及中止交接；验证服务重启不重发输入或停止共享 daemon。
3. M3：完成事件与五分钟补查、小时独立审计、误报/等待反馈及真实故障回放；增加只读状态视图。
4. M4：复用完整发布与 updater 自更新工作，增加独立维护组件包、Actions 构建/发布与 updater 受管角色；更新维护器前持久交接，重启后核对原执行再继续。
5. M5：聚焦验证、真实原生协议/界面验收、最终完整检查、独立 review、CI、最新主线集成与不可变产物；准备配置和 service/timer 模板但不启用。

## 运行与接口

维护器使用独立状态库，不直接读写 Tend 业务数据库。读取现有 owner API 和事件，使用最小必要事实；事件重连先补查，不跨部署复用游标。故障状态、采集失败和正常等待分别表达。

新增 `tend-maintainer serve|audit`，本机私有控制 socket 提供状态、问题、检查、审计、暂停/恢复、延期、配置采用、对账和更新。`tend maintenance` 覆盖完整输入输出、JSON、分页、request ID、修订、原请求恢复及帮助，并登记能力目录。

全局执行记录先于原生副作用持久化。后台服务和独立 audit 共用此记录；到期、断线和进程退出不证明原生会话结束。实际 UI 连接共享原生会话，服务退出只断开自己的连接。独立 review 由程序在主维修回合结束后串行执行。

后端配置修改先记录目标版本；when-idle 等当前执行结束，interrupt 中止并观察原执行终态后切换。只有 interrupt 保存并传递前一个原生执行的定位；正常退出后的新会话不获得该交接字段。未确认的业务操作仍保留原事实，后继自行核对。

## 发布与更新

依赖完整发布与普通 updater 自更新的最终实现，不另建竞争自更新流程。维护器作为同一提交、同一 GitHub Release 的独立 Linux amd64/arm64 组件包构建和发布；现有四组件主安装包及 service manifest 保持。

组件清单记录源码提交、平台、大小/hash 和独立状态格式兼容范围。updater 添加维护器角色及健康/准入接点。普通更新先交接 updater，再更新业务服务，最后更新维护服务；每一项均核对实际进程与持久收据。自身更新保存原会话及待办，不终止共享 daemon。

## 验收

- 无变化无模型调用，五分钟与六十分钟调度符合配置；新问题和定期审计不会产生第二个活跃维护会话。
- 重启、丢回执、断线、重复输入、中断与配置变更保留原身份；中止交接只有定位字段，无额外工具。
- 正常长检查、等待 CI、显式暂停不重复告警；真实失败、恢复耗尽、启动无进展及修复后旧阻塞可被发现。
- Codex App/CLI 和 TraeX TUI 进入同一原生 thread；读取/人工输入/退出边界及后台继续分别验收。
- 真实故障和健康对照使用确定性 fixture；集成验证使用隔离目录，不改生产服务和个人全局配置。
- 发布包完整性、两种架构、源码身份、损坏与缺失拒绝、重跑和中断恢复；updater 自更新、业务更新、维护器自身更新分别取证。
- 完整 `make check` 使用自动 CPU 预算；独立 review、required CI 覆盖最终候选。发布不等于安装，不启用生产服务或定时器。

## 已实现的边界

- 独立 SQLite 状态与请求原文/收据；历史会话独立分页，日常状态不重写全历史。
- 程序检测与事件补查、单次 audit、单原生 thread、串行原生 review、外部配置采用和中止索引交接。
- owner 只读概览、完整本机 CLI、组件发布和维护器 updater 角色；候选读取不可逆提交收据后恢复调度。
- 使用本机 Codex 与 TraeX 的隔离 app-server 和确定性本地 provider，验证原输入身份、同会话 TUI 展示/人工输入、实际中断后 idle 与 inline review；这些证据不等于生产 App 或服务部署验收。
- 普通 updater 自更新依赖 [PR #280](https://github.com/GhostFlying/tend/pull/280) 交付；集成时将 `maintainer` 纳入其固定角色准入，并覆盖保留子进程与独占锁收据。不以强制恢复或手动覆盖替代，部署前完成接口和实际服务安装的联合验收。

## 独立评审后的恢复修正

1. 持久化创建时解析后的原生 sandbox，并区分首条输入前的元数据读取、空闲时取历史和未知输入对账。服务重启后仍可向原空会话发送首条输入；不重置已提交或结果未知的输入。
2. daemon 重启后的 resume 显式采用该会话固定的后端配置，保留返回的 sandbox；每回合沿已解析权限施加配置中的网络和额外写目录。
3. 更新入口区分明确拒绝和传输结果未知。明确拒绝回到可操作状态，保留原计划和请求身份；未知提交仅查询原操作，不重新发送。
4. 原更新操作被正常监督重启替换后，按原终态收据、已提交证明和当前实际进程核对更新结果，不依赖可变的当前 operation ID。
5. review 结束时即使有待采用后端，也保留读取 review 结果、修复和交付的后续待办；只有确认中止才传递前会话索引。

上述场景各补故障回归，原生恢复同时通过隔离 Codex 与 TraeX daemon 验证，再完成最终完整检查及复评。

复评补充：查询 updater 前释放维护器锁，响应后核对原计划及阶段；补齐保留回滚证明的恢复。首条输入前缓存连接损坏时丢弃该连接，后续仍连接原会话。独立 audit 按修订推进有限状态转换，直至已提交或并入执行中的检查，不假设固定三步足够；无进展即返回，不以模型等待循环代替程序调度。

失败状态补充：未知创建即使尚无输入也保留对账围栏，配置变更不证明原创建结束。失败或非请求中断保留原 turn、输入和触发索引，历史明确记录失败；检测不自动重试模型，新的 audit、resume 或配置采用才允许新尝试。持久化故障通过只读状态直接报告，并记录日志退出交给进程监督恢复，不尝试再写一条故障状态。
