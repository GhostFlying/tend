# 升级窗口、及时推进与停机诊断

Refs: D235。承接 D234 已交付的授权与安装证明修复，只处理真实普通升级仍会遇到的剩余问题。

## 业务起点与终点

普通完整发布集升级已经获准，但 runner 维护覆盖先消耗了安装预算，server 的只读长轮询又不随停机结束；多轮控制/心跳等待及缺失首因使故障难以解释。目标是同一批次在原固定期限内完成停止、备份、候选健康确认与恢复正常，或保留准确拒绝/unknown供原身份对账。现有事务、租约、真实drain、独立健康样本与安装回执不因提速而省略。

## 实施

1. **预算**：区分 runner 维护覆盖与 server 安装授权。为新批次按安装预算加重启预留建立覆盖，使用保守的实际确认截止裁剪安装授权；不修改任何已发授权或整体期限，不新增授权类型。覆盖握手消耗时间、备份耗时和整体期限裁剪。
2. **停机**：server 生命周期结束时仅结束 claim、消息/问题/日志等可重读长等待和事件流；在途业务写入及原文件传输仍按原请求安全收敛。停止接入、HTTP排空、后台结束与存储关闭分段记录。
3. **诊断**：现有轮转日志记录有限活跃请求快照，使用规范化路由、方法、请求类别、关联身份、开始/耗时及取消原因；不输出URL参数、正文或凭据，不建立永久请求账本。自更新明确拒绝在现有私有拒绝凭据旁保留首次诊断，响应丢失/重启后可读；历史未知不重建。日志区分保留的历史错误与当前终态，日志失败不成为新的业务成功条件。
4. **及时推进**：沿现有变更通知/runner心跳循环唤醒有真实状态变化的观察与ACK，避免机械等待下一轮周期。去重/合并唤醒，不自激循环、不并发执行控制步骤、不延长租约；周期检查继续作为兜底。

## 验收与交付

先保存故障回归，再实现。真实HTTP验证只读长等待能在停机时结束，同时在途写入/原件不被截断；诊断能定位仍在等待的规范化路由且不泄露输入。正常App路径验证覆盖与安装预算、原授权不续期和整体期限裁剪；验证取消、错误身份及unknown不重复副作用。即时通知测试须证明进度发生在周期之前且不会忙循环。

最终候选独立全PR审阅、一次完整 `make check TEST_COUNT=1 CHECK_JOBS=0`、自然触发CI和保护检查通过后rebase合入。按用户已授权部署该确定源码的完整format 2发布集，核对真实进程/回执/正常ACK和配置保持，并保存本次阶段耗时；源码验证与真实安装分开记录。本次由外部维护者直接完成，不向Tend创建或派发执行Task。

## 独立审阅后的收敛

原审阅发现即时失败的下载会被进度心跳反向触发，形成无间隔重试。进度报告与下载执行分别处理：同一控制版本失败后仍遵守原RetryDelay，已提交或已核实的同一尝试仅观察；新控制版本可重新评估，未知安装继续沿原身份核实。回归使用真实HTTP503，证明失败能及时上报且不会因ACK重复下载。

过期回归按原记录中的实际阶段截止推进时钟，保留不续期、错误身份与取消断言。首次拒绝诊断放在既有凭据旁的可选诊断文件；旧监督器仍能严格读取原format1凭据，诊断写入或读取失败不影响真实拒绝证明，缺失原因仍为unknown。
