# 已完成交付的历史结清

Refs: D192。修改前记录实施范围；历史结清不产生新的执行许可。

## 问题与目标

已批准的交付执行完成受控部署后，后续独立维护会推进 provider target 与部署基线。
现有候选失效逻辑同时改变交付 duty 状态和版本；原执行之后取得独立验收时，
`complete` 仍要求它匹配当前候选，导致真实完成的历史交付无法结清。

以原执行冻结合同、真实执行和验收结果、绑定升级及安装回执结清原责任。
当前候选的授权继续只用于尚未发生的合入、部署及新执行。

## 实施

1. 复现已批准部署完成、另一维护推进 target/baseline、原执行随后验收通过的完整
   状态转移。确认真实托管工具回调和正式写入使用同一判定，不增加一次性解除标记。
2. 将历史结清校验与当前执行准入分开。读取并验证原 execution 对 Issue、原责任、
   Task/spec、candidate、授权及原升级的不可变绑定；读取真实完成及独立验收证据。
   不从后续候选、最新安装或 caller 提供的 passed 标记推断历史完成。
3. 原 PR 身份未变而只有后续维护或 provider target / 基线推进时，不自动改写已绑定执行的 duty 状态、版本或原批准问题；复用原观察的合并通知，由当前负责人判断剩余工作及授权适用性。新副作用仍核对其真实执行参数与当前安装并发事实，不从漂移机械推导必须重新人工批准。兼容已经被旧观察逻辑置为
   preparing 的持久记录，不修改历史 duty revision、旧批准、Task、Run 或升级数据。
   新候选已取代原执行、身份/范围不符、原安装或验收未完成、确有未决副作用时，
   保留实际拒绝与 unknown。当前 Issue CAS、责任代次和请求去重继续生效。
4. 历史结清仅登记证据和完成原责任；不重新激活旧执行授权，不发起 merge、部署、
   重试、回滚或模型审阅。相同历史事实在后续维护后无需重复人类批准。
5. 同步协调者和工具说明：区分历史结清与新候选授权；负责人可在既有目标中处理
   技术失败、合理安排后继工作和预算。Agent 自设计划不能被升级为人类永久限制；
   真实用户范围、次数和成本限制继续保留，已消耗尝试及已完成报告不可改写。
6. 纳入已调查的只读来源错误映射：不存在的手工注入来源返回正式 not-found；普通
   Issue 消息仍由通用资料读取，不把纯读缺失扩大成身份失效或业务副作用未知。
7. 托管工具的失败或未知回执保留已经分配的原 request_id 和实际状态，便于按原
   身份对账；不因回执只显示错误而生成新身份重发，也不新增独立预检系统。

## 验证与交付

- RED→GREEN 覆盖真实历史结清链、已经失效的保留记录、后续独立维护和所需证据。
- 反例覆盖未完成/未验收、错误批次、错误源码或目标、替换执行、旧 CAS/责任、
  未决升级与真实 provider 身份冲突；确认旧批准不能用于新的部署或执行。
- 托管入口预检与正式事务均接受同一合法历史结清；错误拒绝不产生副作用。
- 相关聚焦测试后，对唯一最终候选完成本地 make check、独立 review、所需 CI，
  rebase 到当前 main 后通过 PR 合入。保留所有失败、纠错及来源证据。
- 构建实际合入版本，评估协议/存储及固定更新器兼容性，保留现有 Agent 配置。
  受控部署后，由原负责人调用普通 complete 及 Issue 收尾；不由维护者直接改账。

## 边界

不新增生产测试对象，不扩大原业务授权，不复活旧 lease/session，不清空历史
unknown，不新建结清状态机、预算审批功能或逐次恢复许可。其他结构性简化继续
保留在既有维护清单，不借本修复改写已提交迁移或全部工作流。
