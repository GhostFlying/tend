# 托管 Agent 限流失败的持久恢复

状态：实现及本地验收完成，等待 PR CI 与受控发布。关联 D120、D11、D73、D88、D111、D113、D114。

## 原生能力核验

已核对 Codex 0.163.0 的运行二进制生成的 experimental schema，以及对应发布源码 `83086188ae0614bd882818ff1aa23f3194962012`。原生已有 Responses 请求重试、退避及 Retry-After 处理；HTTP 429 无有效服务端重试提示时可直接终止，带有效提示则在 stream retry 预算内继续。不能把所有 429 都描述为没有原生重试，也不能认为调大 request_max_retries 就会重试普通 HTTP 429。

app-server 没有 turn/retry 或 turn/resume。已加载且空闲的 thread 可以通过 turn/start、input=[] 开启新的续接回合；进程重启后先 thread/resume。该方式保留会话中的工具结果，无需重新提交原用户输入或合成“继续”消息；不是重启原失败 turn。

隔离假服务验证已确认：无 Retry-After 的 HTTP 429 只有一次请求并以 willRetry=false 结束；带 Retry-After: 1 的 429 在同一回合自动等待重试成功；一次工具完成后限流，空输入新回合能够继续，工具结果保留且该测试工具只执行一次。最后一种情况下，发送给模型的用户消息数量保持不变。

原生错误通知暴露 willRetry、codexErrorInfo 及部分 HTTP 状态，没有通用 Retry-After 调度字段。空输入续接不生成新的 userMessage，clientUserMessageId 不能充当这类续接的持久幂等键。普通消息的 Codex 字段名是 clientUserMessageId，现有适配中的 userMessageId 必须按实际 harness 协议分别处理。

## 目标与范围

主 Agent 与工作项后台 Agent 遇到明确的临时限流后，自动退避并续接原会话；后台无需 owner 主动发送“继续”。恢复责任、预算及下一次时间跨 server 重启保留。第一版只覆盖已确认失败回合的结构化 429 / rate_limit_exceeded，不修改 AxonHub，不增加模型请求代理，不扩展 runner worker 的既有恢复策略。

原生 harness 的内部重连尚未结束时，不启动 Tend 恢复。可结构化识别的鉴权、额度耗尽、参数错误、owner 中断及原因不明的失败不进入本次自动恢复白名单。如果原生只暴露 HTTP 429 而隐藏更细的上游原因，Tend 只能按有界的 429 策略处理。不能仅凭错误文案包含数字 429 判定可恢复。

## 当前缺口

- harness 的 Turn 与 Event 主要保留 status，error 通知没有进入统一结构化失败事实；原始回执虽然保留，但不能直接形成可靠策略输入。
- mainthread.Deliver 将原生 failed 保存后返回 Delivered，表示原消息确实已交给 harness，不表示业务处理成功。后台池因此不会再次调度这项处理。
- outbox 的 Retry 表示原消息肯定未生效。失败前可能已经完成工具调用，不能将 failed 一律改为 Retry，也不能覆盖同一个 main_turns 记录的 turn_id 来隐藏历史执行。
- 现有前台 logical turn 的上下文补正属于完成性修复，不能代替失败回合的业务续接，也不能与它并发调度。

## R1：保留失败事实

在 harness 内定义统一失败事实：原生错误码、可选 HTTP 状态、原生是否仍会重试、错误来源及可选 retry-not-before。将 error 通知、turn/completed 与 thread/read 按 thread_id / turn_id 关联；以确认的最终失败及原生回执为依据，不以一条中途 error 通知触发恢复。

不假设 Codex 会暴露 Retry-After：只有原生协议提供了可核验字段才使用；缺少时走 Tend 默认退避。记录安全摘要，原始事实沿现有 rollout 事实链保存，日志不记录凭据或请求正文。

## R2：恢复状态与事务

新增追加式存储迁移，保存独立的恢复链及执行关联，至少包括：

- conversation_id、原始 message_id、恢复链 ID、当前原生 thread_id；前台关联原 logical turn。
- 每次执行的 request_id / native turn_id 与父失败执行；原生执行记录只追加关联，不覆盖前次身份。
- 失败分类与来源、恢复次数、首次失败时间、next_attempt_at、预算截止时间。
- 本次恢复固定的 model / provider / effort、所依据的会话设置版本及控制代次。
- 状态：等待、启动待确认、执行中、待对账、完成、取消、预算耗尽或需处理。

确认失败、保存原生执行结果、创建或推进恢复记录、写入事件及下一次 outbox 动作在同一 app 事务内完成。对同一失败执行设置唯一约束，重复通知、轮询及重启不能产生多个恢复动作。

同一处理责任下，前台业务续接与仅做上下文补正的执行互斥。准备自动续接时不提前将整个责任结算为最终失败或调度另一条业务执行；结束恢复后再按已有完成性约束结算。

## R3：退避与调度

拟定默认值：首次等待 5 秒，指数增加至 120 秒，再增加 0–20% 正向抖动；最多自动续接 8 次，允许安排恢复的总窗口为首次失败后 15 分钟。参数集中配置，clock 与抖动输入可注入测试。

若存在可信的 provider not-before，下一次时间不早于该时间。超过总预算时进入需处理状态，不能通过提前重试或截短 Retry-After 绕过预算。预算不强制中断已经确认运行中的回合。

下一次时间只计算并保存一次；重启沿用原值，不重新抽取抖动或清零次数。复用现有 outbox 与后台池查询，不创建独立守护进程。等待期间退出后台 Manager，释放后台进程和并发名额；恢复到期再加载同一原生会话。

保持同一会话串行。等待恢复不得堵住停止、撤回等控制动作；不同后台会话不相互阻塞。前台新 owner 消息优先于旧恢复动作：在同一事务中使旧恢复动作失效，并将未完成责任显式关联给新的处理轮次，保留来源，不能静默丢弃或另起一轮继续旧指令。后台收到新的 owner 指令时采用相同的代次检查，先确认最新授权再决定是否续接。

## R4：安全续接与重启对账

开始前再次读取 owner 控制、消息是否撤回、工作项状态、恢复代次、会话设置和原生执行回执。owner 明确修改模型设置时不强行恢复旧设置；使旧候选失效，再根据最新明确选择建立后续候选，保留同一恢复预算。

确认原回合失败且没有未收敛的工具、审批或后台操作后，在同一原生 thread 上通过 turn/start、input=[] 开启新的 continuation turn，使用原生保留的消息与工具结果，不追加合成的用户消息，不重新投递原消息正文、附件或整份任务。必要的最新账本事实仍通过现有上下文注入边界更新。每次原生续接使用新的 Tend 执行 request_id；该次投递的传输身份保持稳定，但不将它描述为 Codex 提供的原生幂等键。

提示不能保证外部副作用恰好一次。启动前必须核验原生及 Tend 工具事实；有工具结果未知、仍在运行的后台操作或无法证明收敛时保留待对账状态，说明具体缺失事实，不自行重放。Tend 工具继续沿既有 request_id 去重及 revision 校验；不得将原生工具已经执行完成理解成“允许再执行一次”。

发出 turn/start 前，先持久保存启动意图、原 thread_id 与最后确认的历史回合边界；收到 turn/started 通知或调用响应后尽快持久保存新 turn_id。空输入不会新增 userMessage，不能仅凭 clientUserMessageId 对账。若响应丢失，重启后按已知 turn_id 查询原生历史；只有能独立核验会话独占且边界之后的唯一新增执行确属本次恢复时，才允许回绑：

1. 已找到执行：关联该执行，继续观察或结算，不再次发送。
2. 明确拒绝且确认未创建执行：允许按同一投递身份再次尝试，预算按持久规则计算。
3. 历史缺失、读取失败或结果歧义：保留待对账和会话围栏；未找到不等于未执行。

owner 停止、撤回、工作项结束及 server 维护围栏都必须在实际启动处再次校验；旧事件和旧恢复候选不能重新启动已失效工作。维护暂停期间不占用后台进程，到期及预算仍按持久时间核验。

## R5：状态展示与通知

沿现有 owner 视图及 Web 会话状态展示恢复阶段、失败原因、已尝试次数、下一次时间与是否需要处理。后台项可见，owner 可在等待期间停止自动恢复。成功后归并为同一消息/工作责任下的多次执行，保留完整事实链。

瞬时退避只写状态与审计事件，不逐次唤醒前台。预算耗尽或恢复受阻时，通过现有持久事件链生成一次去重提醒，交给现有协调者处理；不启动第二个调度 Agent，不自动创建新任务或改变原任务状态。

## R6：验收与发布

- 明确限流后等待到期才续接；成功结束恢复，连续限流触发预算上限；非白名单失败及 owner 中断不自动续接。
- error(willRetry=true) 后原生自行成功，不产生 Tend 恢复；事件乱序、重复通知与历史对账只生成一条恢复链。
- 已完成一次工具调用后限流，后续只完成剩余目标；工具结果未知、后台操作未收敛及鉴权/额度错误保持正确状态。
- 在等待、创建 outbox、发送 turn/start 前后、收到结果前后分别模拟崩溃；恢复时间与预算保持，未知启动不重发。
- 多个后台会话并存，等待释放名额；同会话不重叠；停止、撤回、新 owner 指令、模型设置改变及维护操作能使旧候选失效。
- 前台逻辑轮的业务恢复与上下文补正互斥，最终完成性约束保持；新增 owner 指令的承接不能丢失旧责任。
- Web 刷新后仍显示持久倒计时及处理状态，终止操作具有原 request_id 回执。

单元测试用可控时钟及 fake harness，真实协议验证使用 integration 隔离会话，不向生产任务注入限流。实现通过 make check、指定独立 review 与 PR CI 后，走已有受控发布；上线回读真实配置、存储版本和一次独立恢复的事实链。server/runner 通信不在本次范围，owner 视图优先增加可选信息并评估旧客户端兼容。

## 实现补充与验证记录

- 使用追加迁移保存限流链、每次执行及只读回执对账时间。后台 unknown 的已知 native turn 保留持久读候选，默认每 30 秒重新读取，单次启动等待最多 20 秒；这类对账不发送模型输入，也不增加业务恢复次数。
- 上下文注入之后重复 owner、预算、设置与维护围栏检查；未消费的新 owner 输入必须有可运行投递才可承接责任。原生消费结果未知的输入保持对账，不转给没有后续执行的未知投递。
- 预算在真正启动前耗尽时，逻辑责任进入 needs_review；恢复成功按最终业务结果结算继承的 owner 输入，原始 native failed 事实保持。
- 已完成真实 Codex 0.163.0 加隔离 HTTP provider 的适配测试与管理层端到端验证：工具一次、429 终态、同 thread 新 turn、持久恢复链完成，前后用户输入数量相同且保留工具结果。生产任务未注入故障。
- Web 在桌面和手机宽度验证持久恢复状态、停止与重新读取；类型、lint、格式、281 项 Web 测试和跨平台构建通过。全仓 Go race 检查与 make check 已通过，指定独立 review 的复现问题已修正并加入回归。PR CI 和受控发布继续按 R6 完成。

- 前驱历史的只读请求失败时，在尚未写入启动意图的前提下安全退避重读；读取过程同样受持久预算、owner 控制和维护围栏约束。已发送但缺失回执的续接仍保持 unknown，不用此路径重发。
- Owner 停止先保存消息级停止事实，覆盖后台尚未形成恢复链的竞态。等待计划的未准入替代消息撤回后，仅恢复确定未启动的原候选，沿用原次数和期限；已准备的责任保留为 needs_review。
- 新输入承接完成时更新继承消息的处理状态；native failed 原记录不改写，也不据此制造旧版本的正式后台核对结果。
- Traex 与 Codex 均可能返回 codexHome。适配器通过同一配置命令的 CLI 版本标识确认 Codex，再选择 clientUserMessageId 与已验证的空输入续接。已对真实 Codex 0.163.0 与 Traex 0.211.1 做协议分流验证。

- 普通 Codex 输入的历史关联读取 userMessage.clientId，区别于原生生成的 item.id；真实二进制已验证缺失 turn ID 时仍可按该字段查回。turn/started 对所有托管输入尽早持久保存 native ID。空输入仍只能按已知 native ID 对账。

- 真实 Codex 的后台恢复验证额外关闭原 app-server 进程，再从相同独立 home 恢复原 thread；空输入续接成功，已完成工具输出保留且未重跑工具。
- 已复现并修正终态写库失败后的只读回执对账、明确拒绝注入的未启动状态，以及等待停止或到期后按原生失败事实发布缓冲部分输出。
