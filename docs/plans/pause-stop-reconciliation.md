# 自动结清原 Run 的暂停停止回执

Refs: D218。

暂停或退回 Backlog 会中断目标 Run。若本地 app-server 已退出，但原进程集合中的脱离子进程还活着，首次关闭核对会失败。执行器退出后，租约可能先到期，服务端将同一 Run 标为 unknown，暂停操作继续等待物理停止证明。

1. 复用 runner 的 Hello 对账循环发现原 journal 中的暂停。仅在服务端仍确认相同暂停、原 Run 可对账且没有人工接管、保留隔离或优先收尾结果时，沿现有 app-server 工作区和进程所有权证据检查停止。该路径不进入原生工作或重放原业务。
2. 对明确仍活跃的原进程集合按 Run 退避重查。等待期间不给该 Run 续租，也不把 unknown 投影成运行或中断状态。原身份或证据不符时保留原 Run 并记录检查失败原因。重启后从原 journal 与服务端暂停身份恢复核对。
3. 确认停止后走既有 runs.yield_pause，先将原 Envelope 落盘，再发送。回执丢失或重启后继续原请求身份。已知结果、待答问题、外部等待和其他业务回执沿既有规则收尾。暂停结清本身不授予 Issue 恢复权限。
4. 用真实 runner、HTTP 和 App 复现暂停、首次停止失败、租约到期、原进程集合退出及暂停 pending 从 1 到 0。验证真实进程集合核对、非重试身份错误和同 Envelope 回放。测试可以替换模型服务和注入传输失败；说明原进程启动、关停和账本转换实际覆盖范围。

独立审阅与当前候选的验证可与其他 Issue 并行。串行协调只覆盖最终 rebase、推送和合入，无需暂停 Issue。
