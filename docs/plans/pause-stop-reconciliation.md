# 自动结清原 Run 的暂停停止回执

Refs: D218。

暂停或退回 Backlog 会中断目标 Run。若本地 app-server 已退出，但原进程集合中的脱离子进程还活着，首次关闭核对会失败。执行器退出后，租约可能先到期，服务端将同一 Run 标为 unknown，暂停操作继续等待物理停止证明。

1. 复用 runner 的 Hello 对账循环发现原 journal 中的暂停。仅在服务端仍确认相同暂停、原 Run 可对账且没有人工接管、保留隔离或优先收尾结果时，沿现有 app-server 工作区和进程所有权证据检查停止。该路径不进入原生工作或重放原业务。
2. 对明确仍活跃的原进程集合按 Run 退避重查。等待期间不给该 Run 续租，也不把 unknown 投影成运行或中断状态。原身份或证据不符时保留原 Run 并记录检查失败原因。重启后从原 journal 与服务端暂停身份恢复核对。
3. 确认停止后走既有 runs.yield_pause，先将原 Envelope 落盘，再发送。回执丢失或重启后继续原请求身份。已知结果、待答问题、外部等待和其他业务回执沿既有规则收尾。暂停结清本身不授予 Issue 恢复权限。
4. 用真实 runner、HTTP 和 App 复现暂停、首次停止失败、租约到期、原进程集合退出及暂停 pending 从 1 到 0。验证真实进程集合核对、非重试身份错误和同 Envelope 回放。测试可以替换模型服务和注入传输失败；说明原进程启动、关停和账本转换实际覆盖范围。

独立审阅与当前候选的验证可与其他 Issue 并行。串行协调只覆盖最终 rebase、推送和合入，无需暂停 Issue。

## 已停止的 Issue 负责人续行

正式暂停可在连接级断开事件归账前结束负责人 Run 并释放原租约。恢复 Issue 时，原 action 等待该事件，但没有已附着的线程来消费它。原负责人和工作消息因此一起停在队列里。

在既有暂停续行事务中，核对原负责人、已确认的停止交接、已结束的 Run、已释放的租约和物理停止覆盖的事件尾序号。仅当尾部唯一未应用事件是连接级 disconnected、原业务结果已知时，按原 Run 和序号应用这条传输事实，并记录其原件摘要。保留原事件和停止回执。其余事件与未结业务仍由原归账机制处理。正常准入为同一负责人生成唯一后继，无需重新申请暂停或恢复权限。

回归从真实 Issue 入队与具名负责人领取开始，提交原始断开事件，正式退回 Backlog 并接收来源 Run 的停止回执，再恢复到 Todo。核验首次领取、重试请求、原事件、释放的租约及唯一后继，同时覆盖混合业务事件、缺失物理停止证据和未知 native 操作。

## 独立审阅修订

1. 事件上传遇到传输失败时，保留停止证明与已落盘的暂停请求，通过原 Run 的 Hello 退避重试。只补送未确认事件，并保留事件序号与租约。若暂停回执已发出但响应丢失，沿既有发送路径直接重发同一 Envelope。未知业务结果继续留给原归账入口。
2. Journal 只允许仍处于 started 的原 attempt 进入 pausing。已保存的 worker_done 结果先走正常收尾。
3. 仅在 Run、thread、attempt 通过校验后，复用已有外部停止证明校验，并保留证据来源。
4. Hello 遇到 owner 接管时保留退避检查。接管期间不观察进程或发送暂停回执，直到服务端确认交还和原暂停身份。
5. 用审阅复现覆盖事件上传失败、延迟交还、已完成结果保留和外部停止证明。保留遗失回执、重启和已停止具名负责人续行测试。

## 复审修订

1. 将正式人控同时应用于观察中的暂停和已落盘待交付的暂停回执。Hello 返回 Held 时保留原回执并安排后续核对。服务端在同一事务中为首次暂停确认核对人控状态，阻止消息投递和接管之间的竞态。后续回放使用原 Envelope，已提交回执继续按已保存的物理停止事实幂等确认。
2. 将暂停进程观察阻塞限定在观察阶段。正式 Stop 使用已有最终停止路径。被维护保护隔离的暂停 Run 继续通过正常心跳触发 Hello，只读取后续控制。
3. 用下一条 journal 迁移提高持久格式版本。升级保留原记录，旧 runner 在读取新阶段前由已有版本检查拒绝打开。
4. 回归覆盖首次事件上传时接管、正式交还及原 Envelope，另验证本地检查失败后的正式 Stop、维护隔离中的 Hello、旧格式迁移和旧执行器的版本拒绝。

## 到期租约与跨重启核对

1. 将暂停进程观察和原暂停回执对账都作为只读控制查询。Hello 返回人控或暂停意图与原交接标识，保留已到期租约的期限与状态。等待首次或重放回执期间不通过心跳续租。
2. 先验证原 Run、线程、尝试以及 leader 和全部脱离进程的身份、进程组和共同 boot。若已确认主机重启，原 kernel 进程集合已退出，无需检查新版 PID 或进程组。记录有缺失或冲突时继续保持未知，同一 boot 的进程核验保持既有严格判断。
3. 用 Hello 响应证明真实 HTTP 用例观察到人控，并同时断言原租约状态及期限恒定。用虚拟历史 boot 与真实活跃 PID 验证旧进程组已结束、未触碰当前进程，以及记录不全时保留未知。

## 已停止 Run 的结果优先级与旧 Runner 兼容

1. 在直接确认停止和观察确认停止两条路径汇合后，先沿原 Run、attempt、thread 和工作区核对已保存的结果或验收结论。验证成功时进入原有完成流程。无法核对时保留停止证明及原记录，等待原归账。
2. 在人控期间只向已声明支持等待交还的原 journal 返回暂缓回执。旧 Runner 继续提交已有的物理停止证明。已提交过的回执可继续按原 Envelope 幂等确认。
3. 验证暂停期间已保存的原结果先于暂停回执送达，结果不明时不产生业务请求，以及旧、新 Runner 处理同一人控交错的不同回执路径。

## 恢复结果的工作区控制

1. 停止证明和原结果先进入持久的 worker_done。退出只处理暂停观察和停止回执的执行器，由新的 Hello 确认原 Run 的当前控制和同一租约，再进入普通结果收尾。纯报告和 Git 收集共用此入口，人工接管期间的交还和 Stop 继续经普通控制下达。
2. 复用原租约和已有租约看门狗。将已正式暂停、原进程已停止而等待结果收尾的 Run 报为 waiting。按旧 pausing 快照发出的 Hello 仅能继续停止对账，不能给新的收集阶段授予租约。收到 Stop、失去租约或收到人工接管时，取消正在执行的收集。
3. 回归使用真实执行与控制循环验证旧暂停回复、新 Hello、原租约及收集期间的控制指令，覆盖纯报告恢复期间接管、正式交还后交付同一原结果，以及收到 Stop 后按原规则结清。保留未验证结果用例。

## 验收上传与在途 Stop 的对账

1. 文件上传沿用普通 RPC 的传输结果分类。响应无法解码时保留原上传请求和封存文件，由暂停循环按原退避重查。业务拒绝及证据内容或身份不符沿原路径处理。
2. 任何原租约心跳返回 Stop 时，将后续对账交给当时持有原 Run 的执行器。若正处于执行器切换间隙，直接唤醒 Hello。既有 Stop 路径使用原身份结清，保留先前的物理证明和回执。
3. 验证截断上传响应后使用同一请求和原证据完成验收，并核对前一执行器的 Stop 回复在暂停观察中或切换间隙到达时只结清原 Run。
