# Issue 状态驱动领取与暂停交还

状态：实施中。前置 D215；同一计划的第二个 PR，不部署中间版本。

## 领域与数据

1. 新 Issue 显式记录 backlog；类别与可选 Agent 选择属于 Issue 版本化定义，创建不分配 Task、action、Run 或租约。主 Agent 的“立即执行”使用创建成功回执，连续提交 backlog → todo。
2. backlog 只能前往 todo 或发起取消，不能跳到运行、评审或完成。todo 必须有有效的执行类别；可复用已有选择，也可在状态请求中显式提供。todo 的进入时间用于等待排序。
3. 初次候选直接从当前 Issue 状态及选择派生，无额外入队授权记录。候选匹配复用纯 scheduler；runner.claim 选中后才在同一事务内创建负责人 Task、action、Run、执行 pin 和租约。并发领取、状态退回和选择修改由同一写事务排他处理。
4. 已有执行继续复用原 Task/spec 与冻结选择；本项、祖先、独立验收责任以及前置依赖共用准入判断。backlog 禁止新执行；取消收束与必要回执读取保留独立通路。
5. 历史空状态通过 App 的幂等转换追加 revision；没有执行责任的记录转为 backlog，已有执行责任保留既有工作意图。原始 revision、请求和产物不改写。转换不唤醒纯记录事项。

## 暂停与恢复

1. 退回 backlog 或显式暂停时记录原操作、Issue revision 和整条子责任范围，立即关闭新工作准入。子项工作状态保留，人工接管与用户独立 Task 暂停不被覆盖。
2. 暂停作为 Issue 控制覆盖层，避免通过改写 Task 的独立控制状态实现继承。每个已开启 Run 保留原操作和控制版本。取消优先于暂停，不产生暂停后继。
3. 采用协商能力 `run-pause-handoff-v1`。冻结支持该能力的 Run 通过控制响应获取暂停交还身份；runner 先确认受管 Agent 停止，再以持久原请求发送 `runs.yield_pause`。服务端记录物理停止并结束本 Run、释放租约和槽位，不生成完成、验收或失败结果，不消耗额外尝试。
4. 原成功交还请求在租约释放后仅允许精确回读/重放。停止未知保持占用；已证明物理停止但业务回执未知可以交还槽位，未知义务继续阻止自动续行。
5. 再次 todo 只解除此 Issue 操作引入的覆盖；原 Task/spec/代次、累计预算、代码、工作区、产物和会话引用保留。停止与业务义务均满足、合同仍适用且准入开放后，生成唯一后继 action/Run；不得重做完成项，也不能绕过已有问题交还、人工控制或维护围栏。

## 对外入口与兼容

同步 owner API、主 Agent/Issue Agent 工具、CLI、Web 的创建、类别选择、状态变更、暂停进度、继承原因与取消结果。系统创建的子任务与验收 Issue 也记录真实 backlog → todo 授权版本，合同不再硬编码初始 revision=1。

仅追加服务端与 runner journal 迁移。能力、字段和操作为协商后的可选扩展，保持协议 2/1 原有默认语义；旧 runner 不假报交还或槽位释放，新 runner 连接旧 server 不发送新操作。历史对账仍沿原操作执行。
