# 降低共享 SQLite 写连接争用的影响

生产观察在既有样本中记录了 245 次至少 1 秒的慢写。跨请求累计用时
339.04 秒，其中 315.40 秒在等共享写连接。这个累计值含并发叠加。
以下三项按顺序验证，各自提供可独立审阅的变更。

1. SSE。用真实 HTTP 流回放超过一个读取批次的已提交事件。回放时在另一
   事务中持有 SQLite 写连接，复现首个刷新通知已经 flush、第二批仍然
   卡在刷新确认的现象。把确认交给 Server 管理的写入协程，只保留成功
   flush 后观察到的最高刷新序号。多个连接共享同一水位和写入协程。
   写失败时保留水位并限速重试，关闭时取消并等待协程退出。验证并发
   连接、断线重放和过期时重新读取权威视图，并检查确认只更新 pending，
   刷新通知和业务事件仍可按原规则恢复。
2. Runner 用量上传。用相同数据从实际操作入口测量小批和满批，分别记录
   处理量、事务回调和写连接等待。先检查同源 provider、session 和元数据
   的重复查询，移出循环前验证同一批次内仍可能变化的数据。保留来源、
   host、会话校验及原事务内的归属和幂等语义。
3. Runner 领取和开放轮次结算。用固定阶段及处理条数区分暂停续行、外部
   等待、manager 刷新和 SettleOpenTurns 的子步骤。先构造可重复的写入
   观察样本，只有测量能归因时才改慢操作。沿现有入口验证租约、回执及
   unknown 恢复行为。

每项在最终候选上核对本地受影响检查、独立审阅和 CI。后续生产比较用
相同采样窗、相同慢写阈值和接近的请求量，按操作记录写连接等待、占用
时长及分位数。客户端记录相邻有数据 SSE 批次间隔及 Chat 请求至首个
模型输出字节的时间，按重连和负载分别比较，并记录是否包含其他修复。
