# Issue owner 与跨 Agent 子 Issue 委派

## 目标与边界

Issue owner 是具体 Agent 对某件事承担的责任，不是一种固定 Agent 类型。同一 Agent 可以自己执行，也可以通过子 Issue 委派另一 Agent。每个 Issue 同时只有一个 owner；父 owner 保留整体协调及结果整合责任。

本轮不改 Issue 页面或人工操作流程，保留 owner 人工指派、暂停、取消、交接和恢复。历史任务、协议与未知结果按原合同对账，不重写已有账本，不自动重放此前失败的用户请求。

## 实施顺序

1. 记录 D136。保留历史 `issue_manager` 的协议与存储名称，把它定义为持续责任的执行角色。类别用于能力选择，不再要求专用 manager Agent；普通 Agent 可以声明独立的 owner runtime binding，原生能力经实际探测后可用。
2. 为新 owner 责任启用版本化的子 Issue 委派策略。自身执行任务冻结当前 owner 身份；其他 Agent 的实现必须先成为子 Issue owner。现有独立验收保留，并为另一验收 Agent 建立子 Issue 责任与运行关联，不让 Task/Run 成为没有 Issue 的旁路派工。
3. 接通任意已具备所需能力的 Agent 的 owner 领取、同身份执行及恢复。任务/运行选择冻结身份、配置与 assignment epoch；旧 epoch 或新库存不能偷偷替换执行者。缺少 owner adapter 时保持明确等待，不补造可用能力。
4. 更新动态工具和角色指令：自己做或拆分由 Agent 判断，跨 Agent 的责任边界由服务端强制；不允许原生子 Agent 绕过账本。模型专属说明只影响执行策略，不改变权限。
5. 针对自身执行、递归委派、验收责任、交接围栏、请求重放、旧合同及单槽释放补充验证。完成完整检查、独立 CLI review 和 PR CI 后通过线性合并交付；部署沿既有受控流程进行，不自动启用真实 Bot。

## 验收

- 普通 Agent 可以在能力满足后成为 Issue owner，无需额外创建 manager 身份。
- 同一 owner 能在自己的 Issue 下执行，其他 Agent 的工作具有独立子 Issue。
- 独立验收继续隔离实现材料，验收 Agent 的运行有明确 Issue 责任。
- 子项结果触发父 owner 的既有持久唤醒，父 Issue 不因所有子项结束就自动完成。
- 人工控制接口及页面继续可用，身份、版本、未知结果和历史恢复约束保留。
- 不实现评论 mention 隐式派工，不修改 Issue 交互。

## 实施结果

已实现可选 owner runtime binding、新 owner 发布合同、能力准入、同身份执行冻结及有界验收子 Issue。原 `issue_manager` 历史协议与持久化名称保留，不将旧任务静默转换为新合同。新增查询包含任务与运行的 Issue 责任，前端仅更新生成协议类型。

交接后的旧执行仍保存成功、失败与回答事实，但不能创建新重试决策、问题或后续动作。验收子项的取消等待真实执行与未知结果收敛；正常收尾条件不满足或人工扩展目标时，验收事实保留，子项保持开放。任务刷新不能偷换已冻结的实现者或验收者。

回归覆盖自身执行、子项委派、独立验收材料隔离、责任交接、人工取消、范围变更、重复领取与回执，以及旧执行失败和提问围栏。独立 CLI review 的有效发现均已修复，最终 review 无新增缺陷。完整检查与 PR CI 沿仓库规定执行，生产配置及发布验收记录保留在部署环境，不纳入公开文档。
