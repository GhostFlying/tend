# 工作目录准备失败的负责人修正闭环

## 目标

复用目录的 commit 任务遗漏 `include_existing_changes` 时，保留全部现场，报告明确的启动前诊断，由当前 Issue owner 核对授权并更新原任务合同继续；不自动纳入改动，不将可修正的技术配置问题直接转为用户决定。

## 实施

1. 增加可协商的、可选的启动前失败诊断。runner 以有类型的错误记录工作目录、来源任务、有界文件状态及所缺字段，持久上报；仅明确未启动的已知合同错误进入负责人修正路径。旧 runner/server 保持原有语义，wire 仍为 2/1。
2. server 在失败事务中保存诊断、阻塞当前任务并唤醒当前负责人。取消、暂停、交接、旧 spec/run、unknown 继续遵守既有围栏；无负责人或旧协议证据时沿原失败流程。
3. `tasks_read` 提供负责人作用域内的诊断，不依赖原生日志权限。补齐本 Issue run 消息读取的授权检查；不扩大到其他 Issue。
4. 完善当前负责人关于复用、提交范围、合同修正及技术阻塞的指令和工具反馈。保留现有 task/spec/run 历史，当前合同修正通过 `issues_update_task` 启动新 spec 的执行；重复相同合同不自动重排队。
5. 更新设计决策和生成协议。验证目录与索引不变、失败诊断持久化/去重、负责人唤醒、同任务合同修正后执行、权限、围栏及旧协议回退。

## 验证与交付

使用真实临时 Git 目录、fake harness/runner 和可控时钟验证闭环；执行定向 race 测试、`make check`、独立 CLI review、PR CI 和跨平台编译。通过 PR 线性合入。部署及真实任务恢复单独执行，不修改运行中的业务账本。
