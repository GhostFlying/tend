# Issue 变更通知与负责人任务判断

状态：用户已确认设计方向；主线交付已被合同适用性硬门实质阻塞，外部维护开始统一实施。修复验证及受控部署完成后，由 Tend 沿原责任接续。

## 责任与实施时机

- 本系统问题由外部维护及其协作 Agent 修复，不创建或委派新的 Tend pending Issue，不让业务主线承担平台修复。
- 主线正常推进时保留现有执行，先完成只读调查与维护计划；主线完成后统一处理记录的问题。如果记录中的系统问题实质性阻止主线合法接续，则提前开展必要维护。
- 已有两个界面问题保留原 Issue 与安排；维护启动时统一核对问题清单、责任和变更范围，避免重复实施。
- 本次主线来源指纹因已确认的退役状态显示澄清而改变时，用户明确允许通知原负责人忽略或跳过该机械提示，优先沿原任务继续。若当前入口存在硬限制，由负责人使用现有最小合法合同处理接续，保留实际执行和证据；该次提示不单独启动改造；后续交付执行因受限授权不可读及合同适用性硬门实质阻塞后，本批维护统一启动。

## 用户确认的模型

1. 任何已提交的 Issue 修改都应进入当前负责人的变更通知。程序负责可靠通知，由负责人判断只是状态、进度或说明变化，还是任务要求真正发生变化。
2. 通知复用现有事件与后台批次合并模式，避免连续变更反复拉起负责人。正在运行时保留尚未处理的新变化；负责人本回合已经处理的自产变化不形成无限自唤醒。
3. 负责人可以明确继续原 spec、修订 spec，或记录需要处理的暂停/澄清。继续原 spec 是有效决定，不因来源指纹改变被另一条独立检查推翻。
4. spec 保留某次任务约定及其历史版本。消息、Issue、上下文或进度更新不自动增加 spec 版本，也不自动停止现有 worker。
5. 变化的判断由当前 Issue 负责人在既有授权内完成；普通协调不额外要求人类重复确认。明确的暂停、取消、责任转移及未知执行对账仍使用现有控制语义。

## 已确认的问题

- 当前来源指纹包含目标、约束、授权和拒绝事实。一次保持原任务范围的重试授权被登记为普通文字授权事实后，指纹变化，旧 spec 被标为 `task_agreement`，即使来源审阅已完成也无法调度。
- `continue_existing` 目前参与计划变更校验，却未保存一份能被来源检查和调度共同识别的适用性确认。相同计划的更新还可能直接返回成功，使确认没有实际效果。
- 自动来源修复回合仅允许补齐审阅，并明确禁止更新任务合同；该回合完成后仍可能遗留合同处理责任，没有正常业务协调接续。
- Issue 的一般变更会保存事件，但现有负责人通知没有统一覆盖所有修改。看板状态通知已有合并机制，不能直接将其全部行为视为通用负责人变更通知。
- 只读调查确认已有通知窗口和未领取 batch 两层合并；已领取 batch 会冻结，后到变化进入后继批次。实现复用这些边界，不另造通知总线。
- 现有状态通知的自产过滤可能先取消旧 pending 通知再退出；泛化时必须保留先到的外部事件。writer tail 还需使用真实协调来源，不能只看局部执行对象或笼统排除所有 Agent 写入。

## 实施方向

### A. 统一变更通知

- 在现有事务、事件与 outbox 路径中汇集 Issue 修改，保留原请求、修改来源、Issue 版本及当前责任代次；不新增轮询或第二套消息总线。
- 按 Issue 复用未领取批次；领取后冻结其已知来源，之后到达的外部变化保留为后继批次。幂等重放不重复唤醒，连续变化不会逐条创建原生回合。
- 当前负责人本回合已经知晓并处理的写入可归入本次处理范围；不得以“Agent 写入”为由删除或吞掉同批次中尚未处理的外部变化。
- 未处理变更形成普通协调责任。仅有来源审阅修复完成，不能将仍待负责人判断的变更整体视为处理完成。
- 变更通知不新增“每次修改均须先确认才能运行”的通用准入门。程序记录变化和处理范围，由负责人决定是否需要控制正在执行的任务。

### B. 负责人决定 spec 适用性

- 复用现有 `continue_existing` / `updated` / `stopped` 的责任表达，统一任务视图、上下文诊断与 scheduler 的判定来源，避免多个入口互相推翻。
- 继续原 spec 时保存负责人对具体任务版本及已处理来源的确认和理由；原 spec、输入、历史执行和验收依据保持不可变，不通过偷偷刷新旧 spec 清除阻塞。
- 真正改变任务约定时走正式 spec 修订。新变化到达后交负责人再次判断，不将上一次确认无限扩展为对未来修改的确认。
- 确认绑定当前任务与责任，不把上下文通知变成新的业务授权，也不重放已经完成或结果未知的副作用。
- 若需增加公开输入或视图，CLI、工具 schema、生成类型、帮助及能力覆盖在同一变更中完成；编码前评估协议兼容性并明确所需迁移。
- 初步方案为独立保存判断，不改写旧 spec；复用 `issues.update` 的 disposition 入口，并使相同计划的有效确认也可落账。实施时统一 canonical 诊断、调度和历史路径边界，避免旧确认被解释为审阅过未来来源。

### C. 恢复与有界处理

- 复用已有负责人回合、批次和责任链处理判断，不新增全局审批人或依赖人工消息才能唤醒的隐式步骤。
- 待处理状态、原因、负责人和下一步必须可读；原有恢复预算与升级路径继续有界，不能无限停在 idle，或仅因回合审阅成功就宣称 worker 已启动。

## 必须验证的行为

- 普通状态/进度变更、重试说明及约定保持不变的来源纠正，可由负责人确认继续原 spec；任务版本、输入与既有执行身份不变，诊断和调度一致放行。
- 真正改变目标、约束、输入或交付要求时，负责人修订任务后再按新约定执行；历史 spec 和结果保留。
- 相同计划附带有效确认不再空成功；旧责任、旧任务版本或尚未处理的新来源不能被旧确认覆盖。
- 一组连续修改合并通知；领取边界前后并发到达的变化不丢失、不重复执行。自身进度写入不自循环，也不删除已排队的外部通知。
- 来源修复完成但仍有任务影响待判断时，负责人能继续正常协调；已经应用的业务请求不被再次执行。
- 适用的本地完整检查、独立 review 与 CI 覆盖最终候选；部署后观察由 Tend 自身推进的实际接续，分别报告源码、安装、执行和业务验收。

## 同批待修：交付驱动的共享 PR Review

状态：纳入本次统一实施与验证，不创建或委派新的 Tend pending Issue。

当前只有 Issue 关联 PR、交付候选版本及外部状态观测的基础。正式验收仍绑定 Task、spec 版本和 artifact，尚无跨 Issue 共享的 PR review 记录、结果复用与有限复查流程。旧部署曾登记本需求，但全新部署没有恢复该待办；本节重新记录完整范围。

1. review 以交付物为单位，通常绑定 PR；调查、解释、报告、计划和中间成果默认自查，明确要求 review 时例外。判断依据是实际交付范围，不能仅凭描述是否出现“PR”决定。
2. 同一 PR 的多个 Task 或子 Issue 关联同一份完整交付并整体审阅，不逐 Task 重复安排 reviewer；子 Issue 独立交付 PR 时才分别处理。
3. 每份交付使用唯一正式 reviewer。impl 或 Issue owner 可启动符合仓库约定的 reviewer，其合规执行与结果同时满足 Tend 和仓库要求，不再额外重复源码审阅。
4. reviewer 提交 findings 后，由 impl 或 Issue owner 逐条评估，集中修复采纳项，并记录不采纳的理由；修复交回原 reviewer。
5. 默认一次初审，加最多一个修复复查周期。复查聚焦修改与受影响范围，同一有效候选不重复通读；仍不能闭合时交父 Issue owner 或主 Agent 判断，逐级无法解决才交人工，不自动无限循环。
6. 复用现有 delivery、候选版本和 observer，补齐跨 Issue 的统一 PR 身份与关联、唯一 reviewer、findings、处置、复查及最终结论。结论绑定明确候选版本和需求范围，变化后明确哪些证据仍有效、哪些需要补审，保留历史记录。
7. CLI 同步覆盖关联、解绑、反查和 review 结果查询，Web 展示真实状态；不静默改写存量冻结任务、历史结论或未知请求。
8. 本次改造自身避免逐 Task 独立验收叠加仓库源码审查，保留唯一合规正式 PR review 和上述有限复查。最终候选仍须满足适用的完整检查、CI 与交付要求；源代码、合入、部署和实际业务验证分别取证。

实施时需验证多 Issue 共享同一候选只安排一次 review、相同结果可复用、修复仍归原 reviewer、候选或范围变化的有效性处理、复查预算耗尽后的升级，以及历史任务和未知结果的保留边界。

## 同批待修：server 统一交付状态检查与负责人通知

状态：由外部维护统一实施与验证，不创建新的 Tend pending Issue。已核验的外部 PR/CI 回执保留为原始事实；新的程序观察须由 server 自行读取和记录。

已观察到的故障是 runner 未启用可选交付观察器，刷新请求没有消费者，负责人仍等待观察结果；同时现有观察器没有收集 CI，已成功的 CI 仍以旧快照呈现。仅恢复 runner 配置不能解决检查职责分散的问题。

1. PR 生命周期、head/base/target、可合入状态和 CI/checks 统一由 server 的程序服务检查、保存并持续更新；runner 不再承担交付状态检查，Agent 接收事实后判断如何推进。
2. 同一交付物由 server 统一协调检查，多个关联 Issue 共享事实；复用现有事件、通知窗口与批次合并路径通知当前负责人，避免重复轮询和频繁唤醒。
3. 检查结果绑定明确的交付物与候选版本，区分新事实、旧快照、未知、失败及按条件跳过；候选变化后重新判断证据适用性，不能以旧 CI 成功推断新候选成功。
4. 每次外部读取与待处理刷新都有超时、重试预算和可读诊断。未配置 provider、鉴权失败、限流及持续不可达不能表现为无期限 pending；负责人能读出当前状态、原因和下一步。
5. server 的 provider 配置与鉴权显式管理。候选准备、执行授权和交付完成共用 server 的事实，避免外部已合入但完成判定仍等待无人消费的旧观察。迁移保留原刷新请求、历史观察和未知结果，明确旧 runner 领取与回执的终止规则，避免两处重复消费；实现前评估通信兼容与必要迁移，不能仅靠停掉 runner 循环迁移责任。
6. CLI 同步提供配置诊断、刷新及结果查询，Web 显示相同事实。验证 server 无 runner 消费者仍能完成检查、同 PR 多 Issue 合并通知、CI 完成后负责人实际接续、候选变更、超时与服务恢复。

本次主动通知只解除对未启用观察器的等待，不将消息冒充程序观察记录，也不扩大原合入或部署权限。runner 观察配置恢复已停止，若受控批次已安装则恢复原配置；统一检查在本批实现，经最终验证和受控部署后生效。

## 同批待修：Issue 明确 PR 合入授权

状态：用户明确要求，涉及 PR 交付的 Issue 应事先明确推进到自动合入，还是需要人工审批。纳入本次统一实施，新增可选 Issue 约定，保留存量冻结任务及真实候选批准。

1. Issue 的交付约定明确合入策略：自动合入，或人工审批。策略表达真实交付范围与授权，不能仅按标题是否出现 PR 推断；未明确时在交付前澄清一次，不把每个新候选都当成新的授权请求。
2. 自动合入模式下，Tend 在已有授权范围内完成实现、独立审阅、适用检查和受保护的合入，程序保存具体候选与执行证据。候选正常修订不强制人工逐次批准，变化后重新验证受影响的证据。
3. 人工审批模式下，Tend 准备具体候选和范围，复用现有版本化问题等待实际批准，再执行批准范围。不得将自动合入策略或普通消息伪装为某次人工批准。
4. 同一 PR 的子 Issue 与 Task 共享适用的 Issue 交付授权及正式 review；责任转移、授权变更、拒绝和超出授权范围时明确处理，保留原策略、历史候选、审批和未知结果。合入策略不自动授予部署权限，部署在交付约定中另行明确。
5. 改造前会在 prepare 时无条件创建 approve/defer/end_delivery 问题，执行还要求原问题的精确 owner 批准。改造需同时贯通 Issue 输入/查询、交付候选校验、执行授权、责任完成与 CLI/Web/工具面，不能只在提示词中让 Agent 跳过现有硬限制。

验证自动合入不产生重复人工问题、人工模式保持精确审批、同 PR 跨子任务复用、候选变更后的检查、授权收回与范围越界，以及历史 Issue 未明确策略时的可解释处理。新候选缺少策略时复用单一 Issue 级澄清，准备、审阅和 CI 继续，尚未取得合入授权；已有真实候选批准例外保留。存量主线已有实际批准，必须保留原授权；受限读取及适用性修复部署后沿原责任合法接续，不重复请求该次批准。

## 同批待修：交付执行者的受限授权视图

已复现：创建交付 Task 时提交的 `delivery_authorization` 经服务端核验后，保存到独立执行绑定；它不在 Task spec 或 Task 查询中。worker 的 `read_observation` 只提供执行摘要，无法核验任务要求的完整授权绑定；调用 owner CLI 被拒，即使补 owner token 也不会出现所需字段。交付 Task 又禁止修订冻结 spec，问题输入授权只覆盖原 run/lease，不能直接给接续 run 增加附件。

- 给交付执行者提供绑定自身 Task、run、lease、Issue 责任及已冻结候选的受限结构化视图，明确原交付责任、实际授权策略或批准来源、当前有效性、可执行范围及拒绝原因；不要求 worker 获取 owner 凭据或查询无关对象。
- 将必须核验的授权、恢复与准入事实对应到真实可读字段，保留出处、版本和观察时间。部署验证的 `unconfirmed` 与仅合入任务所需的恢复前置分别解释，不创造不存在的全局 provider 操作账本或要求全机无普通运行。
- 必要补证通过受限的问题接续或专用证据补充传递，保持原批准候选与冻结执行范围；不能把证据补充实现为任意改写交付 spec，也不能把原 run 的文件授权扩展给任意新 run。
- 验证同 Task 接续读取、已释放原 lease、授权撤回或候选变化、越权读取、输入历史及未知副作用；CLI 与动态工具的合法输入输出同步覆盖。

本次先调查现有问题答复是否能合法携带完整原始证据；若现有入口仍被硬门阻断，则实施必要的系统修复，不以盲重试、复制 owner 凭据或新建替代 Task 解决。

### 共享审阅升级后的显式恢复（D186）

默认两轮审阅未闭合后，保留全部 findings、原 reviewer、候选和升级记录。为避免升级成为永久阻塞，增加 `authorize_recheck`：仅外部已认证用户的独立请求可在 `escalated` 状态下，携带 Issue 版本、责任代次、精确 `expected_review_revision` 与理由，明确追加恰好一轮复查预算。托管主 Agent、当前 Issue 负责人及 worker 都不能自行授予该预算；上级尚不能解决时通过现有升级路径交人工。

授权记录追加保存原 `request_id`、允许的下一轮序号与理由，不重置历史轮数、不改变实际 verdict，也不授予合入或部署权限。授权后仍须逐项处置最后一轮 findings，再由原 reviewer 的新 Task/Run 提交真实结果；再次未闭合立即重新升级，不能凭一次授权连续新增轮次。同一请求沿原身份恢复，重复、过期与并发授权必须拒绝或复用原回执。聚焦回归覆盖两轮失败、无授权拒绝、外部用户精确一次授权、第三轮真实通过或失败后重新升级，以及普通负责人无法自我增加预算。

已有 `passed` 结果若仍有效，任何复查请求都直接复用原结果；候选或实际需求改变使其失效、同时预算已用尽时，复查请求保存明确的 `escalated` 状态与父责任通知，保留原 passed 证据且不创建新轮次，再沿同一外部单轮授权入口恢复，不能停在既不允许复查也无法授权的状态。

当前 provider 读取失败或正在刷新只表示暂时无法确认，不证明 head、base 或需求已变化。两类事实使用同一只读判定明确区分；暂时未知时复查返回等待有界 server 观察的可读结果，保留 passed、原预算与历史，不创建升级通知或要求人工追加预算。回归使用真实刷新水位及读取错误，保持候选与需求不变。
