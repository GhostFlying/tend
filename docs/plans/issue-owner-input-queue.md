# Issue 用户队列与业务进展

## 业务契约

- Issue 输入框旁的队列来自同一会话的真实用户消息、消息投递状态与该浏览器的未发送消息。修复队列读取和渲染对后台批次的依赖。可靠队列、撤回、重试、唤醒、steer 和 urgent 仍走原入口。主会话维持现状。
- 当前进展使用既有外部交付观察与共享审阅记录。复用 PR #347 的交付候选、CI 和冲突投影。审阅摘要展示发布的 verdict 及对应候选，和待处理通知状态分别读取。审阅原件保留在外部交付页。
- 历史中从原始观察或审阅事件按需查询其关联的后台通知。使用持久化的精确事件关联、原生执行记录、读取回执和明确等待原因。只凭候选 SHA、事件范围、队列状态或租约无法确认是否收到或处理。诊断读取失败时，原业务事件和页面仍可查看。
- 本 Issue 从独立分支推进，和 PR #347 负责人对齐接口。候选集成前核对实际基线与投影，验证同一候选的独立审阅和 CI。人工合入。

1. 原故障输入为 20:44 已知的 owner=0、background=3（一个处理中、两个排队）。用浏览器 fixture 模拟这组 API 返回，并确认输入框无后台排队提示，审阅返回、CI 失败和冲突仍直接可见。业务事实变化不依赖后台批次完成。
2. 再加入一条真实用户队列响应，确认计数、状态、撤回语义和发送按钮；分别保存桌面及移动视口截图和运行日志。用现有真实 API/E2E 路径核对用户消息和后台 outbox 的分类，以及通知从排队到真实回执的事实。
