# Worker 会话完整正文

## 业务路径

原 Worker 的同一回复在原生回执中已有完整正文，但管理事件序列尾部仍有正文片段，原 close 要求这些片段先写进会话才肯结清。隔离测试覆盖完整回执、落在同一 Run 的第 47 至 60 条旧事件及原 close 的第 60 条水位。只有片段存活时，从实际状态报告中断。

## 实施

1. 由服务端会话及 Runner assignment 判断文本发布方式。Main 沿原调度和批量直播路径。其他协调会话只发布原生完成的回复 Item；同一 turn、item 的正式通知和历史回执沿原消息身份幂等。中断回执里未证明完成的正文只供执行过程读取。
2. 在 Runner 停止为正文片段分配独立业务事件。全屏原生预览复用既有请求读取当前 Run 的内存片段。尚无正式完成通知的片段可随真实 turn 结束或断开事件保存有界快照，供全屏的采集日志读取。普通任务现有的完整 Item 采集沿用。
3. 旧 Runner 仍可用原序号上传片段。服务端只对有可信 Worker 归属、且不携带工具或终态事实的旧正文事件免除投影确认，已有积压沿原 Run 序列收敛。继续校验物理停机、原 close 游标、租约和未结工具、steer 与业务回执。
4. Worker 页面复用现有会话和 Issue 的执行状态，显示中断与失败，历史已保存正文仍可查阅。移除 Issue 普通面依据正在直播的正文推断活动阶段的逻辑。

## 验证

从 Runner/服务端 RPC 和 Web 的真实消费路径验证同 Run 收敛、回执全文只发布一次、丢失尾部显示中断、原工具与未知命令守卫以及后续准入。区分原生预览、采集日志回退、Main 直播和已保存历史。以实际受影响检查、独立审阅及严格 CI 验证最终合入候选。

CLI 用 `tend run preview <run-id>` 读取原生预览。采集日志中的 Worker 片段通过
`tend run rollout <run-id> --process-text true --json` 显式读取，分页仍使用原 Run 的序号。

## 独立审阅后的修正

锁定原审阅报告的四项问题。升级通过真实 RetainEventJSON 快照验证 schema 139 的内联、
明确默认值和外置正文三种存储形状。只放行有 Worker 归属的明确片段，保持原 seq 及工具、
用量和关闭守卫。

Runner 显式 close 成功时，随原物理关闭回执一次冻结尚未完成的片段，服务端沿原 Run
保存观测，回退读取复用现有窗口但不新增事件序号。原回执的重试和完成判断仍按业务字段。
服务端托管 Worker Chat 复用相同的有界片段缓冲及原会话过程入口，运行中读原内存，
结束时将片段一次写入已采集过程。节流的原生并发活跃度先更新，再处理正文投影。

用原审阅提供的独立失败场景验证，并补测正常入口上的关闭结果、紧接的工作准入，以及
浏览器对完成、中断、原生预览和回退的实际 API 消费。复用原审阅 Task 核对新的候选。

## 第二轮独立审阅后的修正

原生 close 成功并等待事件生产者退出后，使用单独限时的本地 journal 上下文冻结末序号、
已观察片段和原回执。先保留可重投回执，再按原顺序发送已保存事件和 close。取消可以
中断传输，原业务身份和已有回执仍供现有恢复路径读取。真实停止、应用序号和未知回执
继续通过原有守卫核对。回归在原生 close 返回处取消，核对原序号、片段、物理停止和
不打开新原生进程的原回执重投。

app 通过只读接口获取会话缓冲快照。过程投影从 protocol 读取已保存事件需要的字段，
并沿用写入端的正文、Item 和 turn 事件标识。

## 跨版本关闭回执

旧 server 严格解码 manager.native_reply。当前 server 在返回 close 的领取响应中声明
接受过程片段。声明与原生请求分开，旧 Runner 宽容地忽略声明，当前 Runner 在冻结回执
前读取声明。无声明的响应沿用原回执形状，已保存的命令、回执和重投信封保持最初内容。
当前 server 也接受不带片段的原格式回执。关闭、停止及业务应用守卫沿用原决定，普通
关闭和 upgrade park 的关闭均走同一领取入口。

用真实 Runner 验证有无声明时产生的原回执及重投。用真实 Server 测试旧请求复用和旧
回执结清。对照协议 5、6 的旧 decoder，在原进程已停后回放新 Runner 生成的兼容回执。
