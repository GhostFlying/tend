# 业务主链与故障边界验证计划

## 目标

约束辅助能力的故障传播，并用真实 Tend 组件和可控外部替身验证 Issue 从执行、独立验收到用户可见结果的连续性。沿用现有业务身份、授权、原件访问和未知结果对账语义。

## 实施

1. 在工程约定中补充辅助路径的故障边界、业务目标恢复和测试契约，避免引入额外审批或形式化流程。
2. 扩展现有单 slot manager E2E，验证 Issue、Task、Run、独立验收、用户可见结果及资源释放，而不是另建模拟 Tend 内部行为的测试系统。
3. 结合归档与事件链的并行修复，在 runner/HTTP/server 路径注入归档不可读与未知回执，验证工具调用和终态、隔离与恢复；以最终合入实现为准保留真实原件约束。
4. 扩展真实 manager 故障恢复场景，覆盖执行已经停止、事件传递失败、runner 重启和原身份收口。
5. 在共享 PR 审阅及交付链覆盖无关和相关基线变化，验证沿同一责任处理和候选证据准确性。
6. 对测试揭示且属于同一边界的结构性问题做最小修复；其他问题保留证据和后续范围。

## 验证

先运行新增的定向测试和受影响包 race 测试，再对最终候选运行 `make check TEST_COUNT=1 CHECK_JOBS=0`、独立 review 和 PR 所需 CI。最终候选基于最新 main 验证后按仓库规定 rebase 合入。线上部署和真实模型冒烟不在本计划内。

## 业务契约与审阅范围

涉及执行、恢复或交付边界时，在现有实施计划或 PR 说明中写清本次实际路径：

- **故障起点**：原业务身份、已发生和未确认的动作、物理执行与消费状态。例如旧 Run 已停止，但原回执未消费，后继消费者尚未附着；不能只写“恢复失败”。
- **目标终点**：原责任在该事实下应能做到什么。原件可读、停止资源归还、同 Task 续行、安装结算和最终发布是不同终点；未知业务结果继续保真，不能为满足测试强行成功化。
- **调用路径和验证**：指出从该起点进入的真实组件、相关回归入口及实际断言。说明哪些是外部 provider、进程、网络或时钟替身，哪些内部状态由 fixture 直接预置，哪些恢复步骤由正常接口驱动。

测试可以预置某个边界来隔离局部契约，但其效力从该边界开始。直接写入 completed 批次再测试继续资格，不证明安装和结算；先替系统补 pending 或清理 attachment，再测试唤醒，不证明停止到交接。缺陷回归优先从正常入口复现原失败并驱动恢复；相关的原 Task、动作、序列和副作用身份保持可核对，外部未知不因 fixture 简化而消失。

独立 review 在原有审阅中沿本次声明的路径核对入口、关键转换和终点，检查 fixture 是否跳过了可能失败的步骤。结论区分“完整差异已审阅”与“哪条业务路径有源码和测试支持”，缺失覆盖如实说明。后续增量复用原审阅并按实际影响补查，不要求每次修改遍历所有历史故障，也不增加审阅轮次、审批表或额外 CI 门槛。

已有 `TestEndToEndSingleSlotManagerDelegatesAcceptsAndCloses` 验证单 slot 委派、独立验收、报告交付、最终通知和 Issue 关闭；其交付物是有限报告，不涉及代码合入与部署。自动部署、同 owner Task 结算或维护后已有安装恢复，需要在已有 App/runner/E2E 构件上覆盖相应真实分支。不能将使用不同授权、Task 类型和安装来源的几个绿色局部测试拼成同一全链通过。

## 恢复与后续修复的选择

先读取原操作的实际结果和依赖范围，再评估现有正式接口是否能在当前授权内恢复原目标。升级的具体分流见 [受阻交付的恢复](../operations/controlled-upgrades.md#受阻交付的恢复)。已有路径可用时，完成当前交付并单独记录长期产品缺口；现有接口不能表达实际恢复时，指出具体缺失的转换和所需证据，再决定同故障链的修复范围。不得以新增通用能力、清空所有历史 unknown 或重复已完成部署作为默认前置条件，也不得为推进绕过真实未知副作用和权限。
