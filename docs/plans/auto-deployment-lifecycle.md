# 自动授权部署生命周期一致性（D231）

## 问题与目标

Issue 已有明确的自动合入和固定部署目标授权，当前候选经过独立审阅、检查和正常责任绑定后，受控升级启动仍只读取人工答复；已绑定升级完成后的责任校验也有同样分叉。结果是有效自动授权无法完成实际安装，修复启动后仍可能无法正常消费安装完成事实。

本计划只统一这些现有授权消费者。人工批准继续校验原始、精确且未撤回的答复；自动授权继续校验既有政策、来源、仓库与部署范围。不得构造人工答复、扩大授权、替换原 Task 或重放未知升级。

## 实现

1. 在升级启动的原责任、代次与独占目标检查中，使用既有 `store.DeliveryGrantValid` 验证当前冻结授权，保留部署候选、原执行绑定、真实租约、源文件身份、实际 provider/部署基线及目标一致性检查。
2. 对已经绑定的升级完成责任，使用同一授权校验。未完成、失败或 unknown 批次不成为完成证据；原人工答复失效或自动来源/政策/范围撤回仍不恢复执行。真实数据库/IO错误继续传播，普通授权失效按现有调度语义返回不可继续。
3. 设计决策同步记录 D231。无 schema、协议、CLI、政策格式、权限或历史迁移变更。

## 验证

先保留未修复版本的真实 App 回归失败，再验证正常自动授权从受控启动到原批次完成后的同 Task 续行/结算。覆盖人工允许与拒绝、自动授权撤回/来源失效/目标越界、失效责任或候选、未知批次和重复启动的拒绝路径。优先复用真实政策、审阅、绑定与租约流程，外部 provider/物理安装仅使用现有替身。

按影响范围运行 focused race、vet、格式检查，保留所有失败和终态证据。提交后的最终候选必须经过独立整 PR 审阅、一次完整 `make check TEST_COUNT=1 CHECK_JOBS=0`、自然触发的精确候选 CI 与保护聚合，再按最新 main 适用性合入。旧候选结果不能替代新候选验证。

## 恢复边界

源代码、门槛通过、实际安装和业务交付分别证明。维护发布应包含已经合入的业务修复，并在新的实际部署基线下使用完整 format 2 发布集。真实安装证明完成后，由原 Issue owner 核对源码包含关系和原交付责任，按正常接口对账；原拒绝请求、失败与 unknown 保留，不能重复旧启动或以旧包覆盖维护发布。实际业务结算和最终报告仍由原 owner 完成。
