# 本地完整检查的有界并发

Refs: D149，延续 D145、D148。

## 依据与验收

现有本地完整检查从其他 Go 包、E2E 到 App 分片依次执行，最后检查 Web；上一完整样本约 25 分 15 秒。Go 包阶段约 8 分钟、E2E 522 秒、最慢 App 分片 378 秒，阶段叠加主导耗时。固定顺序没有根据执行机器的容量调整。Web 构建会清空 Go embed 使用的输出目录，需要先隔离产物才能并发。

默认 make check 保留格式、能力覆盖、协议检查、vet、staticcheck、完整 race、Web 类型/lint/格式/单元测试和构建。目标是有界重叠独立检查，避免把多个重阶段的时长相加；完整未缓存测试的验收以真实并行运行及 E2E 稳定性为准，不把 Go 原生缓存命中解释为调度收益。

## 实施

1. 增加仅使用标准库的本地完整检查调度器，复用现有 Makefile 静态/Web 入口和五个 race 分组。按可用 CPU 选择有上限的并发数与 App 分片；支持显式降低并发和顺序回退。低容量机器保留 E2E 独立阶段。
2. 约束每个 Go 子命令的包并行度，汇总所有失败，拒绝因某组失败跳过其他必需检查；取消时停止本调度器拥有的子进程并等待清理，不操作其他会话。
3. 本地完整检查将 Web 构建定向到每次调用独有的临时目录，待全部检查结束后清理；显式 make web/web-check 保持原构建入口。Go embed 读取的目录在检查期间保持稳定。
4. 对调度预算、低容量隔离、任务全集、失败汇总、取消清理及构建目录隔离做有效测试；复用 CI 原有 race 分组和浏览器验证，不新增检查绕过路径。
5. 冻结候选，真实执行一次完整检查并记录耗时；规定独立 review、PR CI、最新 main rebase 后合并。上一组 CI 的暖缓存验证继续独立完成。

## 本地入口

- `make check`：按有效 CPU 自动选择预算，完整检查；Web 在私有临时目录构建并清理。
- `CHECK_JOBS=1 make check`：顺序回退，自动 App 分片也降为一个。
- `APP_TEST_SHARDS=4 make check`：显式选择 App 分片，组并发仍可独立调整。
- `TEST_COUNT=1 make check`：强制重跑 race 测试，用于衡量真实调度耗时；日常默认保留 Go 原生缓存。
- `make web` / `make web-check`：默认仍在原嵌入目录生成构建产物。

并发预算使用 Go 的有效 GOMAXPROCS，包含运行环境的 CPU 配额约束。组数量最多七个、自动 App 分片最多四个；每个 Go 子进程的运行并发、包并行与 Vitest worker 也有上限。小于 32 个有效 CPU 或选择顺序模式时，E2E 保留独立阶段。

## 验证结果

高容量开发机上的最终候选使用 `TEST_COUNT=1 make check` 强制执行全部 race 测试，完整检查通过，耗时 552.5 秒（9 分 12 秒）；对照的既有四分片检查记录为 25 分 15 秒，约缩短 64%。本轮日志中没有缓存的 Go 测试结果。各组质量/Web/App/API/其他/mainthread/E2E 分别约为 46/56/415/416/525/530/552 秒，E2E 在并发环境中通过，整轮时长由最慢组决定。

预算、任务全集、失败汇总、低容量 E2E 隔离、取消清理及指定 Go 可执行文件的回归通过。规定独立 review 的 Go 路径传递意见已采纳，修正后的复审没有新的可操作问题。运行时长是单次完整实跑样本，日常仍保留 Go 原生缓存。
