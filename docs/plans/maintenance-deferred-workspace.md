# 已确认暂不释放的 workspace 不阻塞维护

依据 D84。本计划修复已完成 run 的 workspace release 在任务仍非终态时造成的维护依赖环，不改变资源归属、任务调度或升级排空标准。

## 实施

1. 核对服务端 `released:false` 的确切语义及终态／脱离绑定后的重新扫描路径。
2. runner 收到成功且可解码的 release 回执后，清除该次本地 release 意图与请求。`released:false` 表示此次已确定未释放；真实资源继续由服务端原任务占用，不伪造停止或释放证明。网络未知、业务错误、不可解析回执继续保留原请求身份和意图。
3. 通过实际 app/runner 协议边界的回归覆盖：维护中实现完成、验收排队而 runner 可以 ready；恢复后验收完成和取消无新 run 两种终态路径由扫描重新排队并释放；服务端已处理但回执丢失仍沿原身份重试；held／unknown 不因此变为 ready。
4. 先用旧行为运行新增关键测试确认失败，再应用最小修复，运行相关 runner/e2e race 与 vet。根 agent 负责完整检查、独立 review、CI 和上线。

## 不变量

- 只有成功且已解码的明确回执可清理本地意图；不能以超时推断未生效。
- 清理本地重试意图不改变服务端占用、保留资源或持久停止事实。
- 后续终态扫描依赖现有真实 journal 停止证明；缺失、held、fenced、unknown 或活动写入仍阻止相应资源释放及必要的维护。
- 不放宽 `pending_operations` 或 runner 升级 ready 的检查，不绕过原工作目录验收的绑定。
- 本次不改变 wire 字段、请求有效性、服务端响应或默认业务语义；修复客户端对既有明确响应的本地队列处理。

## 验证记录

新增真实 HTTP app/runner 回归在修复前确认两条路径均因维护无法 ready 超时；明确 deferred 以及丢回执重试单元回归同样在旧代码失败（本地 release 意图仍为 1）。修复后验收排队时资源仍占用，但 runner 可 ready；替换 runner 后独立验收自然完成，或 owner 取消后没有新 run 也可由现有终态扫描恢复释放。只有成功可解码回执清理意图；丢回执、错误、畸形结果及当前 held/未确认原生操作继续保留必要阻塞。维护安全短路期间不主动重复扫描无变化资源；恢复普通运行或新 runner 首次扫描会重新发现终态资源。
