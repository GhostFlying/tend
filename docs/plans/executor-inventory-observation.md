# 执行器观测与探活隔离

Refs: D143、D149、D159。

## 问题与边界

`Pool.Observe` 与 `ObserveRetained` 在适配器锁被探活占用时返回成功的空列表，
心跳会把它作为真实库存覆盖。探活的外部 IO 不应阻塞心跳，也不能把暂时无法取得
适配器锁解释为执行器已不存在。本项仅修复 runner 内部观测机制，不变更业务定义、
调度、原 Run、冻结 pin、请求身份、CAS 或未知操作的对账。

## 实施

1. 用可控、可取消的假探活冻结 Refresh 或原 manager 解析；先证明已有当前库存与
   原 retained 库存在并发观测时会变成虚假空列表。
2. 适配器初始化及解析继续沿现有互斥锁串行执行；另用短锁发布不可变的逐 snapshot
   观测副本。观测不等待外部探活，不因适配器锁繁忙返回空库存。
3. 当前库存始终绑定 `Source.Status` 的精确 snapshot。尚未初始化的新 snapshot
   只产生自身的未就绪定义，不能借用旧配置的阳性。拒绝及探活完成后及时发布状态。
4. retained 库存继续仅由 server 引用的完整原 pin 集合决定；替换集合立即撤销旧
   观测，刷新发布仍校验同一集合，不从当前配置替代历史定义。
5. 保持既有 normal/maintenance 准入门、N/N−1 wire、字段和默认语义。本项不新增
   公共能力或 CLI 命令，也不缓存或重放整个心跳。

## 验证

- 定向 RED/GREEN：并发 Refresh、原 manager 解析、心跳使用的两个观测入口，
  初始未就绪、完成后新状态、真正空配置、disabled、新私有配置、拒绝及 retained
  集合变化；取消所有假探活并等待退出。
- 运行 agentexec 定向与整包 race 检查，以及既有维护准入定向回归。使用受限 CPU、
  私有构建及临时目录；完整本地检查、独立 review 和 required CI 由统一交付调度，
  只对最终精确候选作通过声明。
