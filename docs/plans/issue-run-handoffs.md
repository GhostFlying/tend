# Issue 消息交接与分轮执行（修订草案）

状态：用户已授权按自动上层 Issue owner 实施。当前责任路由候选在完成本修订前暂停合入和发布。

## 目标

Agent 持续承担 Issue 责任，每次 Run 仅执行一轮。需要其他负责人判断时，将问题、证据、待判断事项及接续位置持久保存到 Issue 讨论，结束本轮并释放执行容量。责任与会话上下文保留，等待期间没有存活的执行进程占用 slot。负责人处理后通过显式回复与接续决定触发下一轮执行。

独立任务各自对应子 Issue；Task 保留冻结合同与独立验收语义；Run 是该合同下的一次执行。交接结束本轮不等于交付完成、验收通过或 Issue 结清。不同 Agent 的会话及实现/验收角色继续隔离。

## 交接过程

1. A 原子保存问题正文、来源 Issue/Task/Run、当前责任版本和交接意图。讨论呈现为 A 将问题提交负责人 B，身份由服务端根据责任链确定。
2. Runner 停止本轮原生执行并持久报告真实结束事实。收到可确认的退出和必要清理事实后才释放容量；报告丢失、仍有活动执行或 unknown 时先对账，不仅凭留言将 slot 视为空闲。
3. 服务端持久唤醒 B，由 scheduler 排队、runner 领取并由 harness 启动。唤醒意图可以先保存，交接状态须防止旧 A 的执行继续产生控制副作用。调度仍遵守实际容量，不引入额外协调名额。
4. B 阅读原问题和证据，在授权内答复、修正计划或逐级上报。需要继续 A 时，保存明确的接续决定与对应回复，触发 A 的新 Run；B 本轮同样正常结束、释放容量。
5. A 的新 Run 读取原问题及有效答复，按冻结执行身份、合同和 workspace 规则恢复。原生会话可恢复时接续历史，否则明确记录上下文重建；旧 Run 不复活、旧凭据不再写入。
6. B 无法处理时继续交父 Issue owner，再到唯一主协调 Agent；遇到人工 owner，或顶层明确无法解决时，才形成用户待办。人工等待同样不占执行 slot。

A 若正在执行当前 Issue 的具体合同，B 是该 Issue 的协调负责人；A 若已经代表子 Issue owner 作责任判断，B 是父 Issue owner。两个位置不引入另一条 worker 管理层级。

## 消息与调度边界

留言是用户可见的交接记录；持久的接收身份、来源问题、版本和接续意图决定实际调度。普通进展、归档、已读和自发回声不自动拉起 Agent。不能通过任意文本 @ 绕过责任链、改变 Issue owner 或取得其他 Issue 的编辑权限。

同一责任与角色不并发运行两个互相冲突的回合。回复提前到达时保存待接续输入，待旧执行退出后领取；重复请求、重复消息、进程重启和回执丢失只接续一次。改派、重挂、撤回、合同失效之后，不再以旧回复启动过期工作。

执行 slot、workspace 占用和原生会话历史分开记录。释放计算容量不代表可以让另一个执行并发修改尚未交接的 workspace；恢复需继承原环境身份与互斥规则，不能悄悄更换环境。

## 对既有候选的修订

- 保留原问题身份、责任链、Agent 与真实人工来源区分、逐跳审计、CLI 能力及 Inbox 过滤的合理部分。
- 替换 D89 的原 Run 持续等待/长轮询路径；撤销 D150 候选中的额外协调名额设计。D128 的分轮等待释放容量原则扩展到需要交接的具体执行。
- 增加真实交接终态、退出确认、持久接续及新 Run 的围栏，而非仅从容量统计中排除仍活着的执行。
- 接续不是实现失败重试，也不是新独立任务；需明确区分回合数与实现/验收尝试额度，不能因每次交接误耗实现次数，也不能借交接绕过已有尝试上限。
- 原 ask_owner 的默认语义改变，必须评估协议升级或单独协商的新合同。历史活跃 Run 保留其真实合同并受控排空/迁移，不把旧 Runner 未实现的交接能力当作已具备。
- Web/API/CLI/具名工具同步呈现交接、等待负责人和接续历史，任务业务完成与本轮结束明确分开。

## 实施顺序与验收

先定义交接/接续状态、权限和协议合同，再实现 app 单事务与事件、runner/harness 退出回执及接续、调度与 workspace 互斥、CLI 与页面投影，最后迁移并验证既有未决问题。设计决策需随实现修订，不将本草案标记为已实现。

核心验收是在单 slot 主机完整完成 A → B → A；每次等待期间实际进程已退出、容量回收，历史上下文和问题身份保留。覆盖多级上报、人工中间层、重复投递、退出或答复回执丢失、重启、改派、合同变更、unknown、workspace 冲突及独立验收隔离。

## Multica 源码参照

本次阅读本地源码提交 `188971168d0e2a6fa7796f8825e2ed096ccc5fe3`，未据此断言上游最新版本行为：

- `server/internal/handler/comment.go`：明确 mention 路由到接收 Agent，并支持排队合并、活动回合补充或延后处理；普通 Agent 留言不一律触发新运行。
- `server/internal/service/task.go`：mention 创建新的执行队列记录，完成记录保留原生 session/workdir 信息。
- `server/internal/daemon/daemon.go`：先取得实际 slot 再领取执行；终态回调及清理结束后释放 slot 并唤醒调度。
- `server/internal/handler/daemon.go`：后续执行可读取同 Agent/Issue 的原 session；不具备恢复条件时不假装连续。完成对账补接未覆盖的留言。
- `server/internal/service/issue_wakeup_join.go`：同 Issue/Agent 的事件回合串行，合并待执行输入，避免自身事件反复唤醒。

Multica 不保证“发出任意 @ 留言就自动结束发送方 Run”。本草案采纳其消息触发下一轮及上下文接续思路，并为 Tend 的责任交接增加明确的结束/接续合同。

## 本次执行合同

使用可选 `issue-question-handoffs-v1` 冻结每个 Run 的交接合同，wire 维持 2/1：未协商的历史 Run 保持 D89 行为；新字段和 `runs.yield_question` 仅向已协商执行启用。提问先保存交接意图，Runner 确认原进程停止后按稳定请求报告交接；原 Run 结束，Action 在原问题答复前保持不可领取。答复与退出可以任意先后到达，两者均持久后才创建原 Action 的接续 Action。新 Run 沿用原 generation，不增加实现尝试额度，保存前序 Run 与原问题引用及原生 thread；接续 Action 使用唯一问题身份去重，保留原 generation、spec 和 artifact；固定原执行配置和主机，保留 workspace 互斥。

代表 Issue owner 的具体执行提问自动交父 Issue owner；历史未绑定 owner 的执行仍先交所属 Issue 的协调负责人。负责人继续无法处理时逐级上报。撤销所有额外协调容量。新增迁移 76；迁移 75 保持已提交内容不变。

旧合同容量对账：若所有实际配置槽位都由不能交接的旧问答占用，且当前接收负责人也固定在同一主机，系统记录该容量阻塞并沿原父链提交给可接手的上级或托管主协调。遇到人工 owner 仍停在该层；原问题、旧答复合同及槽位事实保持不变，主协调无法处理时才形成用户待办。等待交接的原执行快照继续参与保留交换，库存移除不使原合同失去接续配置。

交接提交会释放租约；HTTP 回执丢失后，原 token 仅可重放同一 Run、request ID 与 payload hash 已成功提交的交接请求，不能发起新请求、修改 thread 或读取历史 Run 的执行接口。端到端验证同时覆盖实现和独立验收的交接、重启与回执丢失；旧等待契约通过未声明新能力的运行时观察单独验证。
