# 主会话待处理队列与工作项跟进

状态：实施中。Q1 服务端队列、撤回与历史隔离已实现并通过独立 review；Q2、F1、F2 待交付，尚未部署。

Refs: D11、D27、D69、D70、D74、D81、D88、D90、D91、D94、D97。
实施各阶段时，在同一变更中向 `docs/design.md` 追加对应的新决策，分配当时可用的 D 编号。

## 1. 目标、现状与范围

主 Agent 是唯一的目标协调者：理解 owner 意图、维护计划、派发执行、核对成果和决定下一步。
程序负责持久化、事实观察、条件判断、时间触发和可靠投递；本期不增加独立 PMO 或巡检 Agent。

本期交付两个连续的闭环：

1. 用户发送的消息明确显示为待处理，可在尚未领取时撤回、取回编辑；真正开始处理后才进入对话正文。
2. 主 Agent 能把“等什么、什么时候回来、回来做什么”登记为工作项跟进安排，等待不占 worker slot，触发后进入同一主会话队列。

用户已选择：独立待处理区放在输入框上方；支持撤回及取回编辑。默认发送仍然排队，不变成插入当前 turn 的 steer；本期不做拖拽排序、抢占执行或合并用户消息。

### 已核对的基础

- `internal/app/event_wake.go` 已有同事务 outbox 唤醒；完成、待决及工作项选择回答走现有主会话。
- 完成事件已经留下工作项 completion review；交付观察也能产生主会话通知。普通进度及心跳不应新增模型调用。
- outbox 对已领取投递、前台消息及交接、后台事件分优先级，同组保持提交顺序；主会话串行运行，unknown 不盲目重放。
- 当前聊天按接收 seq 展示全部消息，`queued` 文案为“已收下”；`starting` 仍可能投影为 queued。仅按这个状态隐藏或允许撤回不可靠。
- 现有停止接口只作用于已建立的 turn；本机 IndexedDB 发送队列与服务端执行队列是两个不同阶段。
- 工作项 follow_ons 保存责任及证据，没有条件、到期时间和可执行的唤醒规则。

### 本期与后续边界

本期包含队列服务端与 UI、跟进规则及有限周期检查、等待状态展示、后台事件合并与静默结果、重启及跨设备恢复。
条件只使用已经保存的任务、交付、待决和工作项选择事实。
CI/review/冲突观察、跨工作项订阅、任意 webhook、通用 cron/Autopilot、全局周期复核、独立检查 Agent 和工作流编辑器留待后续，不属于本期验收条件。
本期主动唤醒仅支持托管主 Agent；外挂可以读取跟进事实和待处理记录，但没有宿主启动 turn 的能力时，不宣称能够后台执行，也不开放创建主动跟进规则。

## 2. 聊天队列与撤回

### 2.1 服务端队列是事实来源

新增 owner 只读队列入口 `GET /api/v1/conversation/queue`。通过一致读事务投影 outbox、主 turn、消息控制记录和托管状态，不从聊天当前页推断队列。
响应包含当前处理项、用户待处理项、后台待处理项、各类总数、读取水位、托管是否启用及可核实的等待原因。
每项包含稳定身份、原消息引用、接收时间、控制 revision、领取/处理状态、能否撤回及不能撤回的原因；附件使用现有元数据引用。
分组列表分页，默认每组 50 项并返回后续游标和准确总数；分页期间状态变化由重新读取及稳定 ID 去重处理，不承诺跨多次请求的冻结队列。

队列排序复用真实投递优先级：已领取项优先，待领取 owner 消息与交接保持既有顺序，后台事件随后；用户区内按服务端接收顺序。
交接、升级排空、托管不可用等真实阻塞显示为状态条，不伪装成用户消息。不提供基于猜测的预计等待时间。
未送达的本机消息单独标注，不能标为全局“第 N 条”；多设备先后以服务端提交顺序为准。
只有实际具有主会话投递的消息才算排队，已直接记录的 owner 选择答案、纯通知不能因缺少 state 被误判为 queued。

### 2.2 撤回与领取互斥

新增 owner 写操作 `conversation.withdraw_message`，以 message 为 target，携带 request_id 和 `expected_control_revision`。
消息控制记录保存 revision、撤回时间及来源，关联原提交请求及投递身份；不修改原文或删除附件、请求和审计历史。
前台消息入队、投递领取和撤回都经 app 事务更新这份记录。领取与撤回只能有一方成功。

- 可撤回：对应投递仍 pending，且不存在未确认启动或活动 turn。
- 不可撤回：已经 sending/starting/processing、投递 unknown、已经处理或失败终止；返回当前事实。starting 显示“正在启动”，不能继续冒充可撤回的等待项。
- 已确认被 harness 拒绝、投递安全退回 pending 后可再次撤回；unknown 不能靠退队恢复成可撤回。
- 撤回成功在同事务中将尚未投递的 outbox 标为明确取消的内部终态、写消息控制事实及事件；不使用 delivered 或 failed 伪造取消。
- 领取后、调用 harness 前再验证准入记录，撤回失败不能在前端假成功；守住 StartTurn、重启恢复及交接恢复的所有入口。
- 同一请求重试返回原结果；新请求遇到已经撤回的同一消息返回已有撤回事实，不能再生成副作用。

新队列视图使用明确的 withdrawn 状态。原聊天 API 维持既有 MessageState 枚举，撤回映射为 interrupted，并增加可选撤回元数据供新客户端精确标注，避免旧客户端遇到未知状态失效。
历史消息控制记录通过追加迁移从实际消息、outbox、turn 回填；没有运行证据时不伪造开始或完成时间。

### 2.3 本机发送与取回编辑

发送队列新增“提交请求已尝试”持久标记，在第一次消息 HTTP 调用前保存。附件上传与消息提交分别记录，abort 网络请求不代表服务端未收到消息。
同一浏览器多标签页的提交和本地取消共享发送互斥；优先用 Web Locks，缺少时用 IndexedDB 事务租约协调。旧记录没有尝试标记时按可能已提交处理。

| 当前事实 | 允许的行为 |
| --- | --- |
| 尚未尝试消息提交 | 在本机互斥范围内取消发送；可以直接取回文字和附件 |
| 正在提交或提交结果未知 | 保留记录，先按原 request_id 对账；不得删除记录并声称撤回 |
| 对账尚未找到请求 | 不足以证明不存在在途提交；保留未知，同 ID 完成对账/幂等提交后再尝试服务端撤回 |
| 已送达且服务端尚未领取 | 调用服务端撤回，确认后才移出等待队列 |
| 已经启动或处理 | 不取回为“成功撤回”；显示实际状态和既有停止入口 |

“取回编辑”是撤回后建立新草稿，不是原地更改已提交消息。新发送使用新 request_id；原请求、原文、原附件关联保留。
撤回意图、请求信封和待恢复内容先持久化到 IndexedDB，成功回执与草稿恢复之间崩溃时可重启接续。
普通草稿和被暂存草稿也持久化；输入框已有内容时将它保存为独立暂存草稿，取回内容进入输入框并提示“原草稿已暂存”，提供恢复入口，不静默拼接两条不同意图。
草稿恢复以撤回请求身份去重，不因重复 SSE 或刷新追加两份文字/附件；跨标签页领取恢复动作，其他设备不会自动改写本机输入框。

附件草稿支持本地 File/Blob 和已保存的 attachment 引用。已上传原件复用 file_id，不强制下载或重新上传；未上传内容保留 Blob。
旧图片沿现有读取/上传能力转换为可发送附件，失败保持可恢复草稿，不静默丢图。取回时保留原 reply_to；重新发送的 last_seen_seq 使用用户届时实际看到的原始账本水位。
若原消息携带 decision 选择，恢复为可见待确认选择，发送前重新校验其版本；已失效时保留文字和附件、移除失效选择并明确提示，不能暗中重放旧答案。

### 2.4 正文按处理轮次组织

新增 Web 专用 `GET /api/v1/conversation/transcript`：按稳定展示块分页，块包含触发消息、与其关联的工具及回复，使用 reply_to/turn 身份归组。
原 `conversation` seq API 和账本顺序继续用于审计、工具读取及水位；不重写原 seq、发送时间或历史原文。

- 未开始的 owner 消息只在队列显示；starting 留在队列并禁止撤回。确认 processing 后进入正文。
- 单个处理轮次内部按原 seq 展示，不把随后排队的新输入插到上一轮回答中间。
- 新处理块在首次确认开始时分配持久展示序号；无需 turn 的系统事实在产生时获得独立展示块。旧历史按可恢复的开始事实及原 seq 确定性回填，无法恢复时明确保留历史排序，不编造时间。
- 启动前失败或 unknown 的消息进入明确异常块，不能消失，也不能显示为已处理。已经撤回的消息放入可展开的撤回历史，保留正文和附件读取入口。
- 一页默认 20 个展示块；单块内容仍分页，默认 50 条，防止长工具轮次无界响应。流式输出按 message_id/revision 合并，关联父块未加载时先获取父块，不能挂到最近一个回复下。
- 纯通知仍按事实到达展示；有后台处理的通知保留其源记录，通过处理块引用关联，不复制多份全文。

UI 位于输入框上方，最多直接显示三条待处理消息，其余展开；长文本折叠、附件保留预览/下载入口。
存在待处理 owner 消息时自动展开用户区；后台区默认折叠为数量和最早等待时间。手机限制队列高度并内部滚动，保留输入框和当前回复空间。
agent 忙碌时发送按钮及辅助文案表达“加入队列，当前回复结束后处理”；空输入仍支持停止当前回复，有输入时提供独立停止入口，停止不清空后续队列。
连接断开保留上次快照并标为非实时，结果未知继续展示。SSE、重连、恢复前台触发读回；旧请求响应不能覆盖新水位状态。

### 2.5 历史及授权边界

`conversation_read`、上下文构建、交接包及预备摘要识别 queued、starting、withdrawn。
未投递及已撤回 owner 正文不能作为当前有效执行指令注入；工具历史默认只返回其状态和身份占位，原文保留在 owner 审计读取面。
已执行消息继续可回查。撤回更新会话内容版本，使旧预备摘要失效；新交接显式携带撤回事实，不能复用未反映撤回的摘要来恢复授权。
这不承诺抹掉模型此前读到的内容；已经启动的消息必须用停止和新的 owner 指令纠正，不能借撤回删除既成事实。

## 3. 工作项跟进规则

### 3.1 责任与唤醒分开

新增独立 FollowupRule，不复用执行 task、PlanAction 或 worker run 表达等待，也不把 follow_on 的 resolved 状态用于记录定时器是否触发。
每条规则属于一个 work item，可引用其中一个 follow_on，保存目的/唤醒指令、来源、控制 revision、触发条件、有效期及历史。
目标固定为托管主 Agent，不开放任选 agent 或第二协调者。owner 与主 Agent 可以管理，worker 无此权限。
主 Agent 只能为已有授权目标登记必要跟进；模糊的“以后再说”不自动转换为无限催办，未授权的新工作继续保留建议或选择。

第一版触发类型：

| 类型 | 行为与默认值 |
| --- | --- |
| at | 一次性时间，API 使用 UTC 时间；UI 输入和展示使用用户明确选择的 IANA 时区。已到时间立即进入候选，不悄悄改期 |
| every | 固定时间间隔，最小 5 分钟；必须有 expires_at，默认最多触发 20 次。24 小时表示固定时长，不承诺夏令时地区每日同一当地钟点 |
| condition | 对已有账本事实的一次性条件；默认等待 7 天，到期唤醒一次说明条件未满足，可显式选择到期静默结束 |

条件枚举限定为：同工作项关联任务全部 completed、指定 delivery 为 merged 或 closed、指定 task decision 已回答、指定 work-item choice 已回答。
取消任务不满足 completed；closed 与 merged 分别匹配；新任务、新交付不会因后续关联变动自动加入冻结的目标集合。目标被替代或失效时标为需核对，不改指向替代对象。
只读查询失败或观察未知不能满足条件。基于交付观察触发时携带 checked_at 和提交身份，主 Agent 判断新鲜度及是否需要刷新。
condition 不接受任意表达式或纯文字谓词；多个任务仅提供 all，不引入通用 AND/OR 编辑器。

### 3.2 API、存储和工具

新增读入口 `GET /api/v1/work-items/{id}/followups` 与规则历史读取；在 WorkItemView 增加跟进数量、等待摘要、下次检查时间，不嵌入全部历史。
写操作使用现有请求信封：`work_items.followups_create`、`followups_update`、`followups_pause`、`followups_resume`、`followups_cancel`、`followups_trigger`，工具面提供对应能力。
创建校验工作项 revision；后续修改校验规则 revision；同事务校验工作项当前仍允许该操作。
规则状态使用 active、paused、finished、cancelled；派发与运行状态另行投影，不把“已触发”显示成“已处理”或“承诺已兑现”。
新表分别保存规则、匹配事实/到期 occurrence、背景处理批次及其关联，引用既有消息/outbox/main_turns；追加索引支持按 next_due 查询，不全表扫描历史。
规则建立、修改、取消和恢复均保存历史及来源；更新不覆盖已经启动轮次的输入。

### 3.3 触发与投递

事实变化在原 app 事务写匹配凭据；创建条件规则时在同一事务检查当前状态，解决先完成、后订阅的竞态。
定时扫描使用服务端可取消循环，默认 30 秒检查一次，仅访问账本、不调用模型；判定函数保持纯逻辑，时钟和 ID 注入。
规则匹配、occurrence 去重、派发记录、消息/outbox 和规则水位原子提交。一次性键绑定规则及 revision，周期键绑定计划时间；并发扫描只产生一个 occurrence。
停机期间错过的周期合并为一次待检查，不逐次补跑，下一次从当前时间计算；一次性到期事项在恢复后仍可执行。
有同规则未结束 occurrence 时合并新周期；unknown 保留并暂停该规则后续派发，先对账，不把下一次周期当成重试通道。

触发只唤醒主 Agent 重读当前事实，不直接创建执行任务、决定验收、合并或部署。
主 Agent 可以继续已授权工作、记录等待条件或提出真实 owner 决策；规则到期本身不扩大授权。

### 3.4 生命周期与暂停

- 修改规则递增 revision，撤销旧版尚未领取 occurrence，重新求值；已领取轮次继续带旧来源并在行动前读取新版本，过期安排不能继续授权动作。
- 暂停/取消只阻止之后触发并撤销尚未领取输入；不能假装停止已启动轮次，需要时由 owner 使用既有停止入口。
- 工作项关闭终止其规则和未领取输入，保留全部历史；重新打开不会自动恢复旧规则。
- 工作项 snoozed 暂停普通条件和周期触发；允许显式登记的一次性“到时重新核对”规则唤醒主 Agent，但不自动改变 snoozed 状态或启动执行。
- 恢复周期规则从恢复时刻安排下一次，条件重新检查，一次性已过期规则需明确设置新时间或手动触发。
- 次数在 occurrence 成功入队的事务内计入，合并同一 occurrence 不重复计数；到期或次数用尽后结束规则，已经入队的本轮仍保留实际执行状态。暂停/恢复不重置累计次数。
- expires_at 与条件同时满足时，若同一事务能证实条件已满足，记条件触发，否则记超期触发；每个一次性规则只触发一次。
- 手动触发只执行一次检查，不重置期限、次数或周期。关闭、取消或权限不满足时拒绝；它仍不代表扩大工作授权。

## 4. 后台事件、等待展示与恢复

### 4.1 复用并合并后台唤醒

已存在的完成、待决、选择回答和交付变化继续默认工作，不要求主 Agent 为每个任务重复订阅。
增加后台处理批次：相同工作项且尚未领取的默认事件和 followup occurrence 汇入同一个批次，保存全部源 event/message/规则引用；无唯一工作项的事件按原业务对象单独归组。
同一源事件关联多个工作项时，各工作项分别保留核对责任，不能为了减少轮次遗漏其中一项。
批次冻结后新输入进入后续一个待处理批次，不修改已投递 prompt，不抢断当前轮次，也不合并 owner 消息。
批次保留一个规范触发消息，回复关联该消息；其他通知保留原身份并指向同一批次。批次结束更新投递处理状态，但不自动确认 completion review 或解决 follow_on。
输入有界，只携带最新快照及源索引，源记录完整保存且可分页查询；不能静默丢掉待决答案或用户约束。

主 Agent 的自产工具事件不唤醒自己。规则每次派发受期限/次数限制，普通进度及心跳保持不唤醒，明确条件只在当前 revision 满足一次。
用户输入优先，后台排队时间可见；本期不引入后台抢占或自动插队，避免改变用户正在对话时的处理顺序。

### 4.2 静默检查与 UI

新增受当前后台 turn 身份约束的 check-in 工具，允许记录“没有新变化/继续等待”及证据引用，并正常结束本轮而不发布普通聊天回复。
静默结果进入规则执行历史，连续相同结果在 UI 折叠；不会写普通聊天消息再递归触发自身。原始检查记录保持可追溯。
静默 check-in 不能消费未核对的完成记录、回答待决或隐藏选择卡；这些业务状态仍须使用原有工具明确处理。
有实际新结果、可执行下一步或 owner 待决时，沿现有聊天/选择卡呈现。运行结束只表示本轮结束，不代表全部业务责任完成。

工作项详情新增“跟进安排”：等待条件、下次时间、期限、触发次数、最近结果、暂停/恢复/取消/现在检查及历史。
表单仅提供本期条件枚举、一次性时间和固定间隔；现有授权下主 Agent 可自行登记，owner 也能直接创建和调整。
工作项卡片显示最相关的一条等待摘要与其余数量，不把等待标为 running；未来规则留在这里，到期产生真实待处理批次后才计入聊天后台队列。
选择、待决、承诺、规则互相链接；单纯没有活动 task 不显示“异常”或自动催问。

### 4.3 一致性、可观测性和兼容性

队列及规则视图共享 SSE 失效通知、事务水位、读取代次保护；重连和前台恢复重新读取，历史分页不决定实时计数。
日志记录规则/批次/消息/请求身份、触发原因及结果，复用 slog，不记录附件内容或凭据。
检查指标至少包括用户/后台队列深度与最老等待时间、到期派发延迟、取消竞争失败、合并数量、静默数量和 unknown 数量；不为指标引入外部依赖。

新字段通过 protocol schema 生成 Web 类型，不手改 generated。迁移只追加，不预占迁移编号，不修改已有迁移。
本期不改变 server/runner 通信和 worker assignment，不需要仅为 owner API/UI 扩展提升 runner 协议；任何实际触及旧通信字段或默认语义的变更仍须按约束 16、17 单独评估。
新 Web 根据能力字段启用 queue/transcript/withdraw/followups，缺少能力使用旧聊天并明确缺少撤回/自动跟进，不能假装操作成功。旧 Web 继续使用原 conversation API。
先部署支持迁移及新接口的服务端，再启用新 UI；运行中的主 turn 正常排空，工具定义变化走 D81 交接。
开启新跟进前确认托管主 Agent 可用；临时不可用时保留等待事实并显示原因，不丢弃或伪称执行。
回退到旧服务端前禁用新跟进、排空/对账新批次与消息控制操作，并确认旧代码无法误投已撤回消息；做不到则禁止二进制回退，保留新服务端只回退 UI。不得删除迁移或历史来规避。

## 5. 实施阶段、验证与验收

### 阶段与交付顺序

| 阶段 | 交付 | 放行条件 |
| --- | --- | --- |
| Q1 | 消息准入/撤回事务、queue/transcript 只读投影、迁移、历史和摘要状态处理 | 撤回与领取竞态测试证明只有一方成功，旧 API 兼容 |
| Q2 | 独立队列、轮次正文、本机对账与持久草稿恢复、手机交互 | 双客户端和实际浏览器走通发送、撤回、取回编辑、刷新恢复 |
| F1 | 工作项规则、条件匹配、定时器、occurrence 与生命周期、owner API/工具 | 可控时钟与故障注入证明持久触发、无重复/盲重放、不占 slot |
| F2 | 默认事件与规则批次合并、静默 check-in、工作项等待 UI、上下文注入 | 完整目标从等待到唤醒到后续处理闭环，用户消息保持优先 |

Q1/Q2 完成即可单独交付队列体验，不等待跟进能力。每阶段使用可独立构建的原子提交，更新相关设计决策；后续阶段基于已合入阶段继续，不一次堆积完整大 PR。

### 必测场景

1. A 正在生成时连续发送 B/C：B/C 只在待处理区；A 的全部输出归 A；B 开始后进入正文，C 继续等待。服务端收到前、收到后、启动中状态清楚。
2. 两设备同时发送/撤回、一个设备多标签页发送：不丢消息、不重复恢复草稿，不按本机时间冒充服务端顺序。
3. 撤回与 NextDelivery/StartTurn 竞争、已拒绝启动的安全退回、请求重复、回执丢失、服务端重启：成功撤回的消息永不启动；启动或 unknown 的消息永不伪撤回。
4. 本机未提交取消、在途取消、lookup 暂未查到、上传中取消、提交成功但回执丢失：不把 abort/404 当成没有副作用，原 request_id 持久复用。
5. 取回编辑覆盖纯文字、纯附件、混合输入、已有草稿、旧图片、过期待决选项；在“撤回确认后、恢复前”关闭页面，恢复内容可找回且只恢复一次。
6. 长会话、超过一页的待处理项、单轮大量工具输出、SSE 乱序/重复、流式回复、滚动阅读和重连：队列计数不依赖聊天页，正文不乱归组，滚动锚点稳定。
7. 交接/升级排空/托管离线时显示真实等待原因；撤回后旧摘要失效，conversation_read 不把 queued/withdrawn 原文当新授权；owner 选择直答不产生幽灵排队。
8. 条件在登记前已满足、与登记并发满足、登记后满足：各产生一次有效唤醒；任务取消、交付未知、目标替代不能被当成成功。
9. 时间倒退/跳进、停机错过多周期、并发扫描、事务回滚：一次性不丢，周期最多补一次；UTC 与显示时区正确，固定时长周期不冒称当地每日时间。
10. 修改/暂停/恢复/取消、关闭/重开、snoozed 到期核对、期限与条件竞争：规则 revision 有效，旧版未领取输入撤销，已启动轮次保留真实历史。
11. 默认完成事件和同一条件规则同时命中：只产生同工作项一个未领取批次，所有源事实可回查；批次运行中新事件进入下一批，owner 优先、不互相自触发。
12. 周期检查无变化：不发布聊天回复、不占 worker slot、不触发新轮次；有新情况才出现结果/待决。unknown 不借下一周期重跑，人工停止后台轮次后保留真实结果。
13. 升级旧数据库、旧 Web/新服务端、新 Web/缺能力服务端、工具集交接、回退预检：原消息/附件/验收证据保留，新能力不会静默失效。

服务端单元和集成测试使用 fake harness、注入时钟/ID 和故障点，不调用真实模型。浏览器验证使用现有前端验证设施，在桌面及手机尺寸实际检查布局、输入、附件和队列迁移；仅组件/构建通过不能替代交互验收。
每阶段提交前执行 `make check`，CI 包含 Windows/macOS 交叉编译。每个 PR 合并前运行仓库规定的独立 `codex review --base main -c model='"gpt-6.1-sol"' -c model_reasoning_effort='"xhigh"'`，逐项处理意见并记录理由；较大修订重新 review。
分支从最新 main 建立，遵循既有身份与提交规范；CI 和 review 通过、rebase 最新 main 后只用 rebase merge。

### 整体验收

用户能随时回答：当前在处理哪条消息、自己还有哪些消息排队、是否仍可撤回、哪些工作项正在等待、谁会在什么条件下继续。
“明天再看”或“交付合入后继续”只有收到持久规则回执才可称为已安排；等待、触发、本轮结束、业务责任完成四者在账本与 UI 中明确区分。
主 Agent 始终是唯一协调者；正常任务完成不经过巡检 Agent；未发生变化时不制造聊天噪声。
