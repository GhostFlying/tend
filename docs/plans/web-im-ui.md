# Web IM 入口（D131、D134）

## 状态与基线

- 基于已合入的通信模型及最新 Web 路由、共享组件、阅读位置保持和 sandbox。
- 设计方向已确认；已实现新 IM、独立诊断路由、正式回复、交互与回执，本地验收与独立复核已完成，合入受 PR CI 门禁约束。
- 沿用现有中性色设计系统、导航与移动端布局。
- 先运行上游真实 sandbox 并检查桌面、手机和 Issue 看板，再以当前截图作为设计参考；未基于 sandbox 的早期概念不作为实施依据。

## 页面边界

- 新 IM 作为日常通信入口，使用 messaging API 展示输入、正式回复和面向用户的通知。
- 保留原生主 Agent 会话作为独立诊断入口，继续使用原有接口。
- 不在 IM 中呈现原生 prose、tool call 或 rollout；诊断通过明确入口进入。
- 跨渠道统一查看通信；来源标记不成为选择回复地址的控件。
- 引用回复保留输入关系；Tend 确定回复责任与目的端。
- 附件复用既有上传、预览、下载能力。
- 发送结果、阅读证据与处理状态分别表达；未知和不支持不显示为已读。
- 正式 decision/attention 在 IM 内完成回答，继续调用原业务用例；Issue 链接仅提供上下文，不作为完成回答的必要入口。
- 待处理事项作为有交互能力的正式消息出现；可保留未回复数量和定位原消息的入口，不以跳转卡片代替回答。
- 同一交互在一个渠道正式处理后，其他渠道的原消息更新为“已在 Web / Telegram 处理”，保留答案与时间并使操作失效；阅读和输入受理不触发这一状态。
- 桌面保留现有侧栏与紧凑顶栏；手机保留对话、Issues、收件箱、更多四个底部入口。

## 设计评审内容

1. 桌面完整聊天页：现有侧栏、Tend 身份、正式消息、渠道来源、引用、附件和输入框。
2. 手机布局：保持现有底部导航和触控尺寸。
3. 按需展开的消息详情：投递、阅读、处理以及诊断追踪入口。
4. 待处理、已读后处理中、等待执行、发送失败和 unknown 状态。
5. 消息内的选项、文字回答、执行受理和后续结果；同一交互在 Web、Telegram 和纯文本渠道的等价表达。

交互抽象及跨渠道一致性见 [IM 内的交互请求](im-interactions.md)。设计方向已确认，交互模型由 D134 实现。

## 实施顺序

1. 明确 IM 与 legacy 路由，接入通信查询、恢复游标与事件流。
2. 实现绑定既有业务对象的交互请求、回答准入和结果回执，再实现消息、引用、附件、发送队列与显式用户阅读确认。
3. 接入回执、处理状态及消息追踪，不推断渠道不支持的事实。
4. 扩展 sandbox 通信场景：脚本通过正式回复工具发布内容，保留原生输出供诊断；不把既有流式 prose 自动当作正式发布。浏览器回归覆盖刷新、断线和手机阅读保持。
5. 完成 Web 门禁、完整检查、独立 review 与 PR CI。

## 实现与验收记录

- `/` 为新 IM；`/diagnostics/main` 保留原生主 Agent，`/chat/:id` 保留原有具名诊断会话。两套草稿和发送队列隔离，刷新保留各自原文及附件。
- 只消费正式通信投影，倒序分页保持阅读锚点，SSE 恢复时刷新已加载问题的当前状态。
- 人工事项在引用框中明确勾选完成并提交文字说明；普通提问仍交负责人。超出原用例能力的附件另发消息，不丢弃草稿。
- Telegram 通过引用回复或 ForceReply 输入说明，完成格式为 `已完成：具体完成说明`。
- 浏览器基于真实 sandbox 验证消息、正式回复、选项、完成说明、附件、手机宽度、双草稿和刷新；跨渠道失效、离线队列与重复动作另有替身回归。
- 与已批准稿的对应：保留现有侧栏和手机底栏、Tend 标题、单列时间线、正文内问题、引用框和底部输入区。真实问题使用当前业务选项和来源，交互控件不依赖跳转 Issue；诊断入口作为次级链接。
- 真实 Bot 联调及生产部署不在此次交付验证内。

## CI 缩放回归修正

- 执行过程诊断阅读器在桌面与手机宽度之间反复切换时，可能丢失实时跟随位置；先记录滚动与布局事件顺序，定位跟随意图被改变的原因。
- 保持主动暂停和历史阅读锚点的既有语义，修正布局变化的处理，不放宽底部位置断言。
- 在既有用量与 rollout 浏览器回归中加入重复缩放，再完成独立检查和 PR CI。
