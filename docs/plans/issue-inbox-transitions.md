# Inbox Issue 流转通知

- 在正式 Issue 定义进入 Done 或 Cancelled 的事务里写入一条信息 Attention。以 Issue 和终态 revision 作为来源。
- 在既有 checks 外部等待确认进程退出、原责任及候选仍有效且同候选 CI 仍待结果时写入一条信息 Attention。以实际 wait 为来源。重叠的正式等待共享同一条通知，续行后再次让出可以产生下一轮记录。
- 待人使用已有 owner 决定和行动条目，保留原责任、处理入口和分页。Inbox 信息沿用 Issue 链接和详情读取，显示转换时间和 CI 关联交付。不提供读状态或通知计数，不派生 Chat 卡或唤醒。
- 保留现有历史 Attention。旧终态没有新增通知写入回执，迁移不重放。检查实际终态和待人样本，并区分 Main 结案回报和 Inbox 条目。
- 在实际 Issue 生命周期和外部等待操作后检查 Inbox。覆盖已完成、取消意图与结清、同一 wait 重观测、CI 已结束或未知、下一次有效等待、原决定仍能答复，以及历史和人类计数。浏览器检查通知及 Issue 链接。

主线已有同编号迁移和设计决策。本次接续采用迁移 0144 与 D263，保留主线的报告后决定字段并重新生成协议类型。浏览器路由回归检查新版 Inbox 说明文案，继续验证桌面和手机两种内边距。

## 审阅后的回归检查

- 普通通知读取原等待首次有效的 CI 失效证据。复用 #379 的内部 `board_checks` 记录，在 runner 与 server 的 provider 回执结清刷新代次后保存。已在登记时结束或停止前失效的等待，即使候选回到原 head 或同 head 开始新一轮 CI，也不能再产生通知。旧等待缺少这项原始证据时保留原续行行为。
- 按实际执行归属决定能否写入 Issue 通知。原 Run 固定的 Issue 优先，经理、独立验收和实现任务分别使用现有归属，另行验证固定责任仍有效。独立验收 Run 可以继续观察实现 Issue 的检查并据此恢复自身执行。
- 通过正式 provider 回执、实际停止和 Inbox 读取验证终态重跑、候选往返、刷新栅栏和跨 Issue 验收。报告结案测试同时核对原决定可读、唯一终态通知和行动计数。
