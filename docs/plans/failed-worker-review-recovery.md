# 失败执行结算与独立审阅恢复

## 业务起点与终点

独立报告审阅使用普通 implement Run。原生 turn 给出终态失败且原进程已退出时，重启或短暂本地写入失败可能留下 started journal。现有恢复先找已提交报告，缺少报告即绕回传输恢复。触发案例为 #401 的独立审阅。#405 的 Issue owner 传输停止和 #406 的外部等待订阅有独立业务入口。

原 Run 通过正常 release 保存原生失败、结束原 action、释放 lease 与 slot。终态与物理停妥分别从原记录核实。原运行实体、原报告与未决副作用继续可查。缺少停妥依据保留原 Run，原身份对账后才考虑后续工作。报告不存在也是合法的失败结果。已经完成的真实报告与独立审阅登记照常使用。

## 实施和验证

1. Runner 保留 terminal turn 的类型化错误和原 turn / attempt，重用原进程证明和 journal 的 release 流程。正常失败与重启恢复使用同一路径。测试使用本地替身和隔离进程，覆盖没有报告、临时停妥或上报故障、相同 release 重送以及没有物理证明。
2. 持久的独立审阅身份来自任务契约或共享审阅绑定。与原义务相关的技术失败通知当前 Issue owner。通过现有动作入口显式选择再执行，在同一事务核对授权、失败事实和原义务余量。提醒仅通知，不创建技术重试。最多追加三个明确授权的 Run，失败历史接续可查。最后一次仍失败时通过现有用户通知路径报告证据和可执行的下一步。Provider 策略终态保留原原因并提示处置，不提供原工作重试。
3. 隔离测试走真实的 Run 失败上报、具名 owner 动作、重复请求、其他启动路径与用户通知，验证同义务的限制及未知对账边界。常规 findings 与正式合格报告继续沿现有审阅契约。没有生产状态变更。

已声明的 PR 审阅在领取时保存独立的候选身份。对新 Task、此前已排队的 Task 与正式
审阅重新绑定执行同一待决义务核对。同一候选上的换 Task 不能消耗新的预算；已观察到
不同的 head/base 或不同不可变制品可形成新的审阅义务。缺失候选证据时保留原义务。

明确的技术重试通常使用原 Task。Issue 责任交接使原 Task 的执行契约过期时，当前负责
人可以沿既有 follow_up 关系指定同一已知义务，另行建立当前执行契约。授权与后继 action
同事务消费原失败，同一候选沿原预算结算。正式登记只接收有该恢复凭证的真实产出，
继续验证原候选、要求、独立 reviewer 与执行资格。
