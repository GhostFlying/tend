# 负责人 Run 短暂超时恢复

原交付在一个已经处理的负责人事件等待 SQLite ACK 时中止。应用层写入与 ACK 是两个事务。验证以隔离数据库中实际排满写连接为起点，正常事件处理后保留原 Run、事件序号和会话。最终要求原 turn 能继续处理输入并完成其可授权的工作。

1. Server 保留 handler 成功后的原事件身份。采用有限的独立 ACK 尝试，事务未进入业务回调时可补写。提交无法确认时查原事件和这次 flush 所覆盖的前缀。实时重试前重新验证当前责任、控制及租约。已结束 Run 仍沿既有历史结清路径。
2. Runner 让本机 journal 保留原信封，在有效租约内退避恢复有序上传、反向领取及已记录的回包。短暂读取故障保留 Server 的原回放位置。原生进程确实退出和 journal 无法保存走现有停机路径。
3. 真实停妥后，由原 Task 调度事务核对故障来源、尾部、业务回执及授权。以恢复链起点防重复，最多创建一个有可靠恢复位置的同 Task 后继。仍影响剩余工作的 unknown 使用原身份继续对账。
4. 隔离环境覆盖写连接超时、请求或响应丢失、未知结果、真实停妥和重复停止回执、撤销及租约竞争。保留实际独立审阅和受保护分支检查。生产记录用于对照因果时序。

第一步保持现有 wire 和持久事件格式。后续会在对应变更中明确兼容行为与恢复事实的持久化边界。

PR #393 审阅修正沿用协议感知的有效租约判定。回放时将历史来源与原事件标识一起保存在 Server attachment，关闭排空按原回执身份结算。只重试未进入写回调的 ACK，提交未知仍读取原事件和覆盖范围。隔离回归覆盖协议 6 到期、协议 7 越过旧期限及显式围栏、已停原 Run 结算尾部。

只读回执附件从启动排空开始就按原回执结算，覆盖 close 已在途但真实停妥回执仍未入账的窗口。隔离回归验证等待原序号的 close 在 ACK 写入短暂超时后仍能结清。

原工具回调的结果一旦被 Runner 消费或明确拒绝，随后 ACK 结清的是已处理的原事件。回调在协调会话的异步处理函数发 ACK，可能与 close 并发。该 ACK 沿原 Run/seq 走有界回执结算，在 writer 第一次未开始的超时后可继续结清。普通实时事件的恢复继续核对原租约与业务授权。隔离回归在原工具结果已消费后挂起回调，领取同一会话的 close，再注入 ACK writer 超时并验证原关闭结清、handler 仍只执行一次。

普通事件可能在第一次 ACK 等待 writer 时进入关闭。实时重试在写事务内重新读取原 Run。已入队的正式 close 可以结清同一原事件。已确认物理停妥时，只结清当前停妥凭证覆盖的 Seq。其他情况仍核对当前租约、控制、责任和撤销。已进入事务但结果未知时继续按原身份读回，不改用另一条写路径。隔离测试在首次事务未开始的超时后分别提交 close 与物理停妥，再放行原 ACK，检查原水位和原关闭回执。

正常结案与原生 close 入队之间也要能补写已处理事件的 ACK。ACK 重试沿用原 Run 的派发、任务控制、租约、维护围栏及来源授权检查，仅允许同一职责周期内仍由原负责人结清终态 Issue 的回执。业务操作继续使用原准入规则。测试在真实写连接超时后用正常 Issue 控制操作结案，放行 ACK，再验证同一关闭请求和原事件水位。

第二阶段让 Server 从同一回放游标重新读取完整批次。Runner 未协商 EventSync 时，同步发送也在原执行上下文内处理短暂故障；按 journal 顺序等待原事件确认后才继续。普通 native 回包使用原 command 与请求，明确拒绝或执行上下文结束停止等待。关闭和停妥继续使用原收尾路径与预算。
