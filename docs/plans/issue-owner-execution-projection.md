# Issue 负责人执行投影

## 业务契约与审阅范围

审阅已结清或在等下一轮时，Issue 负责人可能正在独立协调。看板调用
`GET /api/v1/issues?board=true`，CLI 通过 `tend issue list --board`
读取同一 API。当前投影只统计普通 Task，导致有实际负责人 Run 的卡片
仍显示零项运行或仅显示审阅排队。目标是从账本重建当前执行，在原看板和
CLI 读路径中体现状态。读取不会发起执行、改变任务约定或移动看板工作状态。
Refs: D246、D128。

## 实施

1. 在 Issue 汇总中增加当前 owner carrier 的执行投影。验证 Issue 归属、当前
   指派代次和已冻结的 Agent 身份。先读取仍开放的实际协调 Run，再读取已确认
   停止且释放 lease 的外部等待，最后采用已发布且仍待领取的协调动作。首次
   领取前采用现有调度候选。普通 Task 继续按现有责任归集，同一 Run 只统计
   一次。历史终态 Run 不计入执行或完成数量。
2. 看板和 CLI 复用该计数。用独立的可选 owner API 字段表达外部等待，保持旧
   数据可读和 runner 协议不变。看板沿现有 Issue、Task 和 Run 事件刷新，工作
   状态、分组与人工处理过滤仍读取原有事实。
3. 通过真实领取、启动、请求等待、物理停止、重新排队和后继领取验证状态与
   事件水位。回归覆盖负责人和普通 Task 并发、重复关联、已结束 Run、其他
   Issue 和旧代次，以及 CLI 的 JSON 与可读输出。独立分支基于最新 main，另
   用看板分组和待处理筛选候选做兼容验证。

## 子 Issue 预览补充

独立复查发现父卡片的子 Issue 预览和展开列表读取了外部等待计数，但两处共用的标签
仍回退到工作状态。CLI 的子 Issue 摘要也缺少该计数。补齐这两个读取入口，在当前
main 的看板布局上用同一等待数据验证折叠预览、展开列表、详情和 CLI 文本。

## 混合状态与首轮回归

正式审阅发现父卡片会在普通任务运行时隐藏外部等待，在审阅排队时隐藏暂停，
原有防自唤醒测试也仍按旧规则期待零项执行。修复卡片标签组合并补齐两组混合状态
回归。更新领取后的精确启动计数，保留防自唤醒断言。
