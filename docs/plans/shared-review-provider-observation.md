# 共享 PR 审阅的 provider 当前观察

## 问题

共享审阅关联多个 Issue 与贡献 Task。当前有效性投影逐个读取各责任的 provider 缓存；已关闭责任不再刷新，历史候选会反向否定对当前候选已正式通过的审阅。重新 record 或 assess 仍无法消除其他关联责任上的旧缓存。

## 目标与边界

1. 将相同 provider/repository/number 的当前候选作为同一项事实处理，保留各责任及历史观察，不要求所有历史缓存同步到同一个 head/base。
2. 继续校验全部关联责任的交付链接、真实业务需求、贡献范围及正式审阅执行要求。真实候选变化仍使旧结论失效；未知、失败或刷新中观察不得被旧成功缓存掩盖。
3. 修复须让已存在的正式审阅在真实观察一致时自然恢复有效，不手工篡改 valid、不伪造或重复独立审阅，不重放业务动作。
4. 先核实现有 target 级存储和观察时序，复用一致的 provider 事实选择；避免全局扫描、按 Issue 是否关闭添加事故特例，或新增不必要的协议与调度机制。

## 实施

- A1：定位 provider 观察的持久化、轮询和共享审阅投影调用链，复现旧已关闭关联保留旧候选、新候选 record 已通过却仍失效的状态转换。
- A2：统一候选当前观察的选择，并让共享审阅投影使用它；在同一变更更新设计决策。
- A3：针对历史旧缓存、当前未知/刷新、真正 head/base 变化以及需求/执行要求变化做有意义的回归验证，保留错误原件。
- A4：按仓库门槛完成完整检查、独立审阅、最终候选 CI 和 rebase 合入。依据实际新 main 的完整发布集合同进行同配置受控部署，保留在途工作和原请求。
- A5：读回真实共享审阅及负责人状态；让 Tend 继续原 PR 的合入和交付，并继续既有监控。
