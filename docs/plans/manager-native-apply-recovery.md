# 从原序号恢复负责人原生事件投影

负责人事件已被 Runner 和服务端按原 Run、原序号保存。服务端会话读取一批原件时，
读取游标会先前进。若 SQLite 投影失败，随后 drain 仍可能看到更晚的事件，而原件只能
等另一条执行链再次读取。部分物料已提交时，重复使用会话内状态也可能把工具归到新输入。

## 业务契约

从已持久化的最早未应用序号恢复同一 Run 的投影。收件游标与已应用连续前缀分别计算。
发现缺口时保留未应用原件。投影复用原始 thread、物料、逻辑 turn 和已保存的消息来源。
实际工具结果和终态继续来自原始事实。尚未对账的回调、外部效果和停止都保留原状态。

1. 首先把 Issue 负责人可独立重建的工具和 reasoning 等原生条目绑定到事务内投影。
   事务读取原 Run、原序号和原件，复用已存在的投影与原消息来源，最后记录应用位。
   提交回复不明时从原行读应用位。仍缺失时按有界预算重试同一投影。
2. 服务进程独立扫描已有原停妥证明或原 close 已被领取的 Run。close 可以等待其原
   事件得到应用，应用本身不产生停妥证明。每个 Run 先取最早
   未应用原件。记录有限的失败预算和失效位置。失败记录不替代原件和原事件账本。
3. 独立恢复器只写已有事件对应的本地事实。原 close、Runner receipt、租约和责任
   继续由已有守卫推进。原工具结果未知时保留阻塞，禁用历史回调的重新执行路径。
4. 通过隔离 SQLite 和正式接收/恢复链验证首次失败、部分写入、重启、停止/取消、
   缺口、未知提交回执、原消息路由和实际调度。单独记录实际两组原始输入的验收对应表，
   保护私有原件，不向 GitHub 提交生产正文。
5. 候选从实际交付目标分支准备。与现有应用后 ACK 恢复共用原身份及应用位。独立复核及
   所需本地检查与 CI 通过后，按仓库规则合入。
6. 恢复工具开始事件时，若同一 Run 的有效停妥回执已覆盖原序号，将展示状态
   记为中断。原生开始事实照常保留，之后恢复的实际终态仍可覆盖中断。同线程的
   上下文快照优先按原修订排序，跨线程仍按已记录的时间判断，不降低时间水位。
   用直接 Issue 消息和交错的收件、投影时间分别验收。
7. 恢复停妥后的回调时，沿同一 Run、原回调及原投递请求核对已确认的拒绝，只更新
   投递状态，保留工具本身的结果。在线与附着前缓冲的历史回调共用投影守卫。
   已应用水位从第一条缺失或未应用序号前停止。用确定拒绝后还有待应用尾部、
   附着前历史回调和连续多条缺口分别验证。

Refs: D262、D268。

## 晚到的观察和来源

- 原 Run 中更晚的同工具完成观察已经应用时，旧的运行中观察只补原始记录和应用位。
  依据覆盖较新观察的原停妥证明收束运行状态，并保留已有输出和来源。
- 如果缺失的是命令的后台运行观察，先核对同一原 Run、线程、回合、根回合和工具中已应用的
  后序终态。仅当终态与既有 rollout 一致且两条观察符合原命令阶段转换时，允许补录旧观察。
  验证两条原件均保留、终态输出不变，且冲突的 rollout 仍阻止应用位推进。
- 队首缺少原回合来源时，保存明确依赖并停止定时重试。收到唯一且属于同一 Run、
  会话、线程及根回合的原绑定后，恢复器重新校验并接续队首。瞬时写入错误仍有界重试。
- 验证后序已应用但前序缺失的原输出，以及邻接请求不能解除停放、迟到权威来源
  到达后正常消费者恢复原队首并推进连续应用水位。
