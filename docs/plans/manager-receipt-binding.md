# Manager 回执恢复保留原执行模式

## 问题与边界

已接收的 manager 执行可能在事件落账超时后进入关闭对账。原生工具模式是已接受执行快照的一部分，参与已有线程的 binding 身份；`ReceiptOnly` 和 `RequireReceiptReader` 则决定当前附着可以做什么。当前选择器在关闭、park 或严格 reader 状态下清除原生工具模式，使同一责任计算出另一个 binding。查不到原线程后，启动路径可能尝试创建线程，又被围栏拒绝，无法消费仍保留的原事件和关闭回执。

修复必须保留已有 binding 算法和历史快照，不迁移线程、不重放原输入，不扩大 fenced manager 可以执行的命令。最初的写连接等待超时与恢复路径的身份错误分别记录；本计划修复后者，使任何相同的暂时退出都能恢复原回执。

## 实施

1. 在当前 main 上用真实 manager 选择器复现：冻结原生工具模式、建立原线程 binding、排入原 close，再读取启动选择；断言原模式和 binding 保持，恢复仍为 receipt-only。
2. 把原生工具标记保留为已接受的执行模式。当前运行进入关闭或受限读取时，不用临时权限状态改写该模式；新普通执行继续按实际协商能力准入。
3. 覆盖关闭和严格回执 reader 的选择、原线程恢复及禁止新原生工作的边界。保留原有未协商执行不因升级扩大能力的回归。
4. 更新 D208，说明执行身份与当前许可分别派生。私有选择语义修正不改变通信字段、runner assignment、协议版本、存储格式或历史 binding。
5. 完成定向回归、独立审阅、完整 `make check CHECK_JOBS=0 TEST_COUNT=1` 和最终候选 CI，经 PR rebase 合入。使用实际合入版本的完整发布集受控部署，再按原回执证据恢复原 Issue。

## 验收

- 关闭前后的同一执行仍找到同一个已绑定线程，没有新增 `start`、turn 或 handoff。
- 原 close、未应用事件、未知请求和业务回执按实际结果结清，失败不伪造成功。
- receipt-only/严格 reader 仍不能启动新业务；新执行的原生工具能力仍须显式协商。
- 现场部署完成与原业务交付分别证明，监控继续沿原 Issue。
