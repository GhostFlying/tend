# 按用户约定发布进展和结果

原目标是让使用者在约定终点看到一次可信结果，也能随时追问或在确需选择时收到已有决策卡。PR 登记、审阅、CI、分配、可恢复阻碍和等待已经有 Issue 进展、业务事实与后台唤醒。当前 Agent 指令还要求把普通阶段进展发到聊天，后台回合也可能将内部事件作为回复对象。

1. 调整主 Agent、Issue owner、后台输入与通信工具的发布指导。主动发布前看用户的交付约定和已发生的事实，普通进展保存在原 Issue，主动追问沿输入答复，受实质影响的承诺及时说明，真正的选择沿原卡处理。
2. 在已有 Issue 计划、承诺和消息收据上表达跨 Issue 的统一交付，记录明确成员、触发终点和稳定的发布身份。覆盖部分完成、成员取消、约定调整、恢复及重复回调。沿用既有消息投递与 unknown 对账。
3. 区分内部代理对 Attention 的答复与人类输入，保留答案及审计身份；只把属于人的提问及答复投影到用户通信。
4. 验证自动合入的中间进展、本来需要人的决策、按需追问和明确要求的阶段通知，以及跨 Issue 的原子发布。测试中区分 fixture 预置的外部观察与真正执行的发布转换；合入跟踪和部署依原授权。

独立审阅复现了连续追问的断点。用户引用汇总、Main 按原问题答复并关联多项 Issue 后，下一次引用答复会触发多责任歧义。沿持久化的实际回复关系认领同一段汇总讨论，验证再次追问仍进入 Main，并保留普通多 Issue 消息、单 Issue 责任与已取消约定的路由语义。

复审还覆盖同一原话的成员和输入身份。验证 Main 消费回合中的补充提问后能正式答复该条消息，后台仅持有历史原话时仍保持安静。同一原话可关联独立 Issue，显式发布独立 Issue 的结果按其实际责任判断，省略范围时才使用触发消息及后台批次的责任。
