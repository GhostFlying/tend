# IM 内的交互请求

状态：设计方向已确认，包含跨渠道处理来源提示；待实施。Refs: D131、D53、D89、D133。

## 产品目标

用户在消息内看到问题、选择或补充、提交回答，并收到真实处理结果。Issue 和任务链接用于查看上下文，不作为必经步骤。Web、Telegram 以及只能收发文本的渠道具有相同的业务能力，展示方式按渠道能力变化。

前一版固定在输入框上方的“查看并处理”摘要不是新 IM 的交互方案。待处理请求进入消息时间线，可通过轻量的未回答数量定位原消息；不要求用户跳转到 Issue 或收件箱才能回答。收件箱继续提供聚合视图。

## 三层职责

| 层 | 职责 |
| --- | --- |
| 业务对象 | decision、attention、worker question 和现有控制对象保持权威状态、版本、权限及实际副作用 |
| 交互请求 | 将问题及允许的回答方式绑定到业务对象，记录发布消息、版本、回答来源和结果关联 |
| 渠道呈现 | Web 消息内控件、Telegram 消息与按钮、纯文本问题与引用回复；将输入规范化后交回应用层 |

交互请求不是另一套 decision 状态机，也不是通用表单或任意命令引擎。它不复制 Issue 责任、不独立宣告问题已解决、不允许 Agent 提交任意 HTTP 操作或收件地址。

## 最小模型

下列描述模型职责；实际 DTO 唯一定义于 protocol。

**InteractionRequest**：

- 稳定交互身份，与原 decision/attention/control 对象关联；同一业务问题多渠道共用。
- 原业务身份、问题版本及需要的控制版本；问题版本和内容版本不混用。
- 发布消息身份及冻结的问题版本引用、依据摘要、选项和对应后果。正文复用正式消息，历史提问保持原版。
- 允许的回答：选择、文本、选择加补充、明确完成确认；附件仅在原用例支持时开放。
- 允许的 action 引用及字段约束，由服务端登记和校验；显示标签不承担动作身份。
- 当前可操作性从业务对象派生：可回答、已回答、已替代、已撤回或不再适用。

**InteractionResponse**：

- request_id、交互身份、用户实际看到的版本、action/option 引用，以及文本与已授权附件。
- 已认证的用户身份、来源消息或 callback 身份、实际来源端点及目标提问消息；不能由 Agent 填写渠道地址。
- 回答受理与业务执行结果分别关联。相同输入重放恢复同一结果，不重复记录回答正文或重复执行。
- 正式受理的回答关联实际处理渠道、处理时间、答案摘要和响应身份，供所有已发布端点呈现同一结果；不以最后一次读取或按钮点击的渠道覆盖处理来源。

**InteractionPresentation**：

- 各渠道的消息与分片映射、问题版本、展示版本以及允许的动作引用。
- Telegram callback 使用短的不透明引用，由服务端解析并再次验证绑定关系；不是携带权限的通用命令。
- Web 和各外部渠道都使用同一业务对象判断是否仍可回答；过期按钮是否及时移除不影响正确性。

## Agent 与 harness 的边界

- Agent 通过既有业务工具提出问题、补充依据或解释回答；服务端从合法业务对象构造可回答的交互，不让 Agent 手写任意卡片或按钮命令。
- 呈现、渠道能力选择、外部地址和 callback 映射由 Tend/adapter 确定；Agent 不参与判断目的渠道。
- 精确选项和已登记控制由应用层执行；自由文字及新条件交给准入时的当前负责人，不要求主 Agent 中转，也不交给历史负责人的失效执行。
- 负责人不可用时明确表示等待，并保留原问题与回答；不偷偷换人或把业务对象当成已经解决。

## 用户路径

### 明确选择

1. Tend 在消息中给出“实现失败，接下来怎么办？”，解释已有选项的后果，并附可选 Issue 链接。
2. 用户点击“重新实现”或引用此消息回复该选项。
3. Tend 核对用户、原问题版本、选项及对象控制版本，通过原业务用例原子记录回答和必要动作。
4. 消息中显示“已记录你的选择：重新实现”；只有确认已入队时才显示“已安排重试，等待执行”。
5. 真实执行开始或产生终态后再追加对应反馈，不把回答成功说成任务完成。

明确、合法的选项可以直接处理，不要求一律唤醒模型或再次确认。语义本来就是确认的动作直接表达确认；只有需要澄清目标或存在明确的额外确认要求时才增加步骤。

### 文本或补充

- Web 点击“文字回答”或引用问题，输入框显示被回答问题及已有选项；取消引用即恢复普通聊天。
- Telegram 可直接引用 Bot 的问题消息回复，保持原外部消息关系；不增加 /issue 命令。
- 输入“重新实现，先补上数据库兼容性检查”时，不能丢掉补充说明后直接重试旧要求。带新条件的回答交由当前责任方按原业务合同处理；必要时在原 IM 中确认具体动作。
- 不明确的自然语言先作为原问题的用户输入保留，由负责人解释、澄清并依法正式记录；不能仅靠关键词猜测选项，或把正文中的选项名称当成授权。
- 多个问题并存且未引用时，在同一 IM 内询问具体目标并提供选择；不默认回答最近一件。
- 已经成功提交的回答不能靠编辑原聊天消息自动撤销或改选；后续更正作为新来源处理。

### 人工行动与任务控制

- attention 的人工行动可在消息中提交明确的完成说明，经原 confirm 用例处理；“我读了”不等于“我完成了”。
- 信息通知不强制索取回答；已读、已归档不成为人工行动完成或 Issue 关闭证据。
- 暂停、恢复、取消、交还等控制可复用相同交互结构，但每项必须登记到现有用例并校验实际控制版本。首批先完成 decision、worker 提问和人工行动确认，不顺带构建任意控制指令系统。

## 渠道呈现

| 能力 | Web IM | Telegram 私聊 | 纯文本回退 |
| --- | --- | --- | --- |
| 提问 | 时间线内问题、依据摘要、选项 | Bot 正文与 inline keyboard | 正文、后果说明及选项文字 |
| 明确选择 | 消息内按钮 | 原消息下 callback 按钮 | 引用问题后回复完整选项或该版选项编号 |
| 自由回答 | 引用输入框，或消息内轻量输入 | 引用问题回复；必要时使用 ForceReply | 引用问题回复；无原生引用时使用有作用域的问题短标识 |
| 完成确认 | 带说明的确认控件 | 回复完成说明及适用的确认按钮 | 明确完成说明，保留原问题关联 |
| 结果 | 回答摘要、单独的执行状态、时间线反馈 | 更新原消息的操作区并发送必要反馈 | 追加结果，写明原问题关联 |
| 其他渠道已处理 | 原消息移除或禁用操作，显示“已在 Telegram 处理”及答案摘要、时间 | 编辑原消息，显示“已在 Web 处理”并移除按钮 | 追加关联原提问的失效说明，标明实际处理渠道 |
| 问题变化 | 原提问标注已更新，展示新问题 | 移除旧按钮并发布新版 | 明确旧问题不再适用，重新提问 |

Telegram v1 使用现有 SDK 能承载的正文、InlineKeyboardMarkup、CallbackQuery、ForceReply 与编辑接口；不依赖新 RichMessage、Mini App 或全局 reply keyboard。引用文字路径与卡片路径具有相同校验要求。

按钮回调先持久化 inbox，再尽快 answerCallbackQuery 解除客户端等待。回调确认只表示回调已收到；不能显示业务执行成功，不等待模型回合才反馈。callback_query 加入 Tend 自管 polling 的更新类型与恢复路径。

Telegram 按钮点击本身不产生一条用户聊天消息。Tend 记录真实 callback 来源和“通过按钮选择”的 owner 行为，不伪造 Telegram 用户消息 ID 或发送回执；需要聊天反馈时由 Bot 正式发送。

callback_data 上限为 1–64 字节，保存短引用而非完整 JSON 或业务权限。需验证当前绑定用户、私聊、Bot 身份、原消息映射和问题版本。原生可选能力见 [InlineKeyboardButton](https://core.telegram.org/bots/api#inlinekeyboardbutton)、[CallbackQuery](https://core.telegram.org/bots/api#callbackquery)、[ForceReply](https://core.telegram.org/bots/api#forcereply) 与 [编辑按钮](https://core.telegram.org/bots/api#editmessagereplymarkup)。

## 处理与回执

回答受理、业务动作和渠道更新是不同事实：

- 输入已收到：只表示有持久化来源；Bot callback ACK 也只表示这一层。
- 回答已记录：原业务用例已接受该版答案。
- 正在协调或等待执行：当前责任方或调度路径的真实状态。
- 业务效果已应用、失败、未应用或未知：由原用例与执行记录决定，不由按钮状态决定。

确定选项的来源、回答、领域事件与必要 outbox 在一个应用层事务内完成；外部发送和按钮编辑在提交后执行。需要 Agent 解释的回答先持久保存原文与问题版本，再唤醒当前负责人；不新建第二个负责决策的 Agent。

Tend 从用户此次回答的来源端点决定即时回执目的地：Telegram 回答回原私聊，Web 回答回 Web。Web 统一查询可看到全部状态。另一个已发布端点上的旧按钮通过状态同步失效，但不因此复制一条聊天回复；后续独立业务通知仍按 D131 通知策略投递。

### 跨渠道处理后的失效展示

一个渠道的回答或明确确认被原业务用例正式接受后，同一交互在其他渠道自动失效，并更新原提问的展示。不能只在服务端拒绝旧按钮而让用户仍看到可操作界面。

- Telegram 处理后，Web 原消息显示“已在 Telegram 处理 · 重新实现 · 10:44”；Web 处理后，Telegram 原消息显示“已在 Web 处理 · 重新实现 · 10:44”。
- 原问题和答案历史保留，按钮、回答表单及已打开的回答草稿的提交入口变为不可操作；保留尚未提交的文字供复制或作为后续新消息发送，不静默丢弃或提交它。
- “已在其他渠道处理”表达该请求已获得正式回答；若实际动作仍在排队，单独显示“等待执行”。不得把它写成任务或 Issue 已完成。
- 普通已读、callback ACK、收到聊天文字、待负责人解释以及结果 unknown 都不触发“已处理”。问题被撤回或替代使用对应原因，不伪称某渠道已处理。
- 接受回答的事务记录权威结果及实际处理来源，追加状态事件，并为所有已发布端点登记必要的展示更新。提交后立即推送 Web 事件并调度外部渠道更新，不等待本轮模型完成。
- 只同步该交互已有的发布端点，不因为新绑定渠道而补发历史问题。展示使用 Web、Telegram 等渠道名，不暴露私聊地址或内部执行标识。
- 外部编辑失败时保留待同步状态并恢复重试；原消息不可编辑时发送一条稳定去重、关联原提问的“已在 Web / Telegram 处理”说明。展示更新不再次执行原业务动作。
- 网络延迟、离线设备或同步失败期间若用户仍点击旧按钮，服务端返回已知处理渠道、时间和答案，客户端据此更新失效 UI；冲突回答不覆盖已受理结果。

同一交互在 Web 和 Telegram 同时回答时，原业务事务决定结果。重复的同一答案返回已知结果；冲突的后到答案提示已回答，不再次执行。问题版本变化后不替用户升级版本重试，也不强制在别的页面重新操作。

旧消息的展示可刷新状态或移除按钮，账本仍保留用户当时看见的问题、回答原文与效果。渠道编辑失败不回滚已记录答案；独立对账继续恢复展示。响应丢失时查询原 request_id，不用新身份重新执行。

## 实施增量与验收

当前 D131 已有消息、投递、阅读和责任路由；尚无此交互投影、Telegram callback 消费或跨渠道操作区同步。仅做 Web 按钮不能补齐这些合同。

1. protocol 定义交互引用、问题快照、允许回答及结果投影；服务端从原业务对象构造，不新增另一份待决事实。
2. app 提供统一回答准入，委托现有业务用例；来源、版本、操作身份与原负责人关联在事务内冻结。
3. Web 按消息渲染控件；Telegram 持久消费 callback 并映射引用文本；状态变化驱动展示同步和必要结果发布。
4. sandbox 通过原业务用例生成问题与答案，展示可直接执行的失败重试、worker 自由回答及人工完成说明。
5. 验收引用文字、按钮、补充说明、并发跨渠道、重复回调、旧版本、解绑、未知结果、原消息不可编辑与重启恢复；不允许聊天绕过正式决策校验。
6. 双向验证 Web 回答后 Telegram 显示“已在 Web 处理”、Telegram 回答后 Web 显示“已在 Telegram 处理”；检查按钮和已打开的回答入口失效、未提交草稿保留、答案和处理时间一致、执行状态单独展示。覆盖离线恢复、编辑失败、旧按钮回调和并发冲突，不出现第二次业务效果或虚假的已同步状态。

模型决策已记录为 D134。实现为追加迁移和增量 owner API，runner 协议继续保持 2/1。

## 交付验证

- I1–I5 已实现并通过本地验收；I6 的完整本地检查、独立 CLI review、跨平台编译及浏览器回归已通过，合入继续受 PR CI 门禁约束。
- 问题快照引用原业务对象及版本；提交来源仅在正式受理时冻结。已读、回调 ACK、含新条件的讨论均不关闭问题。
- Telegram 的文字回答提示只投原私聊，不按主动通知规则广播。已关闭按钮返回现有结果，原消息不可编辑时发送一次持久化关联提示；发送结果 unknown 保留对账。
- 单元测试覆盖 Web 与 Telegram 双向失效、版本更正、重复或冲突选择、人工行动、引用附加要求、持久化回调与不可编辑回退；浏览器覆盖已打开引用的跨渠道失效与草稿保留。

- 独立 review 复现并修正：原始输入保留、数字选项歧义、长回答确认、问题依据和安全诊断、人工完成处理状态、迟到文字、ForceReply 附件责任与交接、历史缺页和失效重试、已处理输入的责任变化、历史已提交队列、新标签页草稿及提醒窗口区分。最终复核没有剩余可执行问题。
- 真实 sandbox 验证正式回复的精确来源、工具消费已读、原附件下载字节、桌面／手机、诊断草稿隔离与刷新；跨渠道及 Bot 行为使用替身验证。真实 Bot 联调与部署单独执行。
